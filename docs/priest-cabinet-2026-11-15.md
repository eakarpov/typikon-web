# Кабинет иерея — реализация 15.11.2026

## Проверенная исходная цепочка

Веб-репозиторий: `/Users/georgecarpow/Documents/own/typikon-web`.

- `/pomyannik/priem`: заявка с саном и именем, страницей епархии, почтой и комментарием.
- `commemoratorClaims`: pending → letter-sent → verified → approved / rejected.
- `/api/admin/commemorators`: модератор с правом `commemoration.claims` отправляет письмо, сверяет ответ и принимает решение. Мобильная заявка попадает в ту же коллекцию; код письма приложению не отдаётся.
- `commemorators`: одобренный принимающий; прежние `public`, `accepts`, slug и inviteCode сохранены. Повторное одобрение сохраняет новые настройки.
- Раньше `accepts: []` означало «всё», а записка всегда требовала code или slug. Дат служб и общей очереди не было.

## Мобильные входы

- Моё → Аккаунт → Доступ для священнослужителей (`/priest/access`). Ссылка также есть в секции аккаунта существующих настроек.
- Моё → Кабинет иерея (`/priest`) виден только после подтверждения сервером.
- Список / Чтение работают с одной пачкой выбранной службы и даты. Открытие записки не ставит отметку. «Помянуть» сохраняет отметку и переходит дальше; ошибка не переводит к следующей.
- После основной пачки можно добровольно брать по одной дополнительной записке. «Помянуть и закончить» не резервирует следующую. После перезапуска дополнительная непомянутая записка остаётся за тем же иереем.
- Настройки: три независимых вида, по 30 имён, приём и напоминания по умолчанию выключены; дата/время и IANA-пояс службы; необязательные реквизиты.
- Моё → Мои поданные записки: состояние ожидания / назначенная служба / поминовение. После подачи показываются дата и реквизиты только реально назначенного получателя.
- В меню кабинета сохранён переход к прежнему экрану всех принятых записок, включая длящиеся поминовения.

## Серверный контракт

Все новые адреса — `/api/v2/pomyannik/priest/*`, с обычным `pomyannik` scope и пользовательской сессией; успешные ответы private,no-store.

| Адрес | Метод | Назначение |
|---|---|---|
| profile | GET | approved, безопасная заявка, данные иерея, действующие настройки |
| claim | POST | Подача / повторная подача отклонённой заявки в существующий разбор |
| settings | PUT | Три вида служб и donationDetails; confirmReschedule при переносе принятых записок |
| queue | GET | Пачки служб, их записки, флаг extra и счётчики свободной очереди |
| queue | POST | action=read с noteId либо action=extra с serviceId |
| notice | GET | Проверка актуальности напоминания по serviceId перед показом |

`POST /api/v2/pomyannik/zapiski` принимает `queue: true`. Без code/slug выбирается подходящий иерей; с адресатом записка остаётся адресной. При включённой новой схеме адресные подачи из старого веба также попадают в очередь. Длительные виды сохраняют прежнюю цепочку и не выдаются за разовое поминовение.

Ответ записки дополнен `queueStatus` (waiting/assigned/read/expired) и `assignment` (serviceId, startsAt, timeZone, title, place, donationDetails). Назначения вычисляются из серверного журнала; клиент не угадывает дату по настройкам.

## Инварианты очереди

- `priestServices` хранит службу и журнал резервов: ID записки, число имён, readAt и extra. Имена остаются в исходном снимке `zapiski`.
- Уникальный multikey-индекс `entries.noteId` запрещает назначение одной записки двум службам. Атомарное условие вместимости и проверка revision не позволяют превысить обычный лимит при конкурентной подаче. Replica set и транзакции не требуются.
- Лимит считается в именах на службу; прочтение не освобождает квоту. Записки не дробятся.
- Первоначальный подбор разрешён через две минуты после включения. Новые записки после этого резервируются при подаче; обработчик добирает ожидающие, начиная со старых.
- Распределение: ближайшая дата, затем доля использованного лимита и время предыдущего назначения. Подтверждение иерея и запрет подачи самому себе проверяются сервером.
- Сверх лимита выдаётся только свободная записка. Чужие назначения не перехватываются.
- Отключение приёма сохраняет уже принятые записки. Уменьшение ниже принятого основного объёма запрещено. Перенос непомянутой пачки требует явного подтверждения; подающие видят обновлённую дату.
- После завершённой пачки новая дата создаёт новую службу, старая доступна в истории. Старые непрочитанные разовые записки при подключении настроек переходят в адресную очередь без изменения имён и времени подачи.
- Подача поддерживает requestId: параллельные повторы и потеря ответа не создают второй снимок.
- Отметка идемпотентна. Журнал службы — источник истины; обработчик восстанавливает readAt записки после сбоя между записью журнала и обновлением проекции.
- Существующая чистка имён сохранена. Записку со стёртыми непомянутыми именами нельзя отметить исполненной.

## Обработчик и публикация

Веб-команда `npm run priest:dispatch` — просмотр без изменений. `npm run priest:dispatch -- --run` распределяет очередь и отправляет условные напоминания. Отсутствие FCM не останавливает распределение.

После публикации backend нужен запуск **раз в минуту**, например в существующем серверном crontab:

```cron
* * * * * cd /var/www/typikon.su/typikon-web && npm run priest:dispatch -- --run 2>&1 | logger -t priest-queue
```

Напоминание уходит в часовом окне перед службой, только при включённой настройке и непомянутых записях. Повторные запуски защищены lease и отметкой доставки; устройство дополнительно дедуплицирует показ. Push содержит только вид сообщения и ID службы. Приложение проверяет сессию и актуальность на сервере, затем показывает общий текст без имён и открывает конкретную службу.

В этой задаче production, crontab, публичный APK и эндпойнт версии **не изменялись**. Для работы новых экранов у пользователей нужно выпустить backend и поставить обработчик. Доставку FCM нужно подтвердить на физическом устройстве после выпуска; локально проверены условия отправки и обработка входящего события.

## Обслуживание базы: какие скрипты и в каком порядке

Все — с холостым прогоном по умолчанию: без `--apply` печатают план и ничего не меняют.
Порядок важен, скрипты зависят друг от друга.

| команда | что делает | когда гонять |
|---|---|---|
| `npm run db:fix-aliases` | разводит документы с общим alias номерами `-1`, `-2` | до `db:indexes`, иначе уникальный индекс не встанет |
| `npm run db:indexes` | заводит индексы Mongo | после каждого `mongorestore --drop` |
| `npm run db:search-index` | заполняет `searchName`/`searchContent` и текстовый индекс | после массовых импортов текстов **и после любой правки `normalizeChurchSlavonic`** — иначе запрос нормализуется по новым правилам, а сохранённые копии останутся по старым |
| `npm run db:fix-triodion` | перестраивает подготовительный период Триоди | один раз |
| `npm run db:fix-paragraphs` | приводит границы абзацев к `\n\n` | один раз и после импортов |
| `npm run db:anonymize-logs` | заменяет сырые IP хэшем, подрезает `wasAt` | один раз |
| `npm run db:optimize-logs` | схлопывает адреса, сворачивает старое в помесячные итоги | по мере роста журнала |
| `npm run news:import-about` | переносит список версий со страницы «О проекте» в ленту новостей | один раз, после выкладки раздела новостей |
| `npm run release:rules-db` | везёт на сервер корпус песнопений (`data.db` проекта typikon-rules) | после каждой пересборки корпуса |
| `npm run citations:stats` | пересчитывает свод цитируемости (`citation_stats` в Монге, раздел `/otzvuki`) | **сразу после `release:rules-db`** — числа считаются по корпусу и носят его отпечаток; пока не пересчитаны, страница честно говорит, что описывает прежнюю сборку |
| `npm run release:ordo` | везёт службу сборки последования (`src/` и `rules/` проекта typikon-rules) | после правки кода сборки |
| `npm run release:ustav` | правка устава целиком: корпус, потом служба | после правки `rules/**.yaml` — вместо двух команд выше |
| `npm run mentions:find` | ищет кандидатов на упоминания святых | по желанию, дальше ревью в `/admin/mentions` |
| `npm run mentions:backfill` | дописывает к уже проставленным упоминаниям фрагмент текста | после ревью, если связи ставились до 2026-08-27 |
| `npm run db:fix-accents` | чинит съехавшие знаки ударения по словарю корпуса | после крупных импортов; по умолчанию только отчёт |
| `npm run accents:build` | словарь ударений ТОЛЬКО по корпусу, файлом | для замеров самого корпуса |
| `npm run accents:load` | публичный словарь (книги + песнопения + `lexems`) в `typikon-csl.accents` и покрытие в `accentCoverage` | после правок любого из трёх источников; локально с `NODE_ENV=development`, иначе песнопения выпадут; `--dump` заодно пишет файл выгрузки |
| `npm run accents:add` | дописывает пропущенные ударения в размеченных текстах | после импортов; повторять до «дописывать нечего» |
| `npx tsx src/scripts/audit-bible-versification.ts` | сверяет издания Библии, пишет `BIBLE_VERSIFICATION.md` и эталонную таблицу | после добавления издания или правки его стихов |
| `npx tsx src/scripts/recompute-bible-canon.ts` | пересчитывает канонические ссылки стихов по текущим правилам | **после каждой правки `src/lib/bible/mappings.ts`** |
| `npx tsx src/scripts/verify-bible-migration.ts` | проверяет здоровье Библии: целость канона, полнота всех 1067 зачал | после любого из двух выше |

Флаги пробрасываются через `--`: `npm run db:indexes -- --apply`.

### Служба устава: последование собирает Python, а не сайт

Раздел `/ustav` показывает службу, собранную по Типикону: канву, наполненную
песнопениями книг, и рядом — правила, которые её так сложили. Собирает её не
сайт, а отдельный процесс `typikon-ordo` (`src/ordo_service.py` проекта
typikon-rules), поднятый systemd на 127.0.0.1:8767; адрес — в `ORDO_SERVICE_URL`.
Код лежит в `/var/www/typikon.su/typikon-ordo` — рядом с сайтом и корпусом, а
не в домашнем каталоге: служба системная, принадлежать одному человеку ей
незачем. Рядом, а не внутри `typikon-web`: там своё рабочее дерево git.

Почему не переписать сборку сюда. Устав — конструктор, а не выборка: сколько
единиц петь, откуда их брать и что чем подменяется, решают правила, написанные
руками в `rules/typikon`, и разбирают их полторы тысячи строк на Python.
Второй конструктор разошёлся бы с первым на первой же правке правила — а
правила правятся постоянно, устав ещё достраивается.

Наружу служба не смотрит и в nginx не проксируется: она читает файлы правил по
имени из запроса и про ключи доступа ничего не знает. Сайт ходит к ней сам, с
того же хоста, и отдаёт наружу уже разобранное. Текст правила для «лестницы»
проходит через внутреннюю ручку `/api/ordo/rule`, где путь проверяется второй
раз.

Корпус служба берёт тот же, что и сайт (`RULES_DB`), — второй копии файла на
сервере нет.

**Как доносить правку устава.** Правила живут на сервере в двух видах, и это не
дублирование: `build_db.py` разбирает `rules/**.yaml` в таблицы `ordo_steps`,
`typikon_allocation` и прочие — сборка читает их, а не файлы, и едут они внутри
корпуса; сами же файлы нужны «лестнице», которая показывает их текст, и едут со
службой. Выложить одно без другого — значит получить страницу, где показанное
правило не соответствует собранной службе, причём разойдутся они молча.

Поэтому на правку устава есть одна команда:

```
cd ../typikon-rules && python3 src/build_db.py   # правила -> таблицы
cd ../typikon-web   && npm run release:ustav     # корпус, затем служба
```

`release:ustav` сам проверяет, что корпус не старше правил: если `rules/` правили
после пересборки, он откажется — в базе лежал бы прежний устав, а «лестница»
показывала бы новые файлы.

Отдельные `release:rules-db` и `release:ordo` остаются для случаев, когда меняется
что-то одно: разобрана новая книга (корпус без кода) или поправлен код сборки
(служба без 91 МБ корпуса).

### Что нужно на сервере один раз

Выкладка идёт по ssh без терминала, и обычный `sudo` там пароль не спросит —
скажет «a terminal is required» и упадёт. Поэтому скрипты пользуются `sudo -n`:
он либо срабатывает молча, либо сразу отказывает, и тогда скрипт печатает, что
именно доделать руками, и **завершается с ошибкой**. Молча пропустить
привилегированный шаг нельзя: файл доедет, а сайт продолжит читать прежний
корпус по уже открытому дескриптору, и выкладка будет выглядеть удавшейся.

Проверить, есть ли право (на сервере, под admin):

```
sudo -n true && echo "есть" || echo "нет"
```

Если нет — из-под root, одной строкой в `/etc/sudoers.d/typikon`:

```
admin ALL=(root) NOPASSWD: /bin/systemctl restart typikon-web, /bin/systemctl restart typikon-ordo
```

(путь к `systemctl` сверить через `command -v systemctl` — на части систем это
`/usr/bin/systemctl`.)

Каталог под корпус заводить не нужно: он ложится в `/var/www/typikon.su/`,
рядом с каталогом сайта, куда admin и так пишет при каждой выкладке. Если
вдруг окажется, что писать туда нельзя, скрипт скажет об этом и предложит
`chown` или `setfacl` — но обычно этого шага нет.

Юнит `typikon-ordo.service` ставится из-под root — но однажды: меняется он
редко, и `release:ordo` переставляет его сам только тогда, когда право есть.

Замечание про уже существующее: `rebuild-remote.sh` вызывает
`sudo systemctl restart typikon-web.service` тем же способом и **без `set -e`**.
Если права нет, этот вызов всё это время молча не отрабатывал, а выкладка
считалась успешной — стоит проверить тем же `sudo -n true`.

### Второе хранилище: корпус песнопений

Раздел `/chants` и ручка `/api/v2/chants` читают не Mongo, а отдельный файл
SQLite — корпус проекта typikon-rules (`RULES_DB` в окружении). Это песнопения
книг, разобранные по местам службы: 95 тысяч строк Октоиха, Миней, Триодей и
Ирмология с памятями, знаками и гласами.

Лежит он в `/var/www/typikon.su/data.db` — **рядом** с каталогом сайта, а не
внутри него, и разница тут не в аккуратности. У `nobles.db` один читатель —
сайт, и жить внутри его каталога выкладки ему не мешает. У корпуса читателей
два: сайт и служба устава, выкладываемые порознь. А в каталоге сайта идут
`git pull`, `npm i` и сборка, и сделанный там `git clean -fdx` (обычный приём,
когда сборка сломалась) снёс бы 91 МБ корпуса разом у обоих разделов, ничем
себя не объяснив — `-x` удаляет и то, что перечислено в `.gitignore`.

Соседний каталог этого не касается, а главное — принадлежит тому же admin,
который выкладывает: корпус доставляется вообще без root. Пробовали
`/var/lib/typikon` — по уму место верное, но каталог там заводится только
из-под root, и ради одного файла это лишний шаг при каждой новой машине.

Почему файлом, а не в Mongo. Корпус целиком пересобирается из разобранных книг
и правил устава (`python3 src/build_db.py` в typikon-rules), руками в него не
правят, через админку не редактируют. Это артефакт сборки: класть его в Mongo
значило бы денормализовать реляционные связи и переиндексировать 95 тысяч
документов после каждой пересборки.

Поиск по нему держится на FTS5: токенизатор `unicode61 remove_diacritics 2`
снимает ударения при разборе на слова — и в тексте, и в запросе, — поэтому
нормализованные копии полей, какие приходится держать для Mongo
(`searchName`/`searchContent`), здесь не нужны.

Порядок: пересобрать корпус в typikon-rules -> `npm run release:rules-db`.
Скрипт сам проверяет, что индекс на месте, и перезапускает приложение: файл
открывается один раз на процесс, и без перезапуска новый корпус не увидят.

---

Все скрипты, меняющие контент, после записи сбрасывают кэш выборок через
`POST /api/revalidate`. Для этого нужен `REVALIDATE_TOKEN` в окружении — без него
скрипт предупредит, что сайт будет отдавать прежние данные до истечения кэша (час).

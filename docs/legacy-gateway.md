# Старый typikon.su как шлюз до января 2027

DNS старого домена остаётся прежним. На старой машине работают nginx и продление
TLS-сертификата; Next.js, typikon-ordo и задания приложения после перехода не нужны.
Всё обслуживание приложения и данных происходит на новой машине.

**Шлюз установлен и проверен 2026-10-21; старая реализация удалена после проверки backup/restore.**
Пользовательские записи и хэши API-ключей сверены; отсутствующих личных данных
на новой машине нет. Старые сессии по решению владельца сохранены только в
зашифрованном архиве, без восстановления входов. Команды ниже — инструкция
для сопровождения и повторной выкладки. Срок 15 января взят из `src/utils/site.ts`; он не выключает
nginx автоматически. До завершения переезда домен и сертификат должны действовать.

## Файлы и маршруты

| Файл в репозитории | Куда установить |
|---|---|
| `nginx/typikon-legacy.conf` | старая: `/etc/nginx/sites-available/typikon-legacy` |
| `nginx/typikon-legacy-locations.conf` | старая: `/etc/nginx/snippets/typikon-legacy-locations.conf` |
| `nginx/typikon-legacy-proxy.conf` | старая: `/etc/nginx/snippets/typikon-legacy-proxy.conf` |
| `nginx/typikon-legacy-realip.conf.example` | новая: после замены IP — `/etc/nginx/snippets/typikon-legacy-realip.conf` |

Одинаковые правила действуют на `typikon.su` и `www.typikon.su`, HTTP и HTTPS:

| Запрос | Действие |
|---|---|
| Обычная страница, включая `/api` с документацией | `301 https://www.typikon.info$request_uri` |
| `/api/*`, `/embed/*`, `/dump/*` | HTTPS-прокси на новый nginx |
| Любой путь, оканчивающийся на `.ics` | прокси, включая приходские и личные ленты |
| `/.well-known/assetlinks.json` | прямой проксируемый ответ без смены хоста |
| `/app/*`, `/rss.xml` | прокси для обновлений приложения и подписчиков RSS |
| `/.well-known/acme-challenge/*` | локальный webroot для продления сертификата |

`proxy_pass` без URI сохраняет исходные путь и query. Метод, тело, Authorization,
Cookie, Origin, Range и условные запросы проходят к upstream; повторов запросов
и собственного proxy-cache нет. HTTP-исключения сразу проксируются по HTTPS к
новому серверу, чтобы не терять POST при редиректе старого клиента. Обычные страницы
перенаправляются и для POST: формы и личный веб-интерфейс следует открывать на `.info`.

Upstream — `https://www.typikon.info`, с каноническими Host/SNI и проверкой CA.
Публичный DNS `.info` должен вести на новую машину, а не обратно на старую.
Из-за канонического Host приложение не распознаёт `.su` само: Sunset/Link и
X-Typikon-Notice добавляет шлюз. Существующая визуальная полоса переезда внутри
виджета, зависящая от Host, в этой схеме не появится; ссылки виджета ведут на `.info`.
nginx разрешает это имя при загрузке конфигурации; после изменения IP `.info`
перезагрузи конфигурацию шлюза. Если требуется закреплённый IP, замени только
`proxy_pass` на `https://НОВЫЙ_IP` (IPv6 в квадратных скобках), сохрани Host и
`proxy_ssl_name www.typikon.info`. Не подключай старый Node как fallback.

## 1. Инвентаризация и сохранение данных

На **старой машине**, до изменения nginx:

```bash
sudo nginx -T
sudo ss -ltnp
sudo systemctl status typikon-web.service typikon-ordo.service --no-pager
sudo systemctl list-timers --all
crontab -l
sudo crontab -u admin -l
```

Не публикуй полный `nginx -T` и вывод кронов: там могут быть внутренние адреса
и секреты. Найди все vhost с `server_name typikon.su www.typikon.su`, существующие
пути сертификата, механизм renewal и фактические имена служб/пользователей.
**В репозитории старый `typikon-web.service` содержит `-p 80`: проверь владельца
порта.** Если порт 80 держит Node, nginx не сможет занять его до остановки Node
(см. отдельную ветку переключения ниже). Проверь также 443 и IPv6.

Сохрани в закрытом каталоге вне checkout:

```bash
sudo install -d -m 700 /root/typikon-retirement
sudo sh -c 'umask 077; nginx -T > /root/typikon-retirement/nginx.before.txt 2>&1'
sudo tar -czf /root/typikon-retirement/nginx.before.tar.gz /etc/nginx
sudo sh -c 'umask 077; crontab -u admin -l > /root/typikon-retirement/admin.cron.before'
sudo sh -c 'umask 077; systemctl cat typikon-web.service > /root/typikon-retirement/web-unit.before.txt'
```

Если crontab пользователя отсутствует, сохрани этот факт и продолжай; не заменяй
его пустым файлом. Сохрани отдельно `.env*`, systemd drop-in, SQLite и актуальные
дампы Mongo (с правильными URI/правами конкретной машины). `typikon-users`
проверяй отдельно: пользователи, ключи API, сессии, приходы, заметки, помянники и
токены личных календарей могут отличаться между машинами. Нужные записи сначала
согласованно перенеси/сверь на новой машине, **не накатывай старый users-дамп с
`--drop` поверх действующего нового**. Сохрани копию вне выводимой из эксплуатации
машины и проверь восстановление в отдельную тестовую базу.

Сопоставь старые `/dump/<версия>/…` и APK с новой машиной: ссылки старых публикаций
и DOI должны находить те же файлы, с теми же контрольными суммами. Недостающие
версии скопируй в статические каталоги новой машины до отключения старых.
Старые сессии могут получить 401: прокси не делает подписи и записи разных баз
совместимыми. Пользователям потребуется вход на `.info`; нужные ключи и токены
подписок должны существовать на новой машине до переключения.

## 2. Новый nginx: доверие только старому шлюзу

На **старой машине** проверь доступность нового сервера и сертификата:

```bash
getent ahosts www.typikon.info
curl --noproxy '*' --fail --show-error https://www.typikon.info/api/health
curl --noproxy '*' --fail --show-error https://www.typikon.info/.well-known/assetlinks.json
```

`/api/health` должен вернуть `status: ready` и BUILD_ID текущего релиза.
Если этой ручки ещё нет, сначала выложи подготовленную новую версию сайта.
Установи фактический исходящий IPv4/IPv6 старой машины по сетевым настройкам и
журналу нового nginx: это адрес TCP-соединения от шлюза, а не адрес посетителя.

На **новой машине** скопируй `typikon-legacy-realip.conf.example`, замени
`OLD_GATEWAY_IPV4` реальным IPv4 старой машины. Если соединение идёт по IPv6,
добавь его точный `/128`. Включи файл в **существующий** `server{}` для
`www.typikon.info` (и в соответствующий HTTPS-vhost, если он выделен):

```nginx
include /etc/nginx/snippets/typikon-legacy-realip.conf;
```

Нужен модуль `http_realip` (`nginx -V`). Не используй `0.0.0.0/0`, `::/0`, всю
подсеть хостера или доверие любому X-Forwarded-For. На старой машине заголовки
X-Real-IP/X-Forwarded-For **перезаписываются** фактическим адресом посетителя;
новая доверяет X-Real-IP только от указанного peer. В существующем proxy location
новой машины должны использоваться:

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

Тогда лимиты nginx и приложения считают посетителя, а не общий адрес шлюза.
Если между машинами есть CDN/другой прокси, эту цепочку нужно настроить отдельно:
готовый snippet рассчитан на прямое соединение старого nginx с новым.

```bash
sudo nginx -t && sudo systemctl reload nginx
```

На новой машине не добавляй другой `location /` и не меняй обработку `/dump/`
и `/app/`: их должен продолжать раздавать существующий nginx.

## 3. Автоматическая выкладка без остановки приложения

Подготовь отдельную цель `.env.release.legacy` с доступами **старой** машины
по `.env.release.example`. В ней обязательны:

```dotenv
USERNAME=admin
HOST=АДРЕС_СТАРОЙ_МАШИНЫ
PASSWORD=ПАРОЛЬ_SSH
GATEWAY_SITE_FILE=/etc/nginx/sites-available/typikon
GATEWAY_ACME_ROOT=/var/www/letsencrypt
```

Секреты остаются в локальном файле цели; если sudo-пароль другой, задай
`SUDO_PASSWORD` по общим правилам выкладки. `ENV_FILE` для этой команды не нужен
и не отправляется. Не используй имя `legacy`, пока оно не заведено именно для
старой машины. У команды нет неявной цели prod:

```bash
npm run release:gateway -- --target legacy
```

На старой машине нужны работающий nginx под systemd, Python 3.8+, curl, ss,
доступ к `.info` по HTTPS и административные права sudo на запуск worker Python.
Пароль передаётся через stdin SSH/sudo, без записи в аргументы или файлы.
Новая машина должна быть готова, а доверие IP шлюза из шага 2 — настроено заранее:
эта команда новую машину не меняет и не может проверить её IP-журнал.

`GATEWAY_SITE_FILE` — уже активный файл nginx для **только** `typikon.su` и
`www.typikon.su`; можно указать enabled-ссылку, она сохранится. Файл должен быть
внутри `GATEWAY_NGINX_DIR` (по умолчанию `/etc/nginx`) и присутствовать в `nginx -T`.
Если старые домены разнесены по нескольким файлам или смешаны с другими сайтами,
команда откажет, а не станет удалять неизвестные vhost. Сначала отдельно приведи
этот участок конфигурации к одному файлу. Сертификат/ключ берутся из него;
при нескольких парах задай `GATEWAY_CERTIFICATE` и `GATEWAY_CERTIFICATE_KEY` явно.
Проверь действующий ACME webroot, указанный в `GATEWAY_ACME_ROOT`.

Команда выполняет на старой машине под общей блокировкой:

1. Проверяет, что nginx работает, а порты 80/443 не заняты Node/другим процессом.
   При конфликте **отказывает до записи**: остановка приложения запрещена этой командой.
2. Проверяет исходный nginx, активный vhost и отсутствие других vhost `.su`.
   Проверяет готовность `.info` и сохраняет статусы/Location/маркер старых маршрутов
   обоих имён по HTTP/HTTPS, без приватных URL и ключей.
3. Создаёт закрытый backup в `/var/backups/typikon-legacy-gateway/<UTC-время>-<id>`:
   tar всего дерева nginx, полный `nginx -T`, оригиналы затрагиваемых файлов,
   снимок маршрутов и журналы. Backup остаётся на сервере при успехе и ошибке.
4. Заменяет только указанный vhost и два `typikon-legacy-*.conf` snippet через
   атомарную замену каждого файла, подставляет действующие сертификаты/webroot/CA.
   Другие сайты, enabled-ссылки, сертификаты, env и базы не меняет.
5. Выполняет `nginx -t`, затем **reload nginx**. Проверяет маршруты через loopback
   с Host/SNI `.su`, настоящей TLS-проверкой, BUILD_ID, API, POST/OPTIONS, календарями,
   виджетом/CSP, RSS и манифестом выгрузки. APK и реальные подписки проверяются
   отдельно по шагу 4.
6. При ошибке возвращает прежние три файла, их режимы/владельцев и symlink, повторяет
   `nginx -t`. Если reload уже пытались делать — перезагружает прежний nginx и
   сверяет ответы с сохранёнными маршрутами. При неудаче возврата сообщает
   `ОТКАТ НЕ ЗАВЕРШЁН` и путь backup, завершает работу с ненулевым кодом.

`state.json` в backup содержит итог `active`, `rolled-back` или `rollback-failed`;
`preflight` означает, что подготовка не завершилась и замена ещё не начиналась.
Полные ошибки смотри через sudo в `commands.log`, `nginx.*.txt` и `routes.log`:
`nginx -T` может содержать секреты. Не удаляй backup до окончания контрольного периода.
Во время операции не выполняй другие ручные изменения/reload nginx; общий lock
защищает только параллельные запуски этой команды. SIGKILL/падение машины не дают
гарантии автоматического возврата — для этого остаётся backup и журнал состояния.

**Команда не останавливает, не перезапускает и не выключает старые web/ordo,
MongoDB и кроны.** Она также не переносит пользовательские данные. После успеха
повтори внешнюю проверку с рабочей машины, включая IPv6/реальные подписки/API-ключи
и IP клиента из шага 4. Серверная проверка через loopback не проверяет firewall
и внешний доступ. Отключение приложения из шага 5 пока выполняется только отдельно.

Если автоматический режим отказал из-за раскладки конфигов/портов, ручная ветка
ниже описана для отдельного согласованного переключения; команда её не выполняет.

## 3а. Старый nginx: ручная установка и переключение

Из полученной на старую машину копии репозитория:

```bash
sudo install -d -m 755 /etc/nginx/snippets
sudo install -m 644 nginx/typikon-legacy-proxy.conf /etc/nginx/snippets/
sudo install -m 644 nginx/typikon-legacy-locations.conf /etc/nginx/snippets/
sudo install -m 644 nginx/typikon-legacy.conf /etc/nginx/sites-available/typikon-legacy
```

До включения поправь в файлах:

- Пути сертификата и ключа — **из действующего конфига**, сертификат должен
  покрывать оба имени `.su`. Ключи и renewal не должны зависеть от удаляемого checkout.
- ACME webroot — из действующей конфигурации certbot/другого клиента. В примере
  `/var/www/letsencrypt`; менять renewal без согласования этого пути нельзя.
- Путь CA (`/etc/ssl/certs/ca-certificates.crt` для Debian/Ubuntu) и допустимые
  TLS-протоколы своей версии nginx/OpenSSL. Не выключай `proxy_ssl_verify`.
- Лимит тела `client_max_body_size 20m` согласуй с прежним и новым сервером.
- Если IPv6 не используется/не поддерживается, убери только соответствующие
  `listen [::]`. При существующей AAAA-записи IPv6 должен продолжать работать.

Замени старые vhost `.su` новым. Не оставляй дубликаты `server_name`, server-level
`return`, `try_files`, прокси на `127.0.0.1:3000/80` и include старых bot-фильтров
в этом vhost: они могут перехватить исключения. Другие сайты этой машины не трогай.
Сохрани прежние файлы и список enabled-ссылок для возврата. Включение нового файла:

```bash
sudo ln -s /etc/nginx/sites-available/typikon-legacy /etc/nginx/sites-enabled/typikon-legacy
sudo nginx -t
```

Если nginx уже слушает нужные порты, примени `sudo systemctl reload nginx`.
Работающее приложение пока оставь запущенным для быстрого возврата.
Если **Node держит порт 80**, заранее подготовь и проверь конфигурацию, затем
в коротком окне останови только старый web-unit и примени nginx:

```bash
sudo systemctl stop typikon-web.service
sudo systemctl reload nginx  # или start nginx, если служба ещё не работала
```

При ошибке сразу верни прежние vhost, освободи порт 80 от добавленного listener
nginx (не останавливай nginx целиком, если он обслуживает другие сайты), затем
запусти старый web-unit. На этой ветке проверка работающего шлюза до остановки
старого Node невозможна: оба претендуют на один порт.

Не считай один код возврата reload доказательством успеха: проверь
`systemctl status nginx`, журнал nginx и ответы ниже.

## 4. Проверки без изменения DNS

С машины с Python 3 и curl, где лежит подготовленный скрипт:

```bash
python3 scripts/check-legacy-gateway.py --old-ip АДРЕС_СТАРОЙ_МАШИНЫ
```

При обычном запуске без `--old-ip` используются действующие DNS `.su`.
Проверяются оба имени, HTTP/HTTPS, 301 с query, v1/v2 JSON, POST→405 и OPTIONS→204
на GET-only API, 401 личного API без cookie, assetlinks без редиректа, виджет,
общий календарь, RSS, манифест выгрузки и BUILD_ID нового сервера. Скрипт не
использует `-L` или `-k`, отключает пользовательский curlrc и не посылает ключи и не изменяет данные. Ошибка любого
ожидаемого ответа завершает проверку с кодом 1. Если выгрузка лежит иначе, сначала
уточни доступный путь манифеста, а не принимай 404 за успешный перенос.

Дополнительно вручную:

1. Открой реально встроенную рамку на чужом сайте и её ссылки. CSP должна
   разрешать внешнее встраивание; не добавляй общие X-Frame-Options на шлюзе.
2. Проверь настоящие `/parish/<slug>/schedule.ics` и личную ленту помянника с её
   существующим токеном. Сравни UID и события с прямым ответом нового сервера.
   Не вставляй личный URL в общие журналы/переписку.
3. Проверь настоящий API-ключ старого клиента и личную сессию: достаточны ли
   права и действительно ли данные берутся из нужного пользователя новой базы.
   Не кэшируй/не переписывай 401, 403, 429 и Set-Cookie на шлюзе.
4. Скачай байтовый диапазон APK и одного файла выгрузки (через `.su`, без `-L`):
   `curl --range 0-0 -D - -o /dev/null https://www.typikon.su/app/app.apk`.
   Для существующего файла ожидается 206 и Content-Range, без Location. Сравни
   небольшие реальные файлы и их SHA-256 с `.info`, включая старые версии выгрузки.
5. Проверь IP: запрос с внешней тестовой машины к старому API с поддельными
   `X-Real-IP: 198.51.100.77` и `X-Forwarded-For: 198.51.100.88` должен прийти
   на новый nginx с **настоящим IP тестовой машины**. В access log нового nginx
   проверь `$remote_addr`; при необходимости временно логируй также
   `$realip_remote_addr` как TCP-peer. Прямой запрос к `.info` с такими же
   заголовками также не должен менять настоящий IP. Не включай доверие шлюзу
   по клиентскому Host или произвольному заголовку.
6. Проверь ACME с временным непредсказуемым файлом в действующем webroot через
   HTTP обоих имён. Удали пробный файл; `certbot renew --dry-run` выполняй после
   проверки текущего renewal-метода, не меняя настройки других доменов.
7. Проверь получение полного последования с нового движка, чтобы обнаружить
   внутренние обращения к старым API. В браузере открой старую ссылку, затем
   проверь вход, чтение и профиль на `.info`. Старый offline-кэш установленной
   PWA редиректом не удаляется: ей нужен переход/установка нового адреса.

Gateway access log хранит категории маршрутов, статусы и IP без query и токенов
личных лент. Error log nginx может содержать полный URI при ошибке; доступ к нему
и копиям должен быть ограничен. Следи за 5xx/499/429 и нагрузкой новой машины.

## 5. Отключение приложения и сохранение возможности возврата

После успешного переключения шлюз уже не обращается к старому Node. На старой
машине останови **только подтверждённые службы этого проекта**:

```bash
sudo systemctl stop typikon-web.service typikon-ordo.service
sudo systemctl disable typikon-web.service typikon-ordo.service
```

Имена замени фактическими; отсутствие одного unit не повод отключать чужую службу.
Через `crontab -u admin -e` и соответствующие project timer-unit отключи только
публикацию канала, push, sweep, snapshots и прочие задания старого проекта.
Не выполняй `crontab -r`: на машине могут быть другие задачи. Оставь задания
продления сертификата, logrotate и резервные копии до окончательной сверки.
Убедись, что публикации/рассылки продолжаются только на новой машине.

Повтори smoke-скрипт **при остановленных старых службах** и отдельные проверки
личных/приходских подписок. Это проверяет, что скрытой зависимости от старой
реализации не осталось. Проверь также после плановой перезагрузки, что nginx
поднимается, а старые web/ordo не запускаются.

Пока оставь checkout, старые сборки, базы, env и unit-файлы на месте с закрытым
доступом — для короткого контрольного периода и возврата. В случае ошибки:
сначала верни сохранённую конфигурацию nginx и enabled-ссылки, проверь `nginx -t`,
примени её и запусти старые службы (для Node на 80 сначала освободи его listener).
DNS менять не нужно. Уже закэшированные браузером/поисковиком 301 при возврате
конфига не отменяются; проверяй сетевое поведение curl без следования редиректам.
Не включай старые задания публикации/рассылок одновременно
с новыми. Откат шлюза не синхронизирует новые пользовательские записи обратно
в старую базу; до открытия старого приложения для записи согласуй источник данных.

## 6. Удаление старой реализации

После контрольного периода, проверенного backup/restore и подтверждения, что
новая машина содержит нужные данные и статические версии:

- Выведи из эксплуатации старые project unit/drop-in, сохранив их копии. Сделай
  `systemctl daemon-reload`; не удаляй nginx-unit и настройки renewal.
- Перенеси старый checkout и каталоги сборок в закрытый архив/карантин вне
  webroot. Фактические пути возьми из unit и старой конфигурации; nginx, certbot
  и другие проекты не должны ссылаться на них. Затем их можно удалить по
  утверждённому списку путей. Команд с `rm -rf` по угаданным путям здесь нет.
- MongoDB и общие SQLite удаляй/останавливай только после инвентаризации всех
  потребителей: Mongo на старой машине может обслуживать другие проекты.
- Сохрани gateway-vhost, snippets, CA, сертификат `.su`, renewal, журналы и
  мониторинг до отключения домена. В январе это отдельный завершающий шаг.

Не удаляй сертификат или старые файлы на основании одного успешного `curl`.
Доказательство готовности к удалению — повторные проверки шлюза без старых
процессов, сверенные данные/подписки и пригодная копия вне этой машины.

## Основания и границы проверки

Поведение директив сверено с документацией nginx:
[proxy_pass и заголовки/TLS](https://nginx.org/en/docs/http/ngx_http_proxy_module.html),
[realip и доверенные адреса](https://nginx.org/en/docs/http/ngx_http_realip_module.html),
[return](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html).
Локальные тесты проверяют выбор маршрутов и необходимые свойства proxy-конфига;
они не заменяют парсер nginx. В локальной среде nginx не установлен;
настоящие `nginx -t` и live smoke выполнены на машинах 2026-10-21.

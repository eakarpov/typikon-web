# Скрипты выкладки

Два семейства, и различать их важно:

- **`release-*.sh`, `*-release.sh`, `download-db.sh`** — запускаются на РАБОЧЕЙ
  машине. Они собирают то, что едет, кладут его на сервер и запускают там вторую
  половину.
- **`*-remote.sh`** — исполняются НА СЕРВЕРЕ: скармливаются ему через
  `ssh … bash -s` и руками не нужны. Всё, что им требуется знать, приходит
  переменными в той же строке (`REMOTE_ROOT`, `PART`, `RULES_DB_REMOTE`).

Особняком — `mongod_dump.sh` (снятие резервной копии, живёт на сервере в кроне) и
`check-tts-endpoints.sh` (разовая проверка доступности чужих служб).

## Цель выкладки

[release-target.sh](release-target.sh) подключается первой строкой каждого
скрипта первого семейства. Он выбирает цель и настраивает под неё пути.

Доступы лежат по файлу на цель, в корне проекта: `.env.release.prod`,
`.env.release.test` и сколько заведут ещё. Образец со всеми возможными полями —
[.env.release.example](../.env.release.example).

```
npm run release                              # prod (умолчание)
npm run release -- --target test
TARGET=test npm run release:db               # то же переменной окружения
TARGET=test npm run release:db -- bible_verses
bash scripts/release-app.sh --target test 1.6.0 ~/Downloads/app-release.apk
```

Ключ — любое слово, под которое заведён файл: `prod` и `test` нигде не
перечислены. Проверяется наличие файла, а не имя, поэтому опечатка (`--target
tset`) останавливает выкладку, а не уводит её на прод по умолчанию.

Умолчание — `prod`, чтобы не ломать привычные команды. Защитой служит не оно, а
строка, которую каждый скрипт печатает до первого действия:

```
── выкладка: test (admin@10.0.0.5:/srv/typikon), окружение .env.production.test
```

## Откуда они работают

Лежат скрипты здесь, а работают из КОРНЯ ПРОЕКТА: там `.env.production`,
`nobles.db`, выгрузка корпуса и файлы доступов. Переход в корень делает
`release-target.sh`, он же оставляет путь к самим скриптам в `RELEASE_DIR` — для
тех мест, где один скрипт зовёт другого или отправляет его на сервер.

Поэтому запускать их можно откуда угодно: `npm run release`, `bash
scripts/release.sh`, `cd scripts && bash release.sh` — все три равнозначны.

## Что можно задать в файле цели

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `USERNAME`, `PASSWORD`, `HOST` | — | обязательные доступы |
| `REMOTE_ROOT` | `/var/www/typikon.su/typikon-web` | каталог сайта; из него выводятся остальные |
| `ORDO_REMOTE` | рядом с каталогом сайта | служба сборки последования |
| `DUMP_REMOTE` | `/var/www/typikon-data` | выгрузка корпуса |
| `APP_REMOTE` | `/var/www/typikon-app-releases` | сборки приложения |
| `ENV_FILE` | `.env.production` | какой местный файл уезжает файлом `.env.production` |
| `SITE_URL` | `https://www.typikon.info` | адрес цели снаружи: сброс кэша устава |
| `DEPLOY_ROOT` | `${REMOTE_ROOT}-releases` | версии сайта, `current`, `previous`, блокировка |
| `WEB_SERVICE` | `typikon-web.service` | существующая systemd-служба сайта |
| `APP_PORT`, `PROBE_PORT` | `3000`, `3001` | основной и проверочный порты на `127.0.0.1` |
| `RELEASE_REF` | `master` | ветка/тег/commit из `origin`, которую собирать |

`ENV_FILE` — главное, что стоит задать испытательной машине: свой бот, своё
приложение VK, свой ключ рассылки. Иначе проверка на ней пойдёт от имени
настоящего сайта — посты уйдут в настоящий канал, толчки на настоящие устройства.

## Порядок выкладки

Полное развёртывание с нуля описано в [DEPLOY.md](../DEPLOY.md). Обычная правка:

| Что изменилось | Команда |
|---|---|
| первичный переход службы на релизы | `npm run release:setup` |
| код сайта | `npm run release` |
| возврат предыдущего релиза | `npm run release:rollback` |
| код и база | `npm run release:common` |
| база по частям | `npm run release:db -- texts rest` |
| словарь | `npm run release-csl` |
| новости | `bash scripts/news-db-release.sh` |
| правила устава | `npm run release:ustav` |
| только корпус песнопений | `npm run release:rules-db` |
| только код службы устава | `npm run release:ordo` |
| выгрузка корпуса | `npm run release:data` |
| сборка приложения | `bash scripts/release-app.sh X.Y.Z путь.apk` |

## База: снятие и выкладка по частям

- Резервная копия на сервере снимается раз в сутки (`mongod_dump.sh` в кроне) и хранится семь
  дней.
- Локальная копия прода — `npm run sync:db`; выкладка локальной базы — `npm run release:db`.
- Выкладка идёт по частям, по одному ssh-сеансу на тяжёлую коллекцию: одним сеансом
  `mongorestore` не доживал до конца. Части: `dneslov_names`, `bible_verses`, `texts`,
  `temples`, `rest`. Оборвалась одна — повторяется она одна: `npm run release:db -- bible_verses`.
- Словарь (`typikon-csl`) выкладывается отдельно: `npm run release-csl` дампит базу целиком
  (около 88 МБ). Указатель написаний (`spellings`) производный и пересобирается командой
  `npm run cslav:build -- --apply` на рабочей машине; на сервер он приезжает дампом. После
  правки свёртки написаний на сервере нужен `npm run db:search-index`.
- Приходские и пользовательские данные лежат в `typikon-users` и пишутся только на проде:
  `mongorestore --drop` контентной базы их бы стёр. Перенос с прежнего места — `npm run
  parish:move` (на сервере, однократно).

## Безопасная выкладка сайта

На сервере нужны Node 22, npm, git, tar, curl, flock (util-linux), systemd и
место для нескольких полных сборок с node_modules. `REMOTE_ROOT` остаётся
исходным checkout для кронов и скриптов обслуживания. Сборки лежат рядом:

```
typikon-web/                         # прежний checkout, без git pull при релизе
typikon-web-releases/
   releases/<UTC-время>-<commit>-<pid>/
   current -> releases/новая-версия
   previous -> releases/прежняя-версия
```

Перед первым релизом проверь в файле цели имя действующей службы и порт nginx,
выбери свободный `PROBE_PORT`. Пути должны быть абсолютными, без пробелов и
спецсимволов. У пользователя должны быть права создать `DEPLOY_ROOT`.
Настройка выполняется один раз на каждую цель:

```bash
npm run release:setup -- --target test
```

Команда создаёт `current` на прежний checkout, проверяет, что существующий сайт
отвечает на `APP_PORT`, генерирует
`DEPLOY_ROOT/release.conf`, устанавливает его как
`/etc/systemd/system/<WEB_SERVICE>.d/release.conf` и делает `daemon-reload`.
Работающий процесс при этом не перезапускается. Для этого нужны права `sudo -n`
на `install -d`, `install` и `systemctl daemon-reload`; если их нет, администратор
может установить уже сгенерированный `release.conf` вручную. Файл переопределяет
`WorkingDirectory` и `ExecStart`, сохраняя прочие параметры службы. В команду
запуска записывается абсолютный путь текущего `node`, адрес `127.0.0.1` и
`APP_PORT`. При смене Node настройку следует повторить; изменение порта требует согласовать
службу и nginx отдельно — setup откажет, если на выбранном порту сайта ещё нет. Для обычных
релизов достаточно существующего права `sudo -n systemctl restart <WEB_SERVICE>`.

Изменения сайта сначала должны попасть в выбранную ветку `origin`: релиз
использует `git fetch` и `git archive` конкретного commit, а локальные незакоммиченные
изменения не отправляет. Первый новый commit должен содержать `/api/health`.

```bash
npm run release -- --target test
npm run release:rollback -- --target test
```

Порядок обычной выкладки:

1. Файл окружения цели и `nobles.db` загружаются в отдельный временный каталог.
2. Под общей блокировкой создаётся новый каталог версии; `npm ci` и `next build`
   работают только в нём. Окружение и родословная копируются в релиз; `SQLITE_DB`
   указывает на его собственный снимок `nobles.db`.
3. Next запускается на проверочном порту. `/api/health` должен вернуть HTTP 200,
   `status: ready` и BUILD_ID именно этой сборки. Ручка проверяет MongoDB с
   ограниченным ожиданием и не кэшируется. Она не проверяет все разделы и движок устава.
4. Проверочный процесс останавливается, `current` заменяется атомарно, служба
   перезапускается. Основной порт должен подтвердить тот же BUILD_ID.
5. Только после успеха прежняя версия становится `previous`. При сбое после
   переключения возвращаются старая ссылка и процесс, затем повторяется проверка.

Откат использует уже собранный `previous`, включая его окружение и родословную:
повторно скачивать Git, устанавливать пакеты или иметь локальный `ENV_FILE` не
нужно. Перед переключением эта версия тоже проверяется на отдельном порту.
Неудачный откат возвращает работавшую версию; успешный меняет версии местами.
Первый откат на старый checkout проверяет `/`, поскольку `/api/health` там ещё
нет. Этот checkout нужно сохранить до отказа от такого отката.

Блокировка действует на выкладку сайта, настройку и откат. Текущий процесс не
затрагивается до готовности кандидата, но при переключении есть короткий перерыв
на перезапуск systemd. При обрыве соединения скрипт пытается восстановить прежний
релиз; аварийное завершение машины или `SIGKILL` требует проверки `current` и службы.
Релизы не удаляются автоматически. После ошибки смотри `probe.log` в каталоге
кандидата и журнал службы; не удаляй каталоги, на которые указывают ссылки.

MongoDB, внешний `RULES_DB`, движок устава, выгрузки и другие общие данные этим
откатом не восстанавливаются. Изменения схем должны оставаться совместимыми с
предыдущим релизом. `release:common` по-прежнему отдельно выкладывает контентную
базу; её обновление не входит в атомарное переключение кода. Окружение сайта
обновляется через `release`; другие скрипты продолжают класть свой ENV_FILE в
исходный checkout для служебных задач. Настроенные RULES_DB, DUMP_DIR и
GOOGLE_APPLICATION_CREDENTIALS проверяются
на доступность; относительные пути превращаются в абсолютные относительно
прежнего checkout. Для новых настроек предпочитай абсолютные пути вне релизов.

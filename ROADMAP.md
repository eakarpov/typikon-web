  просто получается крупнее, чем нужно. Чинить не сейчас; если возьмёмся — скорее всего проще
  нормализовать сам `content` в БД (заменить `"\n \n"` → `"\n\n"` при импорте/миграцией), чем менять
  паттерн split на regex сразу в двух местах на разных платформах.

### Блок 1. Дешёвые победы

- **`<html lang="en">`** в [src/app/layout.tsx](src/app/layout.tsx) на русско-церковнославянском

  не попадают вообще. Для контентного сайта на ~3200 страниц это самая дешёвая органика,
  которую мы не берём. Заменить на `src/app/sitemap.ts`, строящий карту из Mongo по реальным

- **Поиск отдаёт всё и без ограничений** — [src/app/search/api.ts](src/app/search/api.ts)

  возвращает все совпавшие тексты целиком, вместе с полем `content` (тысячи символов на
  документ). UI при этом использует только `id` и `name`. Плюс rate limiting отсутствует —
  вместе это простой способ положить сервер.
- **Утечка sqlite-хендлов** — `init()` из [src/lib/sqlite.ts](src/lib/sqlite.ts) создаёт новый
  `Database` при каждом вызове (58 вызовов по коду), `db.close()` встречается один раз. В
  long-running процессе файловые дескрипторы копятся. Нужен синглтон на процесс.
- **`ignoreBuildErrors: true`** в [next.config.js](next.config.js) — типы в проде не проверяются
  вообще, при 247 `: any` по коду. Замер на 2026-08-24: `npx tsc --noEmit` даёт **171 ошибку**,
  большая часть — `unknown` из `better-sqlite3.all()` в модуле `nobles`. Снимать флаг можно только
  после разбора этой кучи, но знать её размер полезно уже сейчас.

### Блок 2. Архитектурный рычаг: сайт целиком динамический

Корневой [layout.tsx](src/app/layout.tsx) вызывает `verifySession()` и `getItem()` — это
заставляет Next рендерить **каждую** страницу динамически. Ни одной `revalidate` или
`generateStaticParams` в проекте нет (проверено, ноль вхождений): страница жития XII века ходит
в Mongo при каждом заходе анонима.

Что делать: вынести сессию из корневого layout (клиентский компонент или отдельный сегмент),
контентные маршруты — `/reading/[id]`, `/saints/[id]`, `/months/[id]`, `/library/[id]` — перевести
на ISR, инвалидация по хуку из админки при сохранении текста. Это самая крупная разовая выгода по
скорости и нагрузке, и она же делает осмысленным офлайн-кэш в PWA.

Рядом: **шрифты**. `public/fonts` — 1.2 МБ OTF, из них `myFont` тянет ~450 КБ (Regular + Bold)
до первой отрисовки текста на каждой странице чтения. Конвертация в woff2 даёт примерно двукратное
сокращение без потерь; сабсеттинг — больше, но аккуратно, чтобы не потерять церковнославянские
надстрочные знаки.

### Статус блока 2 — сделано 2026-08-24 (шрифты не трогали)

**Сессия убрана из рендера.** Корневой [layout.tsx](src/app/layout.tsx) больше не вызывает
`verifySession()`/`getItem()`; сессию забирает [SessionLoader](src/app/SessionLoader.tsx) с клиента
через новый `GET /api/session` и кладёт в тот же redux-стор, из которого меню читало её и раньше.
В `auth`-слайс добавлен флаг `isResolved` — без него у залогиненных на мгновение мигала кнопка
«Войти». `SessionChecker`/`SessionDispatcher` удалены как дублирующие. Важно: `SessionLoader` должен
лежать **внутри** `StoreProvider` — иначе react-redux падает уже на этапе пререндера.

**Что теперь кэшируется.** Пререндеренных маршрутов стало 19 против 2 (`/`, `/library`, `/calendar`,
`/triodion`, `/penticostarion`, `/rest-readings`, `/commons`, статические разделы). `/months/[id]` и
`/library/[id]` — ISR по первому запросу (`MISS` → `HIT`, проверено заголовком `x-nextjs-cache`).

Отдельная находка: **`export const revalidate` для динамического сегмента не работает без
`generateStaticParams`** — Next считает такой сегмент полностью динамическим и результат не кэширует
вовсе. Пустой массив (`generateStaticParams = async () => []`) включает генерацию по первому запросу
с последующим кэшированием, при этом сборка не тратит время на 2500 страниц.

**Выборки из базы кэшируются отдельно** ([src/lib/cache.ts](src/lib/cache.ts), `unstable_cache` с
тегами). Это то, что спасает страницы, которые остаются динамическими: `/reading/[id]` из-за
`?range`, а `/calendar/[id]`, `/weeks/[id]`, `/triodion/[id]`, `/calculator/[date]` — из-за cookie
языка Библии. Замеры на продовой сборке, первый запрос → последующие:

| маршрут | было | стало |
|---|---|---|
| `/calendar/march-30` | 271 мс | 23 мс |
| `/triodion/post-5-vt` | 435 мс | 33 мс |
| `/reading/dobrotolubie-30` | 78 мс | 18 мс |

Ошибки в кэш не попадают: `cachedTuple` пробрасывает их наружу, иначе сбой базы залипал бы на час.

**Инвалидация.** `POST /api/revalidate` (только админ, в проде без прав — 404) сбрасывает теги;
редакторы текстов и дней в админке дёргают его после сохранения
([src/lib/admin/revalidate.ts](src/lib/admin/revalidate.ts)). Отдельная ручка нужна потому, что API
админки живёт в pages-роутере, а `revalidateTag` работает только в app-роутере. Страховка по времени —
час для контента, 5 минут для главной (на ней церковная дата и список последних правок).

**Проверено:** тексты страниц продовой сборки сравнены с версией до изменений — на 14 маршрутах всех
типов единственное расхождение в том, что раньше в HTML попадал `Loading...` из Suspense, а теперь
контент отрендерен сразу. 32 адреса из карты сайта отдают 200. `tsc --noEmit` — 170 ошибок против
171 до начала работы, новых нет.

Что осталось за рамками:
- `/saints/[id]` не трогал — в файлах этого раздела лежит незакоммиченная работа по `nobles`.
- Инвалидация подвешена только на редакторы текстов и дней; книги, месяцы и недели правятся реже —
  их подхватит часовой таймаут.
- `CountMeta` на каждый просмотр страницы пишет в Mongo IP, URL и растущий массив `wasAt`
  ([src/app/api.ts](src/app/api.ts), `writeMetaData`). Рендер это не блокирует (запрос уходит с клиента
  после отрисовки), но документ на популярный URL растёт без ограничений, а собирать IP-адреса — это
  ещё и персональные данные. Стоит решить отдельно: ограничить массив или считать агрегатом.

### Блок 4. Что нужно решить, а не откладывать: `nobles` — РЕШЕНО 2026-08-24

129 файлов из ~494 в `src` относятся к родословной. При этом модуль был объявлен экспериментальным
и «не развиваем» — а последний коммит, незакоммиченные изменения в рабочем дереве и четыре новых

развития. Расхождение снято в сторону признания второго направления. Вопрос отдельного
репозитория/поддомена остаётся открытым — см. раздел «Родословная (`nobles`)» ниже.

### Markdown на странице чтения (флаг `newUi`) — сделано 2026-08-27

Флаг `newUi` («Новый UI (Markdown)») был заведён давно, но жил только в админском
редакторе: страница чтения о нём не знала, и стоял он у 1 текста из 3327. Теперь
[ReadingContent](src/app/reading/[id]/ReadingContent.tsx) при `newUi` рендерит абзац
через `react-markdown`.

Разделение обязанностей: **markdown отвечает за начертание** (жирный, курсив),
**наши метки — за доменное** (`{N}` в массив сносок, `{st|}`/`{pl|}`, `{p|}` колонтитул,
`{a|}` якорь). Markdown таких понятий не выражает, и remark-плагин на каждую метку был бы
тем же велосипедом в другой обёртке. Поэтому строковые куски, которые markdown отдаёт
внутрь своих узлов, прогоняются через ту же пару `renderMarkup` + подсветка заметок,
что и обычные абзацы.

Что сохранено намеренно: абзац остаётся **нашим** контейнером с `data-paragraph-index`
(по нему работают пословное выделение, «сообщить об ошибке» и заметки), а markdown-абзац
рендерится фрагментом — вложенного `<p>` не возникает. Нумерация абзацев прежняя,
`content.split("\n\n")`, так что сохранённые заметки не поедут. Момент выбран удачно:
пользовательских заметок сейчас 0, публичных примечаний 2.

**Выделение в церковнославянских текстах — рубрикацией, а не начертанием.** У шрифта
Monomakh одно начертание, жирного и курсива в нём нет, браузер рисует их синтетически и
почти неразличимо. Поэтому при `csSource` `**жирный**` выводится киноварью, `*курсив*` —
приглушённым цветом, как рубрики в самих богослужебных книгах.

Первым текстом на markdown переведён **Алфавитный указатель**: 465 заголовков статей
(`%(…%)` → `**…**`) и 100 подрубрик (`%[…%]` → `*…*`). Ифику и Правила не трогали —
у них в оригинале 0 и 1 выделение соответственно, переводить нечего.

Попутно: во всех заменах `renderMarkup` проставлены React-ключи (раньше их не было,
и консоль ругалась на `FootnoteLink`).

**Нарезан по буквам — 2026-08-27.** Профиль `ukazatel` в `split-book`: раздел открывает
абзац из одной буквы с точкой. Вышло **27 разделов** (`pravila-ukazatel-1…27`, названия
«Указатель: А» и так далее), прежний адрес `/reading/alfavit-duhovny-1` стал их оглавлением.
Медиана раздела около 3 тыс. знаков, самый крупный — «С» на 21,5 тыс.

Разделов 27, а не 26: буква «Є» встречается дважды. Первый блок — Е (Евагрій, Евангеліе),
второй, стоящий между Ч и Ѳ, — это Э (Економъ, Епітімія), в церковнославянской печати
оба набраны через Є. Названия оставлены как в книге; если нужно различать в списке,
переименовать — одна правка в базе. Там же «Оꙋ» — это У.

Попутно чинилось: нарезчик не переносил в новые тексты `newUi` и `contentType`,

### Чистка HIP и нарезка на главы — сделано 2026-08-27

**Что оказалось на самом деле.** Тексты были не просто «не разбиты», а залиты с orthlib
в сыром формате HIP: читатель видел маркеры разрыва строк `//` (6951 штука в Ифике),
колонтитулы `(л. а҃)`, сноски в фигурных скобках, переключатели `<::рꙋс>`, шапку OCR.
Сырую разметку несли ровно четыре текста базы — Ифика, «Алфавит» и два текста Книги
правил; остальные крупные книги (Добротолюбие, Лествица, ПВЛ, Маргарит) чистые.

**Приведение к юникоду** ([src/scripts/lib/hip.ts](src/scripts/lib/hip.ts), запуск —
`npm run db:normalize-hip`). Целью взят не учебник, а сам корпус: замерены 296 чистых
церковнославянских текстов (3,4 млн знаков), и замены приводят батч к их норме.
Снято 24 157 паразитных титл перед ударением (в корпусе такой пары нет ни разу; плотность
титл в Ифике была 7,8% против 0,42% по корпусу, после чистки 0,61%), 12 924 ASCII-ударения
(`` ` ``→вария, `^`→камора), 13 792 латинские подстановки (i→і, f→ѳ, W→Ѡ, S→Ѕ, V→Ѵ, JЬ→Ѣ,
Jа→Ꙗ), 720 числовых знаков (`#`→҂, `_пс`→ѱ, `_кс`→ѯ). 754 сноски уехали в `footnotes`,
822 колонтитула стали `{p|л. а҃}` — привязка к печатным страницам сохранена, из потока
чтения ушла. Исходник каждого текста лежит в поле `hipSource`, прогон обратим.

Не тронуто и напечатано списком: 19 мест в Ифике с `\@` и `[?]`. `\@` парами обрамляет
слово, к которому дана сноска-перевод, но границы стоят непоследовательно — по одному
тексту читается неоднозначно, гадать не стали.

**Нарезка** ([src/scripts/split-book.ts](src/scripts/split-book.ts), `npm run db:split-book
-- --book=ifika`). Прежний адрес каждого разрезанного текста стал оглавлением части

- **Ифика** — 70 разделов: 67 глав (медиана 3 тыс. знаков), две таблицы-вставки и

  короткий абзац без табуляции, без ссылки на сноску в начале и без номера с двоеточием.
  Оставшиеся ложные срабатывания перечислены поимённо в `NOT_A_HEADING`.
- **Книга правил** — 31 раздел и 3 оглавления, 757 правил, каждое с якорем `{a|N}`:

### Упоминания святых доведены до читателя — 2026-08-27

Граф связей был в базе, но наружу выходил одной стороной: со страницы святого было

**Поправка к цифрам.** «2468 текстов с `dneslovId`» — неверно: в счёт попадала пустая

**Имена святых** — [src/lib/dneslov.ts](src/lib/dneslov.ts). Кэш на сутки (тег

(память `10` не отвечает нигде, `102` отвечает по https и висит по http, разом это
меняется за минуты). Дело не в схеме, а в нестабильности сервиса, поэтому запрос
пробует https, затем http. Раньше `getDneslovObject` всегда ходил по http —
`process.env.NODE_ENV ? http : https` истинно всегда, задумано было обратное.

### Ударения: проверка расстановки — 2026-08-28

Знак ударения — отдельный символ ПОСЛЕ своей гласной, и при наборе или распознавании
он легко съезжает на соседнюю букву. Глазами это не вычитывается: на экране разница
в пиксель. Зато словарь ударных форм, собранный по самому корпусу, отличает «яќо» от
«я́ко» мгновенно — 12 тысяч правильных написаний против трёх десятков сбитых.

**Поправка к оценке.** Первый замер дал «21 320 сбитых знаков в 1225 документах» —
цифра завышена вчетверо с лишним, и виноват был сам замер: разбор рвал слова на буквах
Cyrillic Extended-C, считал ошибкой ударение, отделённое от гласной псили, и включал
румынскую Библию. Настоящее число — **1 997 слов**.

**Что сделано.** Исправлено **1 692 слова в 795 документах**, 291 оставлено человеку.
Скрипт [fix-accent-marks.ts](src/scripts/fix-accent-marks.ts) (`npm run db:fix-accents`),
общее ядро — [src/scripts/lib/accents.ts](src/scripts/lib/accents.ts), 14 тестов.

| основание правки | слов |
|---|---|
| словарь знает одно положение ударения | 1 045 |
| одно положение перевешивает остальные на порядок | 382 |
| лишний знак при другом, стоящем верно | 215 |
| сдвоенный знак подряд | 50 |
| **оставлено:** нет в словаре | 147 |
| **оставлено:** настоящее разночтение (го́ре / горе́) | 93 |
| **оставлено:** верная форма встретилась лишь однажды | 46 |
| **оставлено:** больше двух знаков в слове | 5 |

**Как чинится.** Знак не переставляется наугад: по слову без надстрочной разметки
ищется правильная форма в словаре, из неё берётся НОМЕР ударной гласной, и в исходном
слове знак ставится после той же по счёту гласной. Само слово словарной формой не
подменяется — иначе терялись бы ерок, титло и прочая разметка, которой в словарной
форме может не оказаться.

Страховки: dry-run по умолчанию, снимок прежнего содержимого перед записью, и главное —
инвариант «правка обязана менять только знаки ударения». Если снять их и слово выходит
другим, правка отклоняется при любой уверенности словаря. За оба прогона инвариант не
отклонил ни одной правки; повторный запуск находит 0 к исправлению.

**Что выяснилось про сам корпус** — всё это записано в ядре, чтобы следующий скрипт
не наступил заново:

- **Знаков ударения три, а не один.** Оксия U+0301, вария U+0300, камора U+0311.
  В Елизаветинской Библии вария стоит в 64 тысячах стихов, камора в 11 тысячах —
  проверка «по U+0301» четверти разметки не видит.
- **Вария часто вросшая.** ѐ (U+0450) и ѝ (U+045D) — это «е» и «и» с уже приросшим
  тупым ударением: 221 и 234 текста, 10 190 и 12 756 стихов. Считать их обычными
  буквами — значит потерять целый пласт ударных форм в словаре.
- **А ѓ (U+0453) и ќ (U+045C) — всегда ошибка.** Македонские буквы, согласная с
  приросшим ударением; нашлись в трёх текстах и до этой правки были невидимы вовсе,
  потому что одним символом.
- **Между гласной и ударением законно стоит псили** («а҆́ще»), поэтому проверять по
  непосредственно предыдущему символу нельзя — нужно отступать назад через всю диакритику.
- **Разложенные ї и й.** В Лествице и Маргарите они записаны как і+U+0308 и и+U+0306,
  а не одним знаком.
- **Ерок U+033E** заменяет ъ внутри слова («и҆з̾ ни́хъ») — слово на нём не делится.
- **Буквы Cyrillic Extended-C** (ᲂ, ᲅ, Ᲊ) стоят в Маргарите, Ифике и Алфавите. Разбор,
  который их не знает, рвёт слово посередине и видит обрывок.
- **Слова под титлом — сокращения и числа** (бж҃їѧ, к҃є = 25). Ударение к ним
  неприменимо, из проверки исключены: 75 слов.
- **ᲂ, ᲇ и ᲈ — гласные**, а не диковинные согласные: это о, ѣ и ꙋ старой графики,
  и в Маргарите ударение стоит прямо на них. Пропущено при первом заходе; из-за
  этого 13 верных написаний числились ошибками, а одно (`єгᲂ́` в `margarit-17`)
  успело «починиться» и было возвращено из снимка. Остальные буквы того же блока
  (ᲀ, ᲁ, ᲃ, ᲄ, ᲅ, ᲆ) — согласные и ъ.
- **Половина стихов — румынские.** Из 73 241 стиха 36 280 принадлежат «Сфънта
  Скриптура» (валашская кириллица 1688): другая орфография, свой набор знаков.
  Ни в словарь, ни в проверку.

**Словарь ударений** собирается только из слов без замечаний: иначе сбитая форма
голосовала бы сама за себя, а у редкого слова могла бы оказаться единственной.
Тем же кодом, что и артефакт, — см. следующий раздел.

**Осталось из плана по ударениям:** 28 неразмеченных текстов (решение отложено),
словарь как раздел публичного API и озвучка, ради которой всё это и затевалось.

### Ударения: словарь как артефакт — 2026-08-28

`npm run accents:build` ([build-accent-dictionary.ts](src/scripts/build-accent-dictionary.ts))
собирает словарь в файл. До этого он существовал только внутри текстов: каждый скрипт
перебирал весь корпус заново (полминуты) и заново решал, что считать ударением.

**Что в файле.** Ключ — слово без надстрочной разметки; значение — варианты
УДАРЕНИЯ, а не написания: `[номер ударной гласной, знак, частота, написание]`.

```
"глаголет": [[1, "́", 1100, "глаго́лет"]]
"руку":     [[0, "́", 173, "ру́ку"], [1, "́", 138, "руку́"], [1, "̀", 1, "руку̀"]]
```

**Группировка по положению ударения, а не по написанию** — главное решение здесь.
«а́дова» и «а҆́дова» различаются звательцем, ударение в них на одной и той же гласной,
и считать их спорной парой нельзя. Переход на положения снял **1408 ложных
разночтений** и сразу же дал 16 новых починок в проверке расстановки: слова вроде
«амин́ь», «ап́остола», «Избав́итель» до этого блокировались тем, что варианты
написания дробили счёт.

| | основ |
|---|---|
| всего | 182 812 |
| ударение везде на одной гласной | 174 707 |
| одно положение перевешивает на порядок | 1 881 |
| настоящее разночтение | 6 224 |

Ударных вхождений — 1 612 947: оксия 1 417 279, вария 164 263, камора 31 405.
Это чистое число, без румынской Библии и без слов со сбитым знаком.

**Файл воспроизводим:** ни времени сборки, ни путей внутрь не пишется, две сборки
на одной базе дают побайтово одинаковый результат (проверено по sha256). Размер —
10,7 МБ, `--pretty` для чтения глазами.

**Где ему жить — решать владельцу.** Сейчас он ложится в `script-data/`, а этот
каталог целиком в `.gitignore`, то есть файл остаётся локальным: ни в репозиторий,
ни на сервер он так не попадёт. Для пункта 5 плана (словарь как раздел публичного
API) нужно либо положить его в отслеживаемый каталог, либо загружать в Mongo и
возить вместе с базой. Это меняет и релиз, и то, что проект отдаёт наружу, поэтому
скрипт просто печатает предупреждение и ничего не решает сам.

**Заодно вынесено в общее** — [src/scripts/lib/corpus.ts](src/scripts/lib/corpus.ts):
чтение корпуса для работы с ударениями. Два места, где легко ошибиться, теперь
закрыты в одном: содержимое лежит в двух коллекциях (у библейских книг текст не в
`texts.content`, а построчно в `verses`), и половину стихов надо отбросить как
румынские. Сборка словаря и проверка расстановки берут корпус отсюда.

### Ударения: дописано пропущенное — 2026-08-28

Пункт 3 плана, в урезанном виде: только тексты, которые уже размечены. Скрипт —
[add-missing-accents.ts](src/scripts/add-missing-accents.ts) (`npm run accents:add`).

**Дописано 5 128 ударений в 1 217 текстах.** Самый наглядный случай — «Паренесис»,
где одно и то же слово стоит в строке дважды: «Испо́лните очеса́ ва́ша слез, и а́бие
отве́рзутся **очеса** ва́ша у́мная». Наборщик отвлёкся; глазами такое не выловить.

**Что считается пропуском.** Не «слово без знака» — в церковнославянском наборе
предлоги и частицы знака не несут, и первый замер выдал верхушку из «и», «не», «же»,
«бо», «на». Правило взято из самого корпуса: слову ударение положено, если оно
размечено не реже чем в девяти случаях из десяти («рече́» — 9 466 раз из 10 003,
«же» — 4 из 29 тысяч). Всего таких пропусков по собранию — 33 374, но две трети
приходятся на 28 текстов, которые не размечали никогда.

| состояние текста | текстов | не хватало |
|---|---|---|
| размечено полностью (≥99%) | 1 357 | 1 266 |
| редкие пропуски (90–99%) | 841 | 5 372 |
| размечено частично (30–90%) | 37 | 6 330 |
| **не размечено вовсе (<30%)** | **28** | **20 252** |

Работали только с верхними двумя полосами. Нижние две не трогали сознательно:
расставить ударения в тексте, где их не было (крупнейший — «Повесть временных лет»,
11 141 слово), — это работа за наборщика, а не исправление недосмотра. Отдельное
решение, отдельный разговор.

**Три отсечки, которые пришлось завести, глядя на живые примеры:**

- **Киноварь `{k|…}`** — уставные пометы, которые страница чтения печатает красным.
  В богослужебных книгах их не размечают: внутри киновари знак стоит у 39% слов
  против 98% снаружи. Отложено 275 слов в 46 текстах.
- **Неразмеченные куски внутри размеченного текста** — заголовок («Иже во святых
  отца нашего Иоанна, Архиепископа Константинопольскаго…») или цитируемое зачало,
  которое дальше толкуется («В начале бе Слово»). Поставить знак одному слову такой
  строки — сделать её наполовину размеченной, то есть хуже, чем было. Судим по
  соседям, и **соседи берутся только из той же строки**: без этого условия окно
  дотягивается из заголовка в размеченный текст следом и признаёт заголовок
  размеченным. Отложено 123 слова.
- **Живые разночтения** — 1 113 слов, где корпус даёт два положения ударения
  (`ру́ку` и `руку́`). Только вручную.

**Прогон сходится не с первого раза:** дописанный знак поднимает плотность вокруг
себя, и место, отложенное как неразмеченный кусок, на следующем проходе проверку
проходит. Пять проходов: 5101, 19, 4, 2, 2, 0. Разрастись это не может — строка, где
размечено меньше половины слов, не проходит проверку ни на каком проходе.

**Страховки те же:** dry-run по умолчанию, снимок содержимого перед записью, полный
список правок в TSV и инвариант — снимаем дописанный знак и обязаны получить
исходное слово в точности, причём добавлен должен быть ровно один знак. Опора нигде
не ниже девяти верных написаний; половина правок опирается на тысячу и больше.

После дописывания проверка расстановки (`npm run db:fix-accents`) находит 0 к
исправлению — новых сбитых знаков не появилось.

### Словарь ударений: публичный API — 2026-08-28

`/api/v2/accents` — 293 891 основа церковнославянских ударений. Раздел собран из
**трёх** источников, и это главное, что выяснилось при проектировании.

**Словарь ЦС сам размечен ударениями.** `typikon-csl.lexems` — 33 985 лексем и
148 210 форм, выписанных с ударениями. Сходятся они с корпусом по `accentKey`, снятому
с каждой формы.

> Уточнено 01.09.2026. Здесь стояло, что формы «порождены по парадигмам», а поле
> `lexems.search` — «в точности наш accentKey». Неверно и то и другое. Формы словарь
> держит выборочно (половина существительных имеет ровно одну — саму лемму), а

**Третий источник — корпус песнопений.** Октоих, Минеи, Триоди, Часослов лежат в

размечены ударениями: 98 476 текстов, 2,8 млн слов, из них **2,12 млн размеченных** —
по весу свидетельств почти как весь книжный корпус (1,6 млн). Даёт 33 338 основ,
которых нет больше нигде: гимнография держит свою лексику («богоневе́стная»,
«живоприе́мному», «уневе́стивый»). Корпус на удивление чистый: сбитых знаков — 27 штук
на 2,1 миллиона.

| источник | основ |
|---|---|
| книжные чтения (Mongo, с частотами) | 182 812 |
| песнопения (SQLite typikon-rules, с частотами) | 85 922 |
| словарь ЦС (парадигмы, с грамматикой) | 138 629 |
| знают хотя бы двое | 95 276 |
| **вместе** | **293 891** |

Пересечения всюду частичные: словарь склоняет формы, которых в книгах ни разу не
встретилось; корпус знает употребление, которого нет в парадигмах; песнопения —
третий словарь поверх обоих.

**Частоты книг и песнопений не складываются.** Это главное решение по третьему
источнику. Жанр переворачивает большинство на омографах:

| слово | в чтениях | в песнопениях |
|---|---|---|
| спасе | `спасе́` ×50 (аорист) | `спа́се` ×2024 (звательный) |
| души | `души́` ×545 (ед. род.) | `ду́ши` ×3001 (мн. им.) |
| сердца | `се́рдца` ×814 | `сердца́` ×1293 |
| горе | `го́ре` ×342 (скорбь) | `горе́` ×676 (вверх) |
| лука | `лука́` ×57 (оружие) | `лу́ка` ×223 (имя) |

Сложенная частота дала бы невнятную середину вместо двух внятных ответов. Поэтому
`corpus` и `chants` — отдельные поля, и доля считается внутри источника. Потребитель
берёт тот, который отвечает его тексту.

Запись `спасе` показывает, зачем нужен и третий: словарь объясняет, отчего разница —
`спасе́` это `спасти́` aor. 2p/3p, а `спа́се` это `спа́съ` sg.voc. Два разных слова с
одинаковым написанием без знаков.

**Источники не сливаются в одну «истину».** Там, где знают хотя бы двое (95 276 основ),
ударная гласная совпадает в 97,6% случаев; 2 333 расхождения — разной природы:

- **законные омографы**: «зе́мли» (мн. им.) и «землѝ» (ед. род.) без знаков пишутся
  одинаково; так же «лица», «словеса», «дѣла», «горѣ», «души»;
- **ошибки порождения в словаре**, видные по самому словарю: у лексемы `твори́ти`
  форма `тво́рити`, у `или́` — `и́ли`, у `ѕѣлѡ́` — `ѕѣ́лѡ`. Ещё `наи́паче` против
  корпусного `наипа́че` (522 вхождения), `є́си` против `є҆сѝ` (3 289).

Весомых расхождений корпуса со словарём — где корпус видел слово 50 раз и больше —
**121**. Это готовый список правок для словарного опыта, но разобрать его может только
человек.

Поэтому ручка отдаёт **происхождение, а не приговор**: `corpus` и `chants` с частотами,
`lexicon` с грамматикой и признак `agree` (сошлись ли все знающие слово источники на
одной гласной). Потребитель синтеза берёт источник своего жанра; исследователь видит
разнобой как разнобой.

**Где лежит.** `typikon-csl.accents` — соседняя коллекция рядом со словарём, ключ
слова это `_id`. Своей базы не заводили: у `typikon-csl` общее с ударениями
пространство ключей, свой релиз (`csl-db-release.sh` делает `mongodump` всей базы,
так что коллекция едет на сервер без единой новой строки в выкладке) и та же
редкость пересчёта.

Имена полей в хранении короткие (`c` — книги, `h` — песнопения, `x` — словарь, `a` —
согласие; внутри `v`, `m`, `s`, `n`, `l`, `p`): записей почти триста тысяч, и при
длинных именах коллекция занимала 53,6 МБ уже на двух источниках, раздувая
`typikon-csl` с 8 МБ до 70. С короткими и с тремя источниками — 47,5 МБ, база 63,9 МБ. Наружу всё разворачивается в
читаемый вид в [store.ts](src/lib/accents/store.ts), так что короткие имена не выходят
за пределы модуля.

**Ядро переехало** из `src/scripts/lib/accents.ts` в
[src/lib/accents/core.ts](src/lib/accents/core.ts): из `src/scripts` приложению
импортировать нельзя, а разбор слова нужен теперь и API, и скриптам.

**Ручки.**

- `GET /api/v2/accents/{слово}` — одно слово. Слать можно как есть, с ударениями и в
  любой графике: `а҆́ще`, `аще` и `А́ЩЕ` — один запрос.
- `GET /api/v2/accents?words=аще,земли,зело` — до 200 слов, ответ в порядке запроса.
- `GET /api/v2/accents` — сводка, оговорка и ссылка на выгрузку.

**Промах — это `200` с `known: false`, а не `404`.** Сознательное отступление от
остального v2: имён собственных, редких форм и опечаток исходника в словаре нет и не
будет, для синтеза «не знаю» — рабочий ответ на каждое десятое слово, и заставлять
клиента ловить на этом ошибку значит мешать нормальную работу с поломкой.

Постраничного обхода нет намеренно: четверть миллиона записей по двести за раз — это
больше тысячи запросов ради того, что отдаётся одним файлом.

**Доступ** — как у всего остального: новый раздел `accents` в `SCOPES` и в
`FREE_SCOPES`. Без ключа 60 запросов в час (нынешний `ANONYMOUS_ALLOWANCE`, править
ничего не пришлось), по ключу — обычные тарифы. Ключи с `ALL_SCOPES` получили раздел
сами; в выдаче ключей раздел появился автоматически, она строится по `SCOPES`.

**Оговорка в самом ответе:** словарь описательный, а не нормативный. Он говорит, как
слово размечено в этом собрании и сколько раз, а не как правильно. Без этой строки его
начнут цитировать как источник нормы.

**Ссылка на выгрузку показывается только когда файл выложен** — по переменной
`ACCENTS_DUMP_URL`. Обещать в API адрес, которого нет, хуже, чем промолчать.
Сам файл пишет `npm run accents:load -- --dump путь.json` (48 МБ, из тех же записей,
что ложатся в коллекцию, — выгрузка и API не разъезжаются).

**Оговорка про чужой файл.** `build_db.py` в typikon-rules удаляет `data.db` и строит
заново, и чтение посреди пересборки даёт неполный срез — на этом и попались: тот же
файл отдал сперва 91 450 текстов вместо 98 476, а следом «database is locked».
Загрузчик поэтому печатает число прочитанных текстов и переживает недоступность файла,
собирая словарь без песнопений. Локально нужен `NODE_ENV=development`: иначе скрипт
читает `.env.production`, где `RULES_DB` указывает на путь сервера, и песнопения молча
выпадут.

**Осталось на стороне сервера:** раздача файла nginx'ом. По образцу apk
(`location /app/` → `/var/www/typikon-app-releases/`) — `location /data/` →
`/var/www/typikon-data/`, копирование в релизе и `ACCENTS_DUMP_URL` в окружении.

**Не делалось:** разметка целого отрывка (`POST /api/v2/accents/text`). Требует
разрешить `POST` в CORS (сейчас в `baseHeaders` только `GET, OPTIONS`) и перенести на
сервер разбор, который живёт в скриптах. Вторая очередь. Пока батч по словам закрывает
тот же сценарий, если клиент режет текст сам.

### Раздел «Ударения» для читателя — 2026-08-28

Словарь на 294 тысячи основ был доступен только через `/api/v2/accents`, то есть
программистам. Теперь — [страница `/accents`](src/app/accents/page.tsx), подсказка в
отекстовке и показ на странице чтения.

**Что добавилось в данные.** Чтобы расставить ударения в тексте, мало знать, где знак
стоит: надо знать, положен ли он слову вообще — «и», «не», «же», «бо», «на» его не
несут. В коллекции лежали только ударные счётчики, поэтому в запись добавлено поле `u`
(сколько раз слово встретилось без знака) и заведена коллекция
`typikon-csl.accentCoverage` — 73 текста, размеченных меньше чем на 90%. Корпус ради
этого не трогали: производное лежит рядом со словарём.

Текстов в покрытии 73, а не 65, как считалось раньше: теперь «положено ли слову
ударение» решается и по песнопениям тоже, и слов, которым знак положен, стало больше.

**Ядро разметки** — [src/lib/accents/mark.ts](src/lib/accents/mark.ts), одно на все три
поверхности. Чистое, без базы (за базой ходит
[service.ts](src/lib/accents/service.ts)) — потому и проверяется тестами: 12 штук на то,
что киноварь, слова под титлом и уже размеченное не трогаются, что текст собирается
обратно без потерь и что снятый знак возвращает исходное слово.

Правило осторожное: **знак ставится только там, где собрание отвечает однозначно**.
Спорное слово остаётся без знака и возвращается со списком вариантов — выбирает человек.
Инструмент, который угадывает молча, хуже того, который честно говорит «здесь надвое».

Отдельно пришлось свести варианты **по гласной, а не по паре «гласная + знак»**: без
этого «сотворѝ ×1015 / сотвори́ ×948» выглядело неразрешимым спором, хотя ударение в
обоих написаниях на одной букве — вария ставится в конце колона. На пробном абзаце
спорных было пять из семи слов, стало три, и все три настоящие: `руку`, `души`, `спасе`.

**Ядро переехало** в `src/lib/accents/`: `core.ts` (разбор слова и словарные типы),
`store.ts` (Mongo), `mark.ts` (разметка), `service.ts` (то и другое вместе). Из
`src/scripts` приложению импортировать нельзя, а разбор нужен теперь всем.

**Страница `/accents`.** Два режима: расстановка в присланном тексте (до 20 000 знаков,
переключатель «чтение / песнопение», спорные слова кликаются и раскрывают варианты с
частотами) и справка по одному слову — три источника рядом, со ссылкой на склонение в
словаре. Считает своя ручка `POST /api/accents/mark`, не публичная v2: там кап в
двести слов, а здесь нужен цельный текст.

**Подсказка в отекстовке** — кнопка «Расставить ударения» под полем ввода в
[SubmitForm](src/app/texting/[id]/SubmitForm.tsx), с отменой. Спорные не трогает: человек
сверяется со сканом и видит, как в книге.

**Показ на странице чтения** — переключатель «как в книге / с ударениями» у текстов из
покрытия. Разметка считается на сервере и лежит в `cached()` по тегу `TEXTS`: ПВЛ — 55
тысяч слов, пересчитывать её на каждый заход нельзя. Состояние в адресе (`?accents=1`),
чтобы по ссылке было видно, в каком виде текст показан.

**Это не запись в корпус.** Под текстом стоит прямая пометка: знаки поставила машина,
столько-то из стольких, в самом тексте их нет. ПВЛ размечается на 97,5% (14 543 из
14 910) — но вычитанной книгой это не становится, и отложенное решение по 73 текстам
остаётся за владельцем. Показ просто снимает с него срочность.

**Группы в шапке** — [NavGroup.tsx](src/app/NavGroup.tsx), новый для сайта элемент:
«Собрание» (Библиотека, Песнопения) и «Пособия» (пока одни Ударения; туда же со временем
переедут словарь церковнославянского и родословная). Кнопка с `aria-expanded`, закрытие
по Esc и щелчку мимо — плоский список ссылок клавиатуре был доступен, а выпадающий на
`div` с `onClick` перестал бы быть.

### Публичный API как продукт

Сделано: `/api/v2` с явной лицензией, описанием ручек (`/api`, `openapi.json`) и
стабильными адресами; `/api/v1` объявлен устаревшим и считает оставшихся клиентов.

Доступ отмерен по трём уровням (`src/lib/api/v2/tokens.ts` — правила, `access.ts` — их
применение к запросу):

| кто | сколько | разделы |
|---|---|---|
| свои страницы (Sec-Fetch-Site) | 120/мин с адреса | все |
| ключ, тариф `free` (профиль) | 30/мин, 10 000/сутки | все |
| без ключа | 60/час с адреса | все, кроме поиска |

Ключи пользователь заводит себе сам в профиле (до пяти). Ключи приложения и партнёров
выпускаются в админке (`/admin/api-tokens`: общий список с расходом, правка чисел,
отзыв и возврат) либо тем же скриптом с сервера:
`npm run api:token -- issue --name "Android" --tier app --apply`, там же `list`, `set`
и `revoke`. Отзыв доходит до API не позже чем через полминуты — столько живёт кэш
ключей; из профиля кэш сбрасывается сразу, но полагаться стоит на полминуты: админка
и публичный API — разные сборки, общей памяти у них может не быть.

Что осталось по этой теме:

- **Приложение пока ходит в v1 и без ключа.** Следующий шаг на его стороне: перейти на
  v2 и представляться ключом тарифа `app` — тогда доля клиентов без ключа станет видна
  так же, как сейчас видна доля без `X-Typikon-App`, и v1 можно будет закрывать.
- Счётчики частоты живут в памяти процесса — при переезде на несколько процессов их
  придётся выносить наружу (суточный расход уже в базе и переживёт).
- Отдельной страницы «мои ключи» с историей расхода по дням нет: в профиле видно
  только сегодняшнее число. Появится нужда — данные для этого уже пишутся
  (`typikon-users.apiTokenUsage`, по суткам).

### Новости об обновлениях

Читателю неоткуда узнать, что корпус пополнился: правки тихие, а страница «О проекте»
со списком версий обновлялась руками и отстала. Поэтому — отдельная лента.

- База `typikon-news`, коллекция `posts`. Отдельная, а не коллекция в `typikon`:
  дампы контента накатываются целиком (`mongorestore --drop`, см. `release-db.sh`),
  и новостям в этой карусели делать нечего.
- Запись: заголовок, короткое изложение (уходит в RSS и в описание страницы), тело в
  markdown, вид (обновление/объявление), необязательная версия, черновик/выложено.
  Адрес получается из заголовка латиницей; занятый дополняется номером.
- Читают четверо: лента `/news`, отдельная запись `/news/{alias}`, фид
  `/rss.xml` (в корне: рядом с лентой стоит `/news/[alias]`, и он перехватывал бы
  «rss.xml» как алиас новости) и ручка `/api/v2/news` (раздел доступа `news`, открыт
  без ключа) —
  все из одной кэшированной выборки, сбрасываемой тегом `news` при правке.
- Вкладки профиля открываются якорем: `/profile#tokens` ведёт сразу к ключам API, а не
  к чужим заметкам. Этим пользуются новость про публичный API и страница `/api`.
- Точка «новое» в меню: последняя дата спрашивается у API не чаще раза в полчаса и
  сравнивается с отметкой в localStorage. Пришедшему впервые точка не загорается —
  иначе она горела бы у всех и всегда и перестала бы что-либо значить.
- Дата публикации ставится один раз: правка выложенной новости не поднимает её наверх
  ленты и не зажигает точку повторно.

об этом стоит в ленте (`/news/rabota-nad-6-0`).

Все — с холостым прогоном по умолчанию: без `--apply` печатают план и ничего не меняют.

### Служба устава: последование собирает Python, а не сайт

Раздел `/ustav` показывает службу, собранную по Типикону: канву, наполненную
песнопениями книг, и рядом — правила, которые её так сложили. Собирает её не
сайт, а отдельный процесс `typikon-ordo` (`src/ordo_service.py` проекта
typikon-rules), поднятый systemd на 127.0.0.1:8767; адрес — в `ORDO_SERVICE_URL`.
Код лежит в `/var/www/typikon.su/typikon-ordo` — рядом с сайтом и корпусом, а
не в домашнем каталоге: служба системная, принадлежать одному человеку ей
незачем. Рядом, а не внутри `typikon-web`: там своё рабочее дерево git.

Почему не переписать сборку сюда. Устав — конструктор, а не выборка: сколько
единиц петь, откуда их брать и что чем подменяется, решают правила, написанные
руками в `rules/typikon`, и разбирают их полторы тысячи строк на Python.
Второй конструктор разошёлся бы с первым на первой же правке правила — а
правила правятся постоянно, устав ещё достраивается.

Наружу служба не смотрит и в nginx не проксируется: она читает файлы правил по
имени из запроса и про ключи доступа ничего не знает. Сайт ходит к ней сам, с
того же хоста, и отдаёт наружу уже разобранное. Текст правила для «лестницы»
проходит через внутреннюю ручку `/api/ordo/rule`, где путь проверяется второй
раз.

Корпус служба берёт тот же, что и сайт (`RULES_DB`), — второй копии файла на
сервере нет.

**Как доносить правку устава.** Правила живут на сервере в двух видах, и это не
дублирование: `build_db.py` разбирает `rules/**.yaml` в таблицы `ordo_steps`,
`typikon_allocation` и прочие — сборка читает их, а не файлы, и едут они внутри
корпуса; сами же файлы нужны «лестнице», которая показывает их текст, и едут со
службой. Выложить одно без другого — значит получить страницу, где показанное
правило не соответствует собранной службе, причём разойдутся они молча.

Поэтому на правку устава есть одна команда:

```
cd ../typikon-rules && python3 src/build_db.py   # правила -> таблицы
cd ../typikon-web   && npm run release:ustav     # корпус, затем служба
```

`release:ustav` сам проверяет, что корпус не старше правил: если `rules/` правили
после пересборки, он откажется — в базе лежал бы прежний устав, а «лестница»
показывала бы новые файлы.

Отдельные `release:rules-db` и `release:ordo` остаются для случаев, когда меняется
что-то одно: разобрана новая книга (корпус без кода) или поправлен код сборки
(служба без 91 МБ корпуса).

### Что нужно на сервере один раз

Выкладка идёт по ssh без терминала, и обычный `sudo` там пароль не спросит —
скажет «a terminal is required» и упадёт. Поэтому скрипты пользуются `sudo -n`:
он либо срабатывает молча, либо сразу отказывает, и тогда скрипт печатает, что
именно доделать руками, и **завершается с ошибкой**. Молча пропустить
привилегированный шаг нельзя: файл доедет, а сайт продолжит читать прежний
корпус по уже открытому дескриптору, и выкладка будет выглядеть удавшейся.

Проверить, есть ли право (на сервере, под admin):

```
sudo -n true && echo "есть" || echo "нет"
```

Если нет — из-под root, одной строкой в `/etc/sudoers.d/typikon`:

```
admin ALL=(root) NOPASSWD: /bin/systemctl restart typikon-web, /bin/systemctl restart typikon-ordo
```

(путь к `systemctl` сверить через `command -v systemctl` — на части систем это
`/usr/bin/systemctl`.)

Каталог под корпус заводить не нужно: он ложится в `/var/www/typikon.su/`,
рядом с каталогом сайта, куда admin и так пишет при каждой выкладке. Если
вдруг окажется, что писать туда нельзя, скрипт скажет об этом и предложит
`chown` или `setfacl` — но обычно этого шага нет.

Юнит `typikon-ordo.service` ставится из-под root — но однажды: меняется он
редко, и `release:ordo` переставляет его сам только тогда, когда право есть.

Замечание про уже существующее: `rebuild-remote.sh` вызывает
`sudo systemctl restart typikon-web.service` тем же способом и **без `set -e`**.
Если права нет, этот вызов всё это время молча не отрабатывал, а выкладка
считалась успешной — стоит проверить тем же `sudo -n true`.

### Второе хранилище: корпус песнопений

Раздел `/chants` и ручка `/api/v2/chants` читают не Mongo, а отдельный файл
SQLite — корпус проекта typikon-rules (`RULES_DB` в окружении). Это песнопения
книг, разобранные по местам службы: 95 тысяч строк Октоиха, Миней, Триодей и
Ирмология с памятями, знаками и гласами.

Лежит он в `/var/www/typikon.su/data.db` — **рядом** с каталогом сайта, а не
внутри него, и разница тут не в аккуратности. У `nobles.db` один читатель —
сайт, и жить внутри его каталога выкладки ему не мешает. У корпуса читателей
два: сайт и служба устава, выкладываемые порознь. А в каталоге сайта идут
`git pull`, `npm i` и сборка, и сделанный там `git clean -fdx` (обычный приём,
когда сборка сломалась) снёс бы 91 МБ корпуса разом у обоих разделов, ничем
себя не объяснив — `-x` удаляет и то, что перечислено в `.gitignore`.

Соседний каталог этого не касается, а главное — принадлежит тому же admin,
который выкладывает: корпус доставляется вообще без root. Пробовали
`/var/lib/typikon` — по уму место верное, но каталог там заводится только
из-под root, и ради одного файла это лишний шаг при каждой новой машине.

Почему файлом, а не в Mongo. Корпус целиком пересобирается из разобранных книг
и правил устава (`python3 src/build_db.py` в typikon-rules), руками в него не
правят, через админку не редактируют. Это артефакт сборки: класть его в Mongo
значило бы денормализовать реляционные связи и переиндексировать 95 тысяч
документов после каждой пересборки.

Поиск по нему держится на FTS5: токенизатор `unicode61 remove_diacritics 2`
снимает ударения при разборе на слова — и в тексте, и в запросе, — поэтому
нормализованные копии полей, какие приходится держать для Mongo
(`searchName`/`searchContent`), здесь не нужны.

Порядок: пересобрать корпус в typikon-rules -> `npm run release:rules-db`.
Скрипт сам проверяет, что индекс на месте, и перезапускает приложение: файл
открывается один раз на процесс, и без перезапуска новый корпус не увидят.

---

Все скрипты, меняющие контент, после записи сбрасывают кэш выборок через
`POST /api/revalidate`. Для этого нужен `REVALIDATE_TOKEN` в окружении — без него
скрипт предупредит, что сайт будет отдавать прежние данные до истечения кэша (час).

## Правила для обходчиков (сделано 2026-08-31)

`public/robots.txt` состоял из четырёх строк: `Crawl-delay: 1`, `Host:` (Яндекс
перестал читать эту директиву в 2021-м) и ссылка на карту сайта. Ни одного
`Disallow`, то есть обходчику были открыты и поиск по 12 млн символов
(`/search`), и бесконечное адресное пространство калькулятора
(`/calculator/<любая дата>`), и склонения словаря, и `/admin` с `/profile`.
Публичный API при этом закрыт как следует — ключи, минутное окно, суточная квота
(`src/lib/api/v2/access.ts`), — а страницы не были закрыты никак.

**Сделано.** `src/app/robots.ts` вместо статики в `public/`: правила живут в коде
рядом с картой сайта и по той же причине — отдельный файл в `public/` устаревает
молча, когда адреса разделов меняются. Закрыты личное, дорогое и машинное;
`/api/` со слешем, чтобы страница описания `/api` осталась в индексе.
Отдельной группой закрыты обучающие обходчики: корпус под CC BY 4.0 и против его
распространения мы не возражаем, возражаем против выкачки сайта постранично
вместо API, где для того же есть ключ. Обходчики «по запросу пользователя»
(`ChatGPT-User`, `Perplexity-User`, `Claude-User`) оставлены открытыми — за ними
живой человек со ссылкой на источник. В `next.config.js` — `X-Robots-Tag:
noindex` на те же разделы: `robots.txt` не мешает попасть в выдачу по чужой
ссылке, а заголовок мешает.

**Осталось на стороне сервера.** `robots.txt` — просьба, и не читают её ровно те,
от кого нагрузка. Отказ им написан двумя файлами и применяется вручную:
`typikon-bots.conf` (карты по User-Agent и зоны счётчиков) идёт в
`/etc/nginx/conf.d/`, `typikon-bots-server.conf` (`403` выкачивателям и сами
`limit_req`) — в `/etc/nginx/snippets/`, и подключается одной строкой `include`
в `server{}` сайта.

Разделено именно так после того, как первая попытка применить конфиг ничего не
изменила: половина, которая работает, лежала комментарием в хвосте единственного
файла и читалась как документация, а не как обязательный шаг. Файл в `conf.d`
сам по себе не делает ничего — карты и зоны только заготавливают переменные и
счётчики, — и nginx на нём перезапускается молча и без ошибок. Отдельный
`snippets/`-файл, который надо подключить строкой, пропустить труднее.

Ограничение на `/search` и `/calculator/` навешено через карту по `$uri`, а не
через `location`: иначе пришлось бы завести два `location` со своим `proxy_pass`
и держать их в согласии с основным.

**Грабли, из-за которых конфиг трижды не применился:** правка ключа у уже
существующей зоны разделяемой памяти требует `restart`, а не `reload`. Зона
`typikon_heavy` сначала считалась по `$binary_remote_addr`, потом переехала на
карту по `$uri` — и каждый `reload` откатывался с
`[emerg] limit_req "typikon_heavy" uses the "$typikon_heavy_key" key while
previously it used the "$binary_remote_addr" key` в `error.log`. `nginx -t` это
не ловит и не может: он разбирает конфиг с нуля в отдельном процессе, где нет
никакого «previously», — проверка живёт только в работающем мастере, в момент
`reconfiguring`. `systemctl reload` при этом возвращает успех, потому что мастер
не падает. Снаружи ровно та же картина, что и при неприменённом конфиге, так что
единственный способ увидеть причину — `error.log`. Запросы с `Authorization` из счётчиков
исключены — их считает само приложение, и иначе под ограничение попало бы наше
же мобильное приложение (ходит через okhttp).

Хост общий, сайтов на нём несколько, поэтому имена карт и зон начинаются с
`typikon_` (совпадение имени зоны с чужой — и nginx не запускается), а
`limit_req_status` стоит в `server{}`, а не в `http{}`: в `http{}` он поменял бы
код отказа всем остальным сайтам. Правила вешаются на `server{}` для
`www.typikon.su` — на голом домене живёт только редирект, и проверять их curl'ом
надо тоже по www, иначе видно один 301.

**Заодно: выравнивание на www.** Канонический адрес сайта — `www.typikon.su`
(апекс отдаёт 301), а `BASE_URL` в карте сайта, ленте, календаре и документации
API указывал на голый домен. Каждый адрес из карты обходчик забирал в два запроса
вместо одного — ровно та нагрузка, о которой речь; примеры в документации
(`curl https://typikon.su/api/v2/...`) без `-L` не возвращали вообще ничего, а
тега `canonical` на страницах не было, и какой из двух адресов настоящий,
обходчик решал сам.

Заменены адреса со схемой в 13 файлах; прозаические упоминания «typikon.su» как
названия сайта оставлены. Не тронуты:

- `uid` событий в `calendar.ics` — это опознавательный знак, а не адрес; смена
  превратила бы у каждого подписчика правку дня в новое событие рядом со старым;
- `redirectUrl` виджета входа через Telegram (`AuthorizeChecker.tsx`,
  `login/Content.tsx`) — домен там должен совпадать с заданным у бота в BotFather,
  и менять его надо одновременно с обеих сторон;
- `DEFAULT_SITE_ORIGINS` в `tokens.ts` — там оба адреса, и так и нужно.

В корневом layout появились `metadataBase` и `alternates.canonical: "./"`:
относительный путь разрешается по текущему маршруту, поэтому свой `canonical`
получает каждая страница, а не весь сайт один общий. Страницы со своей `metadata`
это наследуют — поля метаданных сливаются, и `alternates` ни одна не переопределяет.

**Ещё находка, не исправлено:** `openGraph.images` в корневом layout ссылается на
`https://www.typikon.ru/logo.png` — домен `.ru`, не наш, и не резолвится вовсе
(`www.typikon.su/logo.png` тоже отдаёт 404). Картинки в превью ссылок нет ни у
одной страницы сайта. Нужна картинка и решение, какая.

## Библия: своя модель, канон и параллельное чтение (сделано 2026-08-30)

Обе Библии лежали обычными книгами библиотеки: издание — документ в `books` с
`bibleLanguageCode`, книга — документ в `texts` с `bibleBookSlug`, стих — `verses`
с `textId`. Модель молча предполагала, что пара «глава:стих» означает один и тот
же стих в любом издании.

**Это было неправдой, и оно текло.** Паремия «Дан. 3:1–88» отдавала на румынском
33 стиха вместо 88 — без пометки, без запасного языка: в издании 1688 года песнь
трёх отроков напечатана отдельной книгой, а славянский Даниил держит её внутри
третьей главы. Сверка нашла ещё два таких: «Иоил. 2:23–32» отдавал 5 стихов из
10, «Мал. 4:4–6» — ноль.

### Что теперь

У стиха две нумерации. **Родная** (`chapter`/`verse`) — как напечатано в издании,
ею стих показывают. **Каноническая** (`canonRef`/`canonSort`) — приведённая
правилами к эталону, ею резолвятся зачала и сходится параллель. Эталон —
Елизаветинская Библия: она же запасной язык чтений, она же традиция, в чьей
нумерации записан весь устав.

| было | стало |
|---|---|
| `books` + `bibleLanguageCode` | `bible_editions` (сколько угодно изданий на язык) |
| `texts` + `bibleBookSlug` | `bible_books` (`slug` — как напечатано, `canonId` — куда легло) |
| `verses` + `textId` | `bible_verses` (обе нумерации + `canonRef`) |
| адреса `/reading/biblia-*` | раздел `/bible`, со старых — постоянный редирект |

Канон — 77 книг в `src/utils/bibleCanon.ts`, выведен из прежнего `bookMap`.
**Идентификатор книги канона — тот же слуг, что в `pericopes.bookSlug`**: благодаря
этому 1067 зачал и вся разметка сносок не мигрировали вовсе.

### Чего правила не умеют

Правило выражает СМЕЩЕНИЕ («эта книга издания есть такая-то глава канона»,
«с такого-то стиха прибавь столько-то»). Оно бессильно, когда издание иначе
РАЗБИЛО текст на стихи — два слиты в один, длинный разнесён на три.

Сверка (`BIBLE_VERSIFICATION.md`) показала **246 глав** с расхождением длин,
разброс от −67 до +35 стихов: у румынского издания своя разбивка почти по всему
Ветхому Завету. Поэтому правил семь, и все проверены арифметически — Даниил
(песнь отроков, Сусанна, Вил), Малахия и Иоиль, разбитые по еврейскому счёту.

Остальное закрывает **фолбек по непокрытию**: если издание отдаёт меньше половины
ожидаемого, чтение целиком берётся из церковнославянского. Порог, а не строгое
равенство, — по замеру: после правил 1033 чтения покрыты полностью, 25 на 90–99%,
9 на 50–89% (одиночные дыры румынского набора), пустых нет. Строгое равенство
отняло бы у румынского читателя три десятка чтений из-за разницы в разбивке.

### Что нашлось попутно и ждёт разбора

- **В церковнославянском Исходе нет глав 37–39.** В источнике (bible.by/elzs) их
  текст напечатан сплошняком, без стиховой разбивки, и импорт его отбросил. Зачал
  оттуда нет, так что богослужебно не течёт, но эталон дырявый — помечено в шапке
  сгенерированного `src/utils/bibleVersification.ts`.
- **38 дыр в нумерации румынского издания** — пропущенные номера стихов внутри
  глав (Рим. 1:12, 1Кор. 11:9, 11, 24 и другие). Это дефекты набора, не
  версификация; список — в отчёте.
- **Псалтирь и Сирах** расходятся с эталоном на 83 и 36 глав. Выровнять постишно
  можно только сверкой самих текстов; правилами это не выражается.

### Порядок работы с правилами

Правила живут в `src/lib/bible/mappings.ts` — в гите, с объяснением и тестом на
каждое. Дописал правило → `npx tsx src/scripts/recompute-bible-canon.ts --apply`
→ `verify-bible-migration.ts`. Само по себе правило ничего не меняет: `canonRef`
лежит у стихов посчитанным.

Скрипты переноса (`migrate-bible.ts`) и уборки (`drop-legacy-bible.ts`)
отработали; прежние коллекции удалены. Импортёры Библии оставлены ради разбора
источника, но запускаться отказываются — они писали в снятую модель.

## Святцы: свой каталог и снимок dneslov (сделано 2026-08-31)

**Что было.** Идентичности святого в проекте не существовало — её роль играл чужой
номер. `texts.dneslovId`, `texts.mentionIds`, `memory_saint_links`,
`akathist_saint_links`, `nobles.dneslovId`, публичный адрес `/saints/{id}` и,
дальше по цепочке, `rules/memory_saints.yaml` и `memories.dneslov_id` в корпусе
typikon-rules — везде номер dneslov.org. Имена не хранились вовсе: их тянули по
сети в момент рендера, и это записано в шапке `src/lib/dneslov.ts` как
сознательное решение.

Из этого следовали три беды, и все три были уже задокументированы в самом коде:
сервис нестабилен (неполная цепочка сертификатов, схема то одна то другая, замер
2026-08-27 — 39 секунд на страницу указателя); когда он молчит, читатель видит
«Память №3030»; а если у них запись сольют, разделят или перенумеруют, наши связи
поедут молча, и заметить это будет нечем.

**Что сделано.** Два слоя, оба скриптами, рендер пока не тронут.

`dneslov_memories` — снимок чужих святцев: сырой ответ `memories/{id}.json` плюс
подробности по слугу, дата снимка, состояние. Снимает `sync-dneslov.ts`
(`npm run dneslov:sync -- --write`), он же единственное место в проекте, которое
ходит к ним по сети пачкой. Скрипт собирает номера из всех пяти мест, где они у
нас лежат, снимает только устаревшее (`--max-age`, по умолчанию месяц) и
различает три исхода: снято, **исчезло у них** (404) и не ответило. Различие
принципиальное: 404 означает протухший внешний ключ и требует решения человека,
а недоступность не означает ничего — прежний снимок остаётся в силе и НЕ стирается.

`saints` — наш каталог: своя запись со своим `_id`, а номер dneslov ушёл в
`externals`, куда потом встанут Wikidata, «Древо» и месяцесловы других поместных
церквей. Строит `build-saints.ts` (`npm run saints:build -- --write`) из снимка,
а не из сети: сборку надо уметь повторить, не завися от чужого сервера. Поля,
перечисленные в `manual`, перестройка не трогает — иначе правка, сделанная
вечером, исчезала бы при ближайшей синхронизации, и каталог остался бы зеркалом
чужой базы, а не нашей записью.

Из снимка достаются имя (`short_name` — готовая подпись с ударениями), заголовок,
чин (`events[].orders[].name`), соборы, базовый год и **дни памяти**
(`memoes[].year_date` в их формате «ДД.ММ»). Последнее — то, ради чего каталог
понадобится уставу: связь памяти книги с днём календаря.

**Внешние ключи — списком, и почему не картой.** Реестр источников лежит в
`src/lib/saintSources.ts`; сейчас в нём двое — Днеслов и Викиданные (ключи вторых
уже есть в родословной, `nobles.wikidataId`). Просилась карта «источник → ключ»,
и по смыслу `externals` ею и является, но карта не выражает случая, ради которого
каталог заводился: у одной нашей записи может быть ДВА ключа ОДНОГО источника.
Святцы сплошь и рядом держат одно лицо двумя памятями — мирское имя и церковное,
само лицо и перенесение мощей, — и решение «это один человек» принимаем мы, а
хранить его больше негде. Вдобавок Mongo кроет список подобъектов одним составным
индексом, а карту с произвольными ключами пришлось бы индексировать по индексу на
источник, то есть править индексы при каждом новом источнике. Цена решения одна:
пару «источник + ключ» ищут только через `$elemMatch` (см. `byExternal()` там же),
иначе запрос совпадёт, когда источник взят из одного элемента списка, а ключ из
другого.

Из этого же следует, что каталог не обязан быть зеркалом dneslov: святой, которого
у них нет вовсе, заводится своим импортёром и живёт с ключами только своих
источников — или вообще без внешних ключей.

**Чего сознательно НЕ сделано.**

*Слуга нет.* Поле `slug` заведено и уникальность на него поставлена, но не
заполняется. Публичный адрес — обещание, которое нельзя брать назад, а заголовки
у dneslov сплошь и рядом не имена, а фразы («Пренесение мощей святителя Германа,
архиепископа Казанскаго»). Назначать слуги надо отдельной задачей, вместе с
переездом `/saints/{id}` и постоянными редиректами со старых адресов. Затягивать
не стоит: каждый месяц на чужих ключах делает переезд дороже.

*Рендер не переключён.* Страницы по-прежнему ходят к dneslov.org через
`src/lib/dneslov.ts`. Переключение на снимок — следующий шаг, и он же снимает
39-секундный худший случай на указателе.

*В корпус правил ничего не отдано.* Каталог поедет в typikon-rules тем же путём,
что и связи памятей, — выгрузкой во вход сборки (`export-memory-saints.ts`),
когда будет что выгружать.

**Что получилось на первом обходе (2026-08-31).** 852 номера в обиходе, три прохода
подряд: 838 снято, 12 исчезло у dneslov (404), 2 так и не ответили (`624`, `3358` —
таймаут). Каталог: **837 записей**, из них с чином 822, с днями памяти 816, с годом
838, с соборами 734, с иконой 271.

Три находки, ради которых всё и затевалось.

*Двенадцать протухших ключей.* Номера, на которые мы ссылаемся, а памяти у них уже
нет. Четыре пришли из `texts.dneslovId` (тексты Пролога), **восемь — из родословной**,
то есть из связей, которые ставил `link-nobles-dneslov.ts` по их поисковому
`index.json`. Восемь из десяти всех связей Рюриковичей — то есть проблема там не
случайная, а системная: похоже, поиск отдаёт идентификаторы не того рода, что
принимает `memories/{id}.json`. Разбирать отдельно.

*Каталог — не только лица.* По их `type`: Identity 580, **Council 247** (соборы),
Thing 8, плюс по одному Place, Building, Subsisten. То есть четверть записей — не
человек, а собор святых, и для устава это различие придётся уважать: память может
быть лицом, собором, событием или иконой.

*Грязный ключ.* В `texts.dneslovId` нашёлся `"8602 "` с хвостовым пробелом (текст
`prolog-03-04-vifonie`) — он завёл вторую запись той же памяти. Обход теперь
обрезает пробелы и называет грязный исходник в отчёте, а на `saints` поставлена
**уникальность внешнего ключа** (`externals.source + externals.id`, частичная — записи
без внешних ключей ей не мешают). Проверено: дубль отбивается, записи без ключей
уживаются. Это ровно та порча, ловить которую каталог и заводился, — пусть база
падает на записи, а не показывает двоящегося святого.

**Права.** `LICENSE-CORPUS.md` утверждал, что сведения о святых «приходят по их
API при показе страницы, в корпусе не хранятся». Со снимком это перестало быть
правдой, формулировка поправлена. Условия на сами данные dneslov.org нигде не
заявлены — открыт только код святцев (GPLv2). Прежде чем показывать снимок
читателям, стоит спросить их напрямую; сам по себе он — тот же кэш, что и
`dneslov_names`, только долгоживущий.

## Святые: переезд на свой адрес (сделано 2026-08-31)

Вторая половина того же дела: каталог завёлся накануне, но страницы всё ещё жили по
чужому номеру. Теперь адрес страницы святого — наш слуг, `/saints/ioann-zlatoust`
вместо `/saints/102`.

**Слуги.** Назначает `assign-saint-slugs.ts` (`npm run saints:slugs -- --write`).
Транслитерация не своя: взяты `slugify` из `@/lib/news/format` и
`normalizeChurchSlavonic` из `@/utils/churchSlavonic` — иначе «Феофа́но» распадается на
`feofa-no`, потому что комбинирующее ударение не буква. 837 адресов, ни одного
столкновения (тёзкам достался бы номер, но их не нашлось).

Главное правило записано в шапке скрипта: **назначенный слуг не меняется никогда**.
Скрипт заполняет только пустые и не трогает занятые, даже если имя потом поправят.
Переименование записи и смена её адреса — разные события, и второе делается руками,
с редиректом.

**Редирект.** `/saints/{номер}` отвечает 308 и уводит на слуг. Навсегда, а не на
переходный период: ссылки вида `{st|102|Златоуст}` стоят в разметке самих текстов
корпуса, и переписать их означало бы править корпус.

**Неизвестный адрес — 404.** Раньше адресами были одни числа и мусор в них не
заводился; теперь адрес — произвольный текст, и двухсотка с надписью «ничего не
нашлось» на каждую опечатку плодила бы бесконечные мягкие 404. Номера остались
исключением: по ним могут найтись тексты и без записи в каталоге — например у памяти,
которая исчезла у святцев.

**Сеть ушла со страниц.** Заодно (иначе переезд не имел бы смысла) карточка памяти
читается из снимка `dneslov_memories`, а не запрашивается у dneslov.org при каждом
показе. Форма ответа та же самая, разметка не менялась. То же и в двух других местах,
где страницы ходили в святцы: указатель `/saints` берёт все имена одним запросом к
своей коллекции вместо полусотни запросов наружу (замер 2026-08-27 давал там 39 секунд
худшего случая), и блок «Связи» под чтением — он ходил в святцы на КАЖДОЕ открытие
текста. Сеть осталась запасным путём для памятей, до которых каталог ещё не дошёл.

**Проверено на живом сервере:** слуг — 200, номер — 308 с верным `Location`,
несуществующий слуг — 404, неизвестный номер — 200. Указатель показывает 823 памяти
именами из каталога, без единого «Память №N». Блок «Связи» под чтением ведёт сразу на
слуг, без промежуточного редиректа.

**Смена адреса руками.** Правило «слуг не меняется» означает не «никогда», а «не
сам собой»: сменить его можно, но осознанно и с последствиями. Для этого
`set-saint-slug.ts` (`npm run saints:slug -- --saint <слуг|номер> --slug <новый>`).
Он кладёт прежний адрес в `previousSlugs`, и с него продолжает уводить тот же
постоянный редирект; прежний адрес остаётся ЗАНЯТЫМ, чтобы `assign-saint-slugs.ts`
не отдал его новому святому — иначе старая ссылка привела бы читателя к чужой памяти.
Он же сбрасывает кэш: правка идёт мимо приложения, и без этого указатель до часа
показывал бы прежний адрес. Заодно указатель `/saints` помечен тегом `SAINTS` —
он теперь берёт из каталога имена и адреса, а не только считает тексты.

Первое применение: `mariya-bogorodica` → `bogorodica`. Проверено: новый адрес 200,
прежний слуг и номер святцев — оба 308 на новый.

**Ссылки в постах канала.** `buildPost.ts` собирал адрес прямо из метки разметки
`{st|102|Златоуст}`, то есть публиковал в канал ссылку по номеру. Опубликованный пост
живёт вечно, и ссылка в нём должна вести куда надо сразу, а не через переброс, который
однажды может и не пережить правки маршрутов. Теперь номера из разметки собираются
заранее и переводятся в адреса одним запросом (`saintSlugs`), а памяти без записи в
каталоге остаются с номером — страница по нему работает. Проверено на живом тексте:
в посте `https://www.typikon.su/saints/gavriil`.

**Что осталось ходить через редирект** (осознанно):

- ссылки `{st|id|label}` в разметке текстов корпуса — `ReadingContent.tsx`,
  `DayPartReading.tsx`. Их правка это правка корпуса, отдельная работа;
- `NobleCard.tsx` — одна ссылка на странице родословной, клиентский компонент,
  слуга туда пришлось бы прокидывать с сервера;
- `/api/v2/saints/{id}` — опубликованный договор, описан на `/api`. Принимать слуг
  наряду с номером — отдельное решение вместе с правкой описания. В коде помечено.

## Святые: именование и ссылки на изображения (сделано 2026-08-31)

**Основное имя и альтернативные.** Раньше имя было одно и приходило из `short_name`
святцев — подписи, собранной по их правилам. Иногда она читается странно: «Мари́я
Богоро́дица», так никто не говорит. Теперь у записи `name` (основное, наше) и
`altNames` (прочие известные именования).

Альтернативные берутся из `names[].name_text` — единственного поля святцев, которое
обещает быть ИМЕНЕМ. `title` туда сознательно не идёт: иногда это голое имя
(«Феофания»), а иногда заголовок повода («Пресвятая Владычица наша Богородица и
Приснодева Мария (отдание введения во храм)»), отличить нечем, а заголовок повода в
списке имён — прямая ложь. Он и так лежит отдельным полем.

Улов оказался ценнее ожидаемого: у 528 записей из 837 нашлись варианты, и это не
только дореформенные написания, но и мирские имена — «Варлаа́м Ху́тынский ← Михалевич ·
Але́кса · Алексі́й».

Основное имя ставит человек: `set-saint-name.ts`
(`npm run saints:name -- --saint bogorodica --name "Богородица" --alt "Богоматерь,Дева Мария"`).
Прежнее имя не теряется — переезжает в альтернативные. Тронутые поля попадают в
`manual`, и `build-saints.ts` их больше не переписывает; цена честная и её надо
понимать: новые варианты со святцев к этой записи сами не приедут. Для десятков
памятей, правленных осознанно, это верный размен; списком по всему каталогу так
делать не надо.

Имя проведено до разметки, иначе оно осталось бы только в указателе: заголовок
страницы святого теперь берётся из каталога, а под ним строка «Известна также как».

**Ссылки на изображения.** Сами файлы не храним — только адреса. Граница честная:
зависимость от их CDN не исчезает, она переезжает с рендера на загрузку страницы у
читателя, и адреса протухают, так что снимок обновляемый (`--images`, свой срок
`imagesAt`), а разметка обязана переживать битую картинку.

Зато уходит запрос за СПИСКОМ, а он был хуже, чем казалось: оба компонента —
`DneslovImages` на странице чтения и `DneslovRoundImage` в содержании книги — ходили в
святцы **из браузера читателя**. Страница книги на полсотни текстов делала полсотни
запросов к чужому серверу, по одному на строку, и их логи видели адрес каждого нашего
читателя. Теперь ссылки приходят с сервера пачкой (`saintRoundels`, `saintImages`), а
браузерный запрос остался запасным путём для памятей, которых нет в каталоге.
`buildPost` тоже берёт картинку из снимка; разница в том, что снимок хранит
изображения памяти целиком, без разбивки по событиям.

**Ошибка, которая стоила трёх тысяч запросов.** Обход за картинками показывал 40%
удач и падал до нуля, и это выглядело как нестабильность их сервера. Дело было в нас:
`images.json` у памяти без изображений отвечает **204 No Content** — пустым телом.
Голый `res.json()` на пустоте падает, и честный ответ «картинок нет» засчитывался как
«не дозвонились». Пятьсот памятей переспрашивались проходом за проходом и физически не
могли ответить иначе. После правки (204 и пустое тело — ответ, а не сбой) те же
памяти дали 92% с первого захода.

Отсюда правило на будущее: **прежде чем винить чужой сервер, проверить, как мы читаем
его молчание**. Диагноз «они нестабильны» был верен для подробностей памятей и неверен
для картинок, а выглядели оба одинаково.

Тот же дефект нашёлся эхом в браузере: `DneslovRoundImage` и `DneslovImages` на
запасном пути тоже звали `res.json()` и роняли необработанное обещание в консоль
читателя на каждом ряду без кругляша. Поправлено там же.

**Итог по снимку.** Список изображений снят у 835 памятей из 837. Изображения есть у
333 (1299 ссылок), кругляш — у 298. У остальных их просто нет: это не пробел в снимке,
а факт о святцах.

**Попутно.** `akathistsOfSaint` роняла всю страницу святого, когда соседний проект
пересобирал `data.db`: SQLite на запертой базе отвечает «attempt to write a readonly
database» даже на чтение. Обёрнуто — страница переживает пересборку корпуса так же,
как переживает недоступность святцев. Акафисты на ней довесок, а имя и тексты наши.

## Святые: поиск в указателе (сделано 2026-08-31)

Восемьсот двадцать три памяти по полсотни на страницу — семнадцать страниц, по
которым только листать. Добавлен отбор по имени.

**Ищется и по альтернативным именам** — ровно ради этого они и собирались: «Дева
Мария» находит Богородицу, мирское «Алекса» — Варлаама Хутынского. В самом списке
альтернативные не показываются, они работают молча.

**Нормализация — вся соль.** Имена в каталоге с ударениями («Феофа́но»), а набирают
без них; сравнение идёт через `normalizeChurchSlavonic`, который снимает надстрочные
и кладёт дореформенные буквы на современные. Побочно «й» становится «и», а «ё» — «е»:
для NFD краткая и умляут — такие же знаки, как ударение. Для поиска это к лучшему
(обе стороны проходят одну нормализацию), но `normalizeForSearch` из-за этого нельзя
брать для сравнения ИМЕН на равенство — она только для отбора. Слова соединяются по И,
а не по ИЛИ: «иоанн злат» даёт Златоуста, а не всех Иоаннов.

Логика отбора вынесена в `src/lib/saintSearch.ts` отдельно от страницы и покрыта
тестами: ошибка в нормализации не падает, а тихо не находит — такое ловится только
проверкой.

**Отбор в памяти, а не запросом в базу.** Указатель и так строится целиком и лежит в
кэше: восемь сотен строк уже в руках. Заводить ради них текстовый индекс с
нормализованными копиями имён — значит завести ещё одно место, где имя может разойтись
с каталогом. Когда памятей станут десятки тысяч, это перестанет быть верным; пока нет.

**Форма обычная, с методом GET**, без своего кода на клиенте: запрос остаётся в адресе,
страницу можно послать ссылкой и вернуться к ней по истории назад. Разбивка на страницы
запрос не теряет.

## Храмы и престолы: каталог и подвязка к уставу (сделано 2026-08-31)

Идея записана в `typikon-rules/IDEAS.md` («География посвящений»). Прикладная её
половина сделана первой: пользователь называет свой храм и получает престол,
престольные праздники с датами и знаком службы. Аналитика ареалов и волн
почитания — вторым заходом.

**Престол — параметр службы, а не подпись к зданию.** От него зависят отпуст
(«и свята́го, его́же есть храм»), тропарь с кондаком по входе на Литургии, канон
храма на субботней утрене и знак службы в престольный праздник (храмовые главы,
Типикон, гл. 61). Движок устава всё это уже умеет — таблица `parish_prestoly`,
`hram_layer.find_hram`, — но престолы попадают туда только из файлов
`rules/prihod/*.yaml` на сервере. Правка движка, позволяющая назвать престол
запросом, отложена до отдельного подтверждения владельца.

### Словарь посвящений — то, на чём держится всё остальное

`src/utils/dedications.ts`: 126 записей вида «образцы названия → посвящение →
праздники → память устава». Он же связывает обе половины задачи: аналитике даёт
группировку, уставу — `memory_id`, читателю — ссылку на святого.

Разбирает **88%** названий по русской выборке Wikidata, на которой строился, и
**58%** по всемирному каталогу (37 442 храма из 64 192 православных). Разница
не в качестве разбора, а в языках: см. ниже.

Остаток по русской выборке — не брак, а предел разбора: «Красная церковь»,
«Болдыревская церковь», «Лооский храм» никакого посвящения не называют.

**Два яруса, и это не украшение.** Точные образцы всего словаря проверяются
раньше любой короткой основы. Стой основа «троиц» внутри своей записи, храм
Рождества Богородицы в Троице-Сергиевой лавре разобрался бы как Троицкий.

**`\b` в JavaScript не знает кириллицы.** Образец `/спаса\b/` не совпадал ни
разу: между «спаса» и пробелом границы слова для движка регулярных выражений
нет, потому что словом он считает только латиницу. Все Спасские храмы молча
уходили в неразобранные. Закреплено тестом.

### Сверка памяти обязательна

`npm run temples:dedications` находит память по дате — и **сверяет** найденное с
ожидаемым обломком метки (поле `expect`). Без сверки скрипт брал первую память
дня, и это давало тихую ложь: Митрофану Воронежскому доставался Александр
Невский (оба 23 ноября), Кириллу Белозерскому — Кирилл Александрийский, Ксении
Петербургской — преподобная Ксения Римляныня. Теперь такое не связывается вовсе
и попадает в отчёт.

Из 149 праздников память нашлась у 141. Восемь ненайденных — честные дыры
корпуса: Иоанн Кронштадтский, Тихон Патриарх, Лука Крымский, Ксения
Петербургская, «Неупиваемая Чаша». Дореволюционная Минея их не знает, и это
прямой рабочий список, а не изъян разбора.

**Связи со святыми переносятся только выверенные.** Все 653 связи
`memory_saint_links` пока со статусом `pending`, и среди них есть мимо: Ильинскому
храму сопоставитель предлагает Илию Севастийского вместо пророка Илии. Такие
лежат в `saintCandidates` и на страницу не идут.

### Данные

Wikidata (CC0): 11 763 храма России с координатами, 8 555 с годом постройки.
Престола там нет полем — P138 заполнено у 979 из 11 763, — он в названии.

**Запрос беден нарочно.** Добавь к нему P31 или P1435 — число строк множится на
каждое значение свойства, и служба отвечает 502 на 240-й секунде. Тип постройки

### Карта не рисовала подложку — и не рисует её в `/places`

OpenLayers меряет узел в тот миг, когда карту строят, а строится она из эффекта:
вёрстка ширины ещё не дала, и карта запоминает ширину 0. Дальше она честно
решает, что покрывать нечего, и **не запрашивает ни одной плитки** — при этом
метка рисуется, отчего изъян выглядит как «карта без карты». Лечится
наблюдателем размера плюс одним `updateSize` следующим кадром. Старая карта в
`src/app/places` болеет тем же и не починена.

### Каталог стал всемирным, а источником — OSM

Замер решил вопрос об источнике. В OpenStreetMap **70 122** объекта с
православным исповеданием по всему свету; в Wikidata с явной пометкой
православия — **3 532** на весь мир. Вшестеро больше, чем вся русская выборка
Wikidata, и притом не по одной стране. Wikidata остаётся при годе постройки,
охранном статусе и связях с Википедией — этого в OSM нет.

**Престола полем нет НИГДЕ.** В OSM теги `church:dedication` и `dedication` на
весь мир стоят у четырёх объектов из семидесяти тысяч; в Wikidata «назван в
честь» — у 979 из 11 763 по России. Значит словарь остаётся единственным
путём, и вопрос не в источнике, а в языках.

**Словарь заговорил на других письменностях.** Кириллица славянских Церквей
разбиралась и раньше (сербское «Успење», болгарское «Света Троица» ловятся
русскими основами), а греческие и румынские имена были немы совсем. Добавлены
образцы к двадцати пяти частым посвящениям — `αγιου νικολαου`, `sfantul
nicolae`, `svetog nikole`, — и два местных святых: Савва Сербский и Иоанн
Рильский.

Ради них пришлось снимать надстрочные знаки вообще (греческий тонос, румынские
ă, ș, ț), а снимаются они разбором буквы на основу и знак — **тем же разбором
распадается и «й»**. Без защиты «Смоленской» превращалась в «Смоленскои», и
образец с «ой» переставал совпадать. Закреплено тестом.

Позже добавлены английский, французский и грузинский, а «Saint» приведено к
«St» при разборе имени: держать оба вида в каждом образце значило однажды
забыть один из них — на выгрузке так и вышло, «Saint Sophia» и «Saint Basil's»
проходили мимо образцов, написанных через «st». Греческое «Άγιος» тоже
склоняется, и жёсткое `αγι[οα][σς]?` ловило только именительный, тогда как в
названиях храмов стоит родительный: «Αγίου Θεοδώρου».

### Страна, Церковь и устав

Устав у Церквей разный, и собирать службу афинского прихода по русскому уставу
значит выдать ему чужое. Поэтому у храма теперь есть страна, поместная Церковь
и устав движка — или честное «устава этой Церкви у нас нет» (написан ровно
один, `jerusalem/rus-synodal`).

Церковь известна у 58 531 храма: РПЦ 26 974, Румынская 9 045, Элладская 8 439,
Украинская 3 237, Сербская 2 627, Грузинская 2 336, Болгарская 1 470,
Македонская 993, Эфиопская 886, Армянская 716, Албанская 416, прочие меньше.

**Церковь берётся из метки исповедания OSM**, а не выводится: `russian_orthodox`,
`greek_orthodox`, `serbian_orthodox` ставит человек, глядя на храм. Где метка
общая («orthodox»), Церковь выводится по стране — и помечается выведенной
(`churchSource: "country"`), потому что в диаспоре такой вывод неверен: в
Германии рядом стоят приходы РПЦ, Константинополя, Сербской и Румынской.

**Страна — из координаты, а не из источника.** Тег `addr:country` в OSM ставят
редко: он нашёлся у 2 024 записей из 64 849, а по координате страна вывелась у
59 021. Не определилась у 3 804 — приграничные и островные, где грубых границ
не хватило; такие остаются без страны, а не приписываются наугад. Границы взяты Natural Earth 110m
(общественное достояние, 248 КБ в `script-data/countries.geojson`): для «в
какой стране храм» точности хватает с запасом, подробные весили бы десятки
мегабайт ради той же буквы кода. Приграничные и островные остаются без страны,
а не приписываются наугад.

### Приделы: что дают открытые данные и чего не дают

Разбор имени теперь берёт ВСЕ престолы, какие оно называет, а не один:
«Сретенско-Преображенская церковь», «Часовня Параскевы Пятницы и Варлаама
Хутынского». Главным считается названный первым.

Прежняя попытка (поле `alternatives`, 2469 записей) была шумом: она читала и
скобки, а там стоит место — «(Козьмодемьянск)» давал придел Космы и Дамиана
всякому храму того города, «(Никольск)» — Никольский. С отсечением скобок и
общих записей («Богородица (прочие иконы)» при Казанской) остаётся **437**
храмов с двумя престолами по всемирному каталогу — и это уже настоящие приделы.

**Больше имя не скажет.** У храма с тремя престолами в имени стоит один, и
остальные знает только приход. В частных сводах они есть: указатель
days.pravoslavie.ru собран ПО ПРЕСТОЛАМ и выписывает приделы прямо в
заголовке — «Храм Космы и Дамиана (Благовещения) в Шубине», «Храм святителя
Николая (Воскресения Христова) в Ржавках». То же у sobory.ru и temples.ru.

Своды эти авторские, и потому заведён реестр источников
(`src/utils/templeSources.ts`) с правилом для каждого: `import` — везём целиком
(открытая лицензия), `link` — не везём ничего, отсылаем читателя, `verify` —
сверяем поодиночке, когда приход уточняет свой храм. Отдельный факт ничьей
собственностью не является, свод целиком — чужой труд; разница проходит по
объёму, и массовый вывоз — это разговор с владельцами свода, а не задача для
скрипта.

### Каталог числом (после привоза 2026-09-01)

**64 849 храмов** по всему свету: 40 431 из OpenStreetMap, остальные из
Wikidata и сведённые с ней. Из привоза OSM отброшено 9 884 объекта без имени
или без точки — ни престола, ни карты из них не выходит.

Имя кириллицей у 4 765 записей OSM, иным письмом — у 16 469: всемирный каталог
на три четверти нерусский, и это определило работу над словарём.

### Что вышло

- `/temples` — указатель с поиском по имени и месту, отбором по посвящению;
- `/temples/map` — карта всемирного каталога. Сводит храмы в гнёзда СЕРВЕР:
  свести их в браузере можно, но для этого все точки надо сперва привезти, а их
  десятки тысяч.

  **Порога по масштабу нет, и это исправление, а не упрощение.** Сперва порог
  был («ближе девятого шага показываем поодиночке»), и делил он карту не по
  тому признаку: решает плотность, а не приближение. Посреди Владимирской
  области девять сотен отдельных точек слипались в кашу и на девятом шаге.
  Теперь клетка одна на все случаи, а разбирается по содержимому: один храм в
  ней приходит сам собою, с именем и адресом, несколько — числом.

  **Шаг сетки задан в ПИКСЕЛЯХ, а не в градусах.** Два градуса на пятом
  приближении дают на экране двадцать точек, а кружок гнезда имеет сорок в
  поперечнике — кружки налезали друг на друга. Шаг обязан меряться в том, в чём
  меряется налезание; градусы из него выводятся по масштабу. Заодно это
  ограничивает и объём: клеток на экране всегда полторы сотни, сколько бы
  храмов ни лежало в базе.

  **Ответы приходят не в том порядке, в каком их просят.** Всемирный вид
  считается по всей базе и отвечает медленнее ближнего, а приходит последним —
  и затирал уже отрисованную область прежними гнёздами. Внешне это выглядело
  как «карта не обновляется при приближении», хотя нужный ответ давно пришёл и
  был показан. Лечится номером запроса;
- `/temples/[slug]` — престолы, престольные праздники с гражданскими датами и
  знаком службы, «это мой храм», карта, ссылки на источники;
- «мой храм» живёт в браузере, как настройки чтения, и даёт строку «сегодня
  престольный праздник вашего храма» на `/calculator/[date]`.

### География посвящений — раздел

`/dedications` и `/dedications/[slug]`. Отвечает на три вопроса, на которые до
сих пор отвечали впечатлением, а не числом.

**Где кончается почитание — радиусом ареала.** Медианное удаление храма от
средоточия и радиус, вмещающий четыре пятых. У Николая Чудотворца — 348 и 705
км, у местных святых счёт идёт на десятки вёрст. Медиана, а не среднее: один
храм в диаспоре уводит среднее на тысячи вёрст, а медиану — никуда.

**Когда почитание разошлось — волной построек рядом с чертой прославления.**
Ради этой черты раздел и делался: столбцы сами по себе говорят лишь «строили
тогда-то», а дата прославления превращает их в ответ. У Серафима Саровского
самый высокий полувек — 1900–1949, черта 1903 года стоит в его начале, медиана
1904, половина храмов между 1901 и 1912. У Митрофана Воронежского то же после
1832-го.

Год прославления проставлен ТОЛЬКО там, где он не спорен (одиннадцать записей).
Для древних святых прославление растянуто и датируется по-разному, и подпирать
картинку спорным годом значило бы выдать спор за факт.

**Что посвящение говорит о возрасте здания** — медианой года и границами
половины: Никольский храм скорее всего первой половины XIX века (медиана 1823,
половина между 1780 и 1878).

**Главная оговорка, без которой всё это ложь.** Сырое число храмов на карте
показывает не почитание, а плотность населения. Поэтому по странам считается
ПРЕВЫШЕНИЕ доли посвящения над его же долей по всему каталогу, а не количество.

**Порог честности:** ниже десяти храмов выводов не делаем вовсе — по такому
числу точек меры говорят о полноте каталога, а не о почитании. Показывается
только карта и прямая оговорка. По тому же порогу рисуется и волна.

Картинка волны — обычный SVG, собранный на сервере: она неподвижна, её
разглядывают, а не крутят, и тащить ради неё библиотеку графиков в браузер
незачем. Карта посвящения — та же карта храмов с отбором, а не вторая её копия.

### Придел и есть престол

Уточнено по ходу работы: в приделе престол один, и «придел Никольский» значит
«престол святителя Николая». Разница между записями храма — только в том,
главный престол или нет. Сверх того бывает престол УТРАЧЕННЫЙ: освящённый здесь
когда-то и упразднённый, память которого приход всё равно празднует. Такой не
выводится ниоткуда и ставится только руками — поле `state` у престола.

### Не сделано

- форма правки для приходов и разбор правок в админке — а это единственный
  настоящий источник приделов;
- сверка с частными сводами поодиночке (правило `verify` реестра источников);
- словарь молчит на албанском, грузинском и арабском: имена этих храмов не
  разбираются вовсе;
- регион внутри страны: `P131*` до субъекта федерации кладёт запрос Wikidata,
  взято только ближайшее P131 (район или город);
- `/temples` в карте сайта;
- правка движка устава ради престола запросом — ждёт подтверждения.

## Хронология: перевод дат и разбор датировок (сделано 2026-09-01)

Страница `/chronology`, пункт «Хронология» в «Пособиях». Две вкладки: перевод одного
дня между календарями (по умолчанию) и разбор летописной датировки перебором.

**Счёт свой, а не запросом к службе, и это осознанное отступление** от того, как
устроено последование (`src/lib/ordo.ts` ходит в typikon-rules). Там иначе нельзя:
устав — живой конструктор в полторы тысячи строк, второй такой разошёлся бы с первым
на первой правке правила. Хронология же ЗАКРЫТА: полтораста строк, сверенных с
печатной таблицей, меняться им не с чего. А пособие, которое темнеет, когда на
сервере не поднята служба на Python, пособием быть перестаёт.

Риск двух счётов настоящий и в этом проекте уже сбывался — «минус тринадцать» зашит
в [calcDay.ts](src/lib/calcDay.ts) и трёх других местах, тогда как рулзы давно считают
разницу стилей через юлианский день. Поэтому расхождение ловится прогоном, а не
обещанием: `npm run chronology:diff` сверяет обе стороны на 1485 годах. Питонова
сторона сверена с книгой, значит совпадение с ней — сверка с книгой через одно звено.

**Чем проверено.** `src/utils/chronology.ts` — свойствами, которые сломаются от
опечатки, но не переписываются вместе с кодом: Пасха всегда воскресенье и всегда в
границах 22 марта — 25 апреля; вруцелето шагает на единицу, а через високос на две;
основание растёт на одиннадцать и раз в девятнадцать лет на двенадцать — это лунный
скачок, без него круг не замкнулся бы. Границы совпадения новоюлианского с
григорианским не объявлены, а выведены счётом и вышли теми самыми: 1 марта 1600 —
28 февраля 2800. Александрийская эра проверена независимой величиной: её отставание
от константинопольской вышло ровно шестнадцатью годами.

**Три исхода перебора разведены** и объяснены на странице: один год — сошлось;
несколько — запись недоопределена, и это ответ о ЗАПИСИ; ни одного — запись
противоречит себе, и тогда показывается, каким чтением она чинится. Голого «без
индикта что-то находится» мало — печатается поправка: «читать индикт как 6 вместо 7,
правка на единицу, → 5 марта 1203».

**Одинаковые ответы сводятся в одну строку.** Мартовский счёт эры с сентябрьским дают
одно и то же лето круга ВСЕГДА и расходятся только днём и только на сентябре–феврале;
григорианский с новоюлианским совпадают с 1600 по 2800, то есть почти на всякой дате.
Две одинаковые строки читались бы как два разных ответа — это один в двух именах.

**Грузинский короникон и селевкидская эра добавлены** в тот же день. Короникон —
номер года внутри 532-летнего круга; кругов у него несколько, и один и тот же номер
приходится на каждый, поэтому рядом с числом всегда назван круг. Тут же поправка к
тому, что стояло в заметках: короникон был назван «буквально нашим великим
индиктионом», и это неверно — длина и устройство общие, а фаза разная, византийский
круг пошёл с 1941 года, грузинские с 781, 1313, 1845. Короникон 1941 года равен 97.
Селевкидская взята сирийским, октябрьским счётом — тем, в котором стоят рукописи;
македонский, весенний, апрелем не приближаем: нисан месяц лунный.

**Эфиопский и армянский добавлены** тогда же. Египетский строй вынесен общим счётом:
коптский с эфиопским разнятся только эпохой и именами месяцев. Армянский особый — у
него нет високоса вовсе, год ровно в 365 дней уходит назад на сутки за четыре года и
обходит круг за 1461 год, день в день равный 1460 юлианским; это единственный здешний
календарь, чьё начало года не стоит на постоянном числе, и потому единственный, чью
эпоху нельзя проверить свойствами — она ждёт датированного колофона.

Попутно поправилось ходячее описание эфиопского: «Новый год 11 сентября» верно только
для нашего века. Начало года прибито к юлианскому счёту (29 или 30 августа), а разница
стилей растёт на сутки за столетие — в XVII веке это было 9 сентября, после 2100 станет
12-е. В тесте закреплено неподвижное, подвижность проверяется отдельно.

**Два счёта пока стоят пустыми строками с пометой «в плане»** (иудейский и хиджра). Читатель, не нашедший иудейской даты, иначе решит,
что мы о ней не знаем. Что делать с каждым — в `TODO.md` рулзов, раздел
«Календарь и портал».

**Открытым остаётся индикт:** общепринятый счёт расходится с колонкой разобранного
Приложения Типикона на постоянную величину, и решается это печатной страницей, а не
кодом. Оговорка стоит на самой странице.

## PWA: установка и чтение без интернета (сделано 2026-09-02)

Разошлось с этим разделом на 97 коммитов: манифест, воркер и запасная страница
появились ещё 2026-08-24 (`3bcbf55`, `3f17d4e`), а в списке идей PWA всё это время
числилась ненача́той. Здесь — что было и что доделано.

### Что стояло с августа

[manifest.ts](src/app/manifest.ts) (имя, иконки 192/512 из мобильного приложения,
`standalone`, ярлыки на сегодняшний день и поиск), [public/sw.js](public/sw.js)
(навигации сеть-вперёд, `/_next/static` и шрифты из кэша), регистрация только в
проде ([ServiceWorkerRegistrar](src/app/ServiceWorkerRegistrar.tsx)), страница
[/offline](src/app/offline/page.tsx) и `appleWebApp` в корневом layout — установка
на iPhone, где манифест не читают.

### Офлайн был пассивным, и это не то, что обещано

В кэш попадало только уже открытое, молча и с обрезкой по сотне записей. Обещание
«чтение без интернета наравне с Android-приложением» так не закрывается: в дороге
открывается вчерашнее, а не завтрашнее.

Теперь у чтения и у дня есть **«Читать без сети»**
([OfflineSave](src/app/components/save/OfflineSave.tsx)) — на `/reading/[id]` в одном
ряду с «Сохранить из браузера», на `/calendar/[id]` и `/calculator/[date]` под
навигацией по дням. Отмеченное так живёт в отдельном кэше `typikon-saved`, который
не обрезается и **не versioned**: правка правил воркера не должна стирать то, что
человек отложил себе в дорогу. Страница дня выводит тексты чтений целиком, поэтому
отложить её одну — достаточно, за отдельными чтениями ходить не надо.

Сохраняется не только HTML. Страница отдаёт воркеру список своих подкладок — стили,
скрипты, шрифты (`link[href]`, `script[src]`, плюс журнал `performance` — шрифты
приходят из CSS, в разметке их нет), и они кладутся в тот же кэш. Без этого
сохранённое открылось бы голым после первой же выкладки: имена чанков содержат хэш
сборки, и прежних в общем кэше уже нет. Замер: страница дня — 463 КБ, чтение —
523 КБ, вдвоём 1,7 МБ (подкладки общие, второе чтение прибавляет только свой HTML).

Разбор отложенного — в `/settings`, раздел «Чтение без интернета»
([OfflinePages](src/app/settings/OfflinePages.tsx)): список, дата, занятое место,
удаление поштучно и «убрать всё». Занятое считается по факту содержимого кэша, а не
складыванием записей описи: половину объёма делают общие шрифты, и приписывать их
одной странице было бы неправдой. Убрать одну страницу подкладки не трогает — они
общие; целиком их сносит только «убрать всё».

### Запасная страница не работала вовсе

Найдено при проверке: воркер отдавал разметку `/offline` **прямо под запрошенным
адресом**. Заголовок вкладки менялся на «Нет сети», но роутер Next видел, что дерево
маршрута в HTML не про этот адрес, шёл за данными в сеть, которой нет, — и страница
падала в «Что-то сломалось». То есть весь запасной путь с 24 августа показывал
читателю ошибку вместо объяснения.

Чинится не подменой ответа, а переводом на собственный адрес страницы
(`Response.redirect`): там разметка и адрес сходятся. Зацикливания нет — запрос
самого `/offline` до этой ветки не доходит, его отдаёт поиск по кэшам выше.

Заодно: при установке воркер теперь достаёт подкладки запасной страницы из её же
разметки (регуляркой по `/_next/static/...`) и кладёт в кэш. Иначе она открывалась
бы без стилей — её собственные чанки в общий кэш не попадали никогда, потому что до
беды на неё никто не заходит.

На самой `/offline` теперь список отложенного ([SavedLinks](src/app/offline/SavedLinks.tsx)):
без него человек знает, что сохранённое где-то есть, а добраться до него без
интернета может только по памяти адреса.

### Личное больше не оседает на диске

`networkFirst` клал в кэш **любую** навигацию, а `/profile` собирает на сервере имя,
заметки и список ключей API. Исключены были только `/api` и `/admin`. Отдавалось это
лишь в офлайне, но лежало на диске и после выхода из учётной записи — на общем
компьютере лишнее. Признак для исключения не «закрыто от поисковика» (тот список
шире, см. [robots.ts](src/app/robots.ts)), а «в ответе лежит личное»: `/api`,
`/admin`, `/profile`, `/texting`, `/login`.

### Проверено

На продовой сборке с остановленным сервером: сохранённый день и сохранённое чтение
открываются со шрифтами и разметкой; несохранённый адрес приводит на `/offline`, где
виден список отложенного и переход по нему работает; `/profile` в кэше страниц
отсутствует. Тесты — 307 против 298 (счёт страниц по-русски и размер занятого);
`tsc --noEmit` — 149 ошибок, как и до работы, новых нет.

### Не сделано

- Push-уведомления — отдельный пункт «доведения до пользователя»: нужен VAPID-ключ
  и хранение подписок на сервере.
- Отложить наперёд («сохранить неделю вперёд») — сейчас откладывается только
  открытая страница.
- Признака «ты сейчас офлайн» на обычных страницах нет: человек узнаёт об этом,
  лишь наткнувшись на несохранённый адрес.
- Шрифты по-прежнему OTF (1,2 МБ): у отложенного это половина первого сохранения.
  Перевод в woff2 из блока 2 аудита так и не сделан.

## Корпус как данные: выгрузка (сделано 2026-09-02)

`npm run corpus:dump` собирает выгрузку, `npm run release:data` кладёт её на сервер,
страница `/data` рассказывает, что внутри и на каких условиях.

### Зачем — дыра, которая висела в robots.txt

[robots.ts](src/app/robots.ts) закрывает пятнадцать обучающих обходчиков со словами:
против распространения корпуса не возражаем, возражаем против выкачки постранично
«вместо API, за которым для того же самого есть ключ и понятная квота». Но API — не
канал для выкачки: тариф `free` даёт 30 запросов в минуту и 10 000 в сутки, а в корпусе
3 244 текста и 155 765 стихов, то есть несколько суток опроса. Получалось, что мы просим
идти законным путём, которого нет. Выгрузка его создаёт.

### Разбор по правам — главное здесь, а не формат

В базе рядом лежит наше, чужое и наше-под-чужой-лицензией. Слои описаны в
[LICENSE-CORPUS.md](LICENSE-CORPUS.md), а кодом выражены в
[dumpLayers.ts](src/scripts/lib/dumpLayers.ts). Сборка **останавливается**, если в базе
завелась коллекция, о которой никто ничего не сказал: молчание не значит «можно
выкладывать», и первая же новая таблица иначе уехала бы наружу молча.

| слой | лицензия | что внутри |
|---|---|---|
| `corpus` | CC BY 4.0 | тексты, книги, дни, седмицы, знаки, зачала, памяти, святые, посвящения, словарь ударений — 191 956 записей |
| `bible` | CC BY 4.0, по файлу — PD и GPL-3.0 | издания, книги, согласование нумераций по всем пяти изданиям, текст стихов по четырём — 237 770 записей |
| `temples` | **ODbL 1.0** | 64 854 храма с престолами |

Всего 494 580 записей, 24,0 МБ.

**Два открытия по правам, которых лицензия не знала.**

Каталог храмов завезён 1 сентября, уже после того, как лицензия была написана, и в ней о
нём не было ни слова. А в нём **53 091 запись из OpenStreetMap** — то есть ODbL, с
обязательным указанием источника и share-alike на производные базы. Выложить его под
CC BY 4.0 значило бы пересдать чужую базу на своих условиях. Отсюда отдельный слой и
новый раздел в лицензии — чинить это надо было в любом случае, даже без выгрузки.

С Библией тоньше. Наша работа во всех пяти изданиях одна: разбор на книги, привязка к
канону и **согласование нумераций**. А набранный текст стиха наш только в двух — румынская
кириллица 1688 и китайский Новый Завет 1910. Церковнославянская взята с bible.by,
латинская из `lb42/vulgClem`, греческая — ВЗ из `LXX-Swete-1930`, НЗ с myriobiblos.gr.
Издания в общественном достоянии по возрасту, но оцифровка — чужая работа на своих
условиях.

Поэтому **согласование нумераций отдаётся по всем пяти изданиям и без текста**: 155 765
строк вида «издание, книга, глава, стих — и канонический адрес». Это, пожалуй, самое ценное
в слое: его можно приложить к своей копии любого из пяти изданий.

Словарь ударений (182 812 основ) выводится в сборке из тех же текстов, а не берётся
готовым из `typikon-csl.accents`: та коллекция дополнена словарём церковнославянского,
взятым со стороны. Заодно закрыт вопрос «где ему жить», висевший с 2026-08-28: в выгрузке.

Из святых сняты `imageUrl`, `roundelUrl` и `externals` — поля, перенесённые из dneslov;
из текстов `adminInfo`, `fileId` и производные `searchContent`/`searchName`.

### Греческий: своя лицензия на один файл (2026-09-02)

Отдавать Библию без текста оказалось половинчато, и мы пошли искать источник, которым
можно делиться.

**Ветхий Завет отдаём.** Оцифровка Свита выпущена под GPL-3.0 — то есть распространять её
**разрешено**, только на условиях оцифровщика. Значит, прятать её незачем: файл
`bible-verses-grc-ot.jsonl.gz` (29 847 стихов) идёт под GPL-3.0, полный текст лицензии
лежит рядом (GPL §4 требует передавать копию вместе с работой, ссылки мало), а сам текст
взят из [licenses/GPL-3.0.txt](licenses/GPL-3.0.txt) — скачан из того же репозитория, что и
данные, а не с постороннего сайта.

Ради этого у выгрузки завелась **лицензия на отдельный файл**, а не только на слой. Городить
ради одного файла третий слой значило бы спрятать различие в устройстве каталогов вместо
того, чтобы назвать его: теперь и в таблице на `/data`, и в LICENSE.txt слоя, и в манифесте
у каждого файла видны свои условия.

**Новый Завет сперва отложили, потом заменили — см. следующий раздел.** Первый заход искал
политонику в репозиториях `byztxt` и не нашёл: текст Робинсона всюду **без ударений и
придыханий** (`βιβλος γενεσεως ιησου χριστου`), это набор для разбора, не для чтения.
Прочие открытые греческие Новые Заветы с ударениями (SBLGNT, Нестле 1904, THGNT) — другие
издания, критические, а не Патриаршее.

Ральфс 1935 тоже отпал: [единственная доступная оцифровка](https://github.com/eliranwong/LXX-Rahlfs-1935)
под CC BY-**NC**-SA и выведена из CCAT, где нужна подписанная пользовательская декларация.
Некоммерческая оговорка несовместима с нашей CC BY.

Чтобы читатель не остался с пустым местом, у слоя завёлся раздел **«чего здесь нет и где
это взять»**: по каждому невыложенному изданию сказано, почему его нет и где взять самому.
Он виден и на `/data`, и в README слоя, и в манифесте (`notShipped`).

**Поймана вторая тихая потеря.** Деление Библии на заветы отбирает стихи запросом, и первый
заход отбирал ветхозаветную половину перечислением канонических книг — а в греческом
издании есть девять книг, которых в славянском каноне нет вовсе: Оды, 4 Маккавейская,
Еноха, Псалмы Соломона, Даниил, Сусанна и Вил по Септуагинте, Товит по Синайскому списку.
**2 034 стиха выпадали молча.** Теперь Ветхий отбирается отрицанием («всё, что не Новый»),
а сборка проверяет, что половины сходятся с целым, и останавливается, если нет. Проверка
коллекций такую беду не ловит: она про таблицы, а эта — про строки внутри таблицы.

### Греческий Новый Завет заменён на открытый — и он вернее (2026-09-02)

Искали, чем можно делиться, — нашли то, что заодно точнее.

**Источник.** [ebible.org `grcbyz`](https://ebible.org/find/details.php?id=grcbyz) —
«1904 Patriarchal Greek New Testament with 20 corrections from later editions»,
**Public Domain**, политоника, полный USFM с номерами Стронга, ровно 7 958 стихов —
столько же, сколько было у нас, адрес в адрес.

**Кто вернее печатному изданию.** Судили не на глаз: третейским взят выверенный
М. Робинсоном по печатному Антониадису текст (`byztxt/greektext-antoniades` — без
ударений, зато эталон состава слов). У всех троих снято подвижное «ν»: Робинсон его
нарочно регуляризовал, и без поправки меряется условность набора, а не текст.

| | совпадает с печатным изданием |
|---|---|
| прежняя копия (myriobiblos.gr) | 89,1 % |
| **ebible.org grcbyz** | **96,1 %** |
| расходятся оба | 3,6 % |

Около 556 стихов печатному изданию отвечал открытый текст, а не наш.

**Что изменилось в базе** ([import-greek-nt.ts](src/scripts/import-greek-nt.ts),
`npm run bible:greek-nt`): переписано 7 016 стихов, добавлен 1, удалён 1.

- Большая часть переписанного — **конечные знаки препинания**, которых у нашего
  греческого Нового Завета не было вовсе, а у всех прочих изданий есть (у ЦС 36 653
  из 36 961). То есть издание приведено к общему виду, а не разошлось с ним.
- **Рим. 14:26** появился: византийское славословие, которое издание печатает в конце
  четырнадцатой главы, а у нас его не было.
- **Мк. 7:16 удалён** — и это правда издания: у Робинсона стих стоит ПУСТЫМ
  (`7:16 ` без текста), то есть печатное Патриаршее издание его не печатает. Наша
  прежняя копия печатала. Зачало Мк. 28 (7:5–16) потеряло один стих из двенадцати;
  покрытие зачал по греческому осталось **100%** (`measure-pericope-coverage`).

Ветхий Завет не тронут: он в этом же издании, но из другого источника и под другой
лицензией, поэтому уборка исчезнувших стихов ограничена книгами Нового Завета.
Идентификаторы выводятся тем же хешем, что в `import-bible-edition.ts`, иначе стихи
раздвоились бы. Прогон идемпотентный: второй раз показывает ноль изменений.

**В выгрузке** греческий Новый Завет теперь идёт отдельным файлом как **общественное
достояние** — не под лицензией слоя: требовать указания источника на текст, свободный
от притязаний, мы не вправе. Наша работа над ним (разбор и согласование) остаётся под
CC BY 4.0, и это сказано в указании источника.

Заодно уточнено правило в проверках: полный текст лицензии обязан нести **копилефт**
(GPL требует передавать копию, §4), а общественное достояние — нет, передавать в нём
нечего. Прежняя проверка требовала текст у всякого файла со своими условиями и на
этом справедливо упала.

**Не сделано:** прежняя копия текста сохранена в запасе локально, но в репозиторий не
кладётся; исходный USFM лежит в `greek/grcbyz` (каталог в `.gitignore`), как и прочие
исходники изданий.

### Стихи, которых издание не печатает (2026-09-02)

Прямое следствие замены: греческий читатель видел на стих меньше, чем сосед со
славянским, и различить «издание так печатает» и «у них дыра в наборе» ему было нечем.
Молчаливый пропуск и наша недоработка выглядят одинаково.

Теперь такой стих **показывается, но помечается**: приглушённым цветом и крестиком, а
под текстом — строка о том, почему его в издании нет и откуда взят показанный текст.

Таблица живёт кодом ([absent.ts](src/lib/bible/absent.ts)), а не в базе — по той же
причине, что и правила приведения: случаев наперечёт, каждый требует объяснения, и
правка должна быть видна в истории. Плюс запись в базе не пережила бы переимпорт: он
удаляет всё, чего нет в источнике, — а этого стиха в источнике как раз и нет.

**Текст берётся у самого издания.** Для Мк. 7:16 это «εἴ τις ἔχει ὦτα ἀκούειν,
ἀκουέτω.» — слово в слово как напечатано в Мк. 4:23 того же издания (тот же оборот
стоит и в Мк. 4:9). Значит мы ничего не заимствуем со стороны и не подмешиваем чужую
орфографию к своей.

Врезается в двух местах, и оба покрывают по два потребителя сразу:
`parallelChapter` — раздел Библии и `/api/v2/bible`; `resolvePericopeVerses` — чтения
дня. В параллельном виде ячейка заполняется, в одиночном заводится строка (иначе
глава молча шла бы 15, 17).

**Покрытие считается по найденным, а не по показанным.** Восполненный стих издание не
печатает, и засчитывать его в покрытие значило бы утверждать обратное — порог отката
на церковнославянский должен видеть настоящее положение дел.

### Греческий Ветхий Завет: проверка прав и качества (2026-09-02)

Возник вопрос: не тот ли это случай, что с Новым Заветом, — текст на деле свободен, а
мы завязались на источник, объявивший неверные права? Проверено, и ответ иной.

**По правам.** Печатный Свит (Кембридж 1909–1930, Свит †1917) в общественном достоянии
бесспорно; GPL-3.0 объявлена на оцифровку. Свободно изданная оцифровка **того же
издания** существует — [nathans/lxx-swete](https://github.com/nathans/lxx-swete) из
проекта First1KGreek под CC BY-SA 4.0. То есть выбор есть.

**Но брать её не стоит.** Сверка по 54 книгам, 28 379 стихов: совпадает 62%, расходится
37%. Чья описка — определено по частоте (настоящее слово в корпусе повторяется, описка
распознавания встречается однажды). Из 9 915 расходящихся слов **5 916 (59,7%) — описки
у них**, 125 (1,3%) у нас: `κα` вместо `καί`, `πατης` вместо `πάσης`, `αργου` вместо
`ἀγροῦ`. First1KGreek выкладывает многое невычитанным OCR. К тому же CC BY-SA — тоже
share-alike, и выигрыш перед GPL-3.0 для выгрузки невелик.

Полностью свободный вариант один — [Брентон 1851](https://ebible.org/find/details.php?id=grcbrent)
на eBible, но это **другое издание**, а не Свит.

### Просчёт счёта: «273 разорванных слова», которых не было

Стоит записать, потому что ошибка поучительная. Сверка насчитала 273 стиха, где
склейка всех пробелов уравнивает наш текст со свидетелем, — и это было объявлено нашей
порчей. При разборе оказалось наоборот:

- **263 стиха** у нас исправны (`καὶ υἱοὶ Ἑσερὼν`, `ὁ δεύτερος`) — это **свидетель
  слипает слова**, своя беда распознавания. Первая же попытка чинить по его границам
  выдала `καὶυἱοὶ` из правильного `καὶ υἱοὶ`.
- **10 стихов** несут квадратные скобки Свита — его помету о восполненном по другим
  рукописям (`ὁ θ[εὸς λέγων]`). Сравнение заменяло знаки пробелами и принимало скобку
  за разрыв слова. **Скобки остаются**: убрать их значило бы выдать восполненное за
  прочитанное.
- Настоящий случай **один**: Пс. 118:127, где «τοπάζιον» (топаз) разорвано надвое и
  обломок получил свой гравис — «τὸ πάζιον», по соседству с «τὸ χρυσίον».

Мораль для будущих сверок: границы слов чужой оцифровки — не эталон, а мнение, и
принимать его без проверки нельзя.

### Половины греческого издания записаны разными знаками

Найдено при этой же правке. Ударение «ά» в юникоде записывается двояко: U+1F71 (оксия,
блок Greek Extended) и U+03AC (тонос, знак новогреческой монотонии). Канонически они
равны, отображаются одинаково, и NFC сводит первое ко второму.

**Ветхий Завет** (Свит) записан оксией, **Новый** (eBible) — тоносом: 7 930 стихов из
37 805, то есть ровно новозаветная половина. Это не порча — оба вида верны, — но
побайтово они различны, и всякое сравнение без нормализации считает их разными.
Первая правка топаза на этом и споткнулась: `indexOf` не нашёл ничего, а когда нашёл —
вписал в политонический стих чужой знак.

**Приведено к NFC 2026-09-02** ([normalize-bible-unicode.ts](src/scripts/normalize-bible-unicode.ts),
`npm run bible:normalize -- grc-lxx-pat`). NFC — рекомендованная форма обмена (W3C,
UAX #15), в ней держат тексты Perseus и First1KGreek, и знаки «с оксией» в ней просто
не встречаются: они объявлены каноническими дубликатами.

Свернулось 29 708 стихов, **длина не изменилась ни в одном**: один знак заменён одним,
восемь видов — ί, έ, ά, ύ, ό, ή, ώ, ΐ, всего 193 551 знак. **Политоника цела**: гравис
(17 005 стихов), тонкое и густое придыхания (20 743 и 2 052), ипогегрименная (2 773),
циркумфлекс (5 081) остались своими знаками — дубликатов в базовом блоке у них нет.

Проверяется тем, что NFD до и после совпадает до знака: значит текст канонически тот
же, изменилась только запись. Стих, не прошедший проверку, не пишется, и прогон
останавливается.

**Румынское издание не тронуто.** У него не в NFC 33 484 стиха, и все меняют длину:
там NFC не заменяет знак на равный, а СОБИРАЕТ надстрочные знаки с буквой. Это правка
другого рода и другого риска — её задевает разметка ударений, — поэтому скрипт требует
для таких изданий отдельного `--allow-length-change`.

**Поиск не задет.** Проверено: `$text` стоит только на `texts` и `notes`, библейские
стихи не индексируются нигде — ни на сайте, ни в `/api/v2/search`. А общий нормализатор
([churchSlavonic.ts](src/utils/churchSlavonic.ts)) устойчив к этой перемене по
устройству: он делает NFD и снимает комбинирующие знаки, а NFD разлагает оксию и тонос
одинаково. Закреплено тестами в [search.test.ts](src/lib/search.test.ts): одно и то же
греческое слово, записанное двояко, нормализуется в одно.

Правка сделана списком, а не разбором ([fix-swete-typos.ts](src/scripts/fix-swete-typos.ts),
`npm run bible:fix-swete`): каждое исправление названо, объяснено и видно в истории —
так же, как правила приведения и стихи, которых издание не печатает. Поиск идёт с
оглядкой на нормализацию юникода: в базе греческий записан знаками Greek Extended
(«ά» — U+1F71, оксия), а в исходнике скрипта набирается U+03AC; канонически это одно и
то же, побайтово — разное, и обычный `indexOf` не находил ничего.

### Формат и воспроизводимость

JSON Lines под gzip, файл на коллекцию. Не дамп Mongo: тот читается только Mongo и везёт
наружу нашу схему со всеми её случайностями, а строка JSON читается чем угодно. ObjectId
разворачивается в строку, дата — в ISO, **ключи сортируются**.

Выгрузка воспроизводима: дата сборки живёт только в манифесте, внутрь файлов не попадает.
Две сборки на одной базе дали одинаковые sha256 по всем двадцати двум файлам (проверено).
Поэтому обновление сверяется, а не перекачивается вслепую.

`manifest.json` несёт на каждый файл число записей, размер, sha256, снятые поля с причиной
и лицензию слоя. Рядом с файлами каждого слоя — свои LICENSE.txt и README.md.

### Где лежит и что нужно на сервере один раз

Выгрузка кладётся в `/var/www/typikon-data` — **вне** каталога сайта, по той же причине,
по какой там же лежат корпус песнопений и сборки приложения: в каталоге выкладки идут
`git pull`, `npm i` и сборка, и `git clean -fdx` снёс бы двадцать мегабайт молча.

Раздаёт файлы nginx, сайт их не проксирует. Нужен один блок:

```
location /dump/ {
    alias /var/www/typikon-data/;
    autoindex on;
    add_header Access-Control-Allow-Origin *;
}
```

`/dump/`, а не `/data/`: страница `/data` — своя, и location со слешем перехватывал бы
всё под ней. Значения по умолчанию в коде (`DUMP_DIR=/var/www/typikon-data`,
`DUMP_URL=/dump`) — уже продовые, править окружение на сервере не нужно.

Приём на сервере ([data-remote.sh](data-remote.sh)) раскладывает архив во временный
каталог и переносит на место одним движением: распаковка поверх живого каталога дала бы
несколько секунд, когда манифест уже новый, а половина файлов ещё старая, — и скачавший в
эту секунду получил бы выгрузку, не сходящуюся с собственными суммами.

**На прод ничего не выкладывалось**: скрипты написаны и проверены на синтаксис, запуск за
владельцем.

### Проверено

Сборка дважды на одной базе — 23 файла, суммы совпали. В файле греческого Ветхого Завета
нет ни одного новозаветного стиха, и 29 847 + 7 958 сходятся с 37 805. В выгрузке нет ни одного снятого
поля (проверено поиском по распакованным файлам). Страница `/data` собрана и прочитана
целиком: слои, лицензии, таблицы файлов с суммами, список исключённого с причинами.
Тестов на саму выгрузку — 22: разбор по правам (в том числе «коллекция не может быть и
выложенной, и исключённой», «у файла со своей лицензией есть и указание источника, и её
полный текст»), приведение документа и показ чисел. Весь набор проекта зелёный. `tsc --noEmit` — 149 своих ошибок,
как и до работы.

### Не сделано

- Выгрузка не выложена на сервер и nginx не настроен — за владельцем.
- Нет постоянного адреса версии: `/dump/manifest.json` всегда последний, прежних сборок
  не остаётся. Для ссылки в научной работе нужен `/dump/2026-09-02/`.
- Не объявлено наружу: записи в ленте новостей нет, в robots.txt обходчикам про выгрузку
  не сказано.
- Каталог храмов отдаётся целиком, без отдельного файла на страну.

## Напевы: ноты под песнопением (сделано 2026-09-02)

Под текстом стихиры выводится напев — крюками или линейными нотами, с выбором
традиции и местного извода. Разделы: `src/lib/tunes`, данные в
`src/data/tunes` (там же README с форматом), показ на `/chants/[id]`.

### Страница песнопения появилась только теперь

Чтобы положить ноты ПОД стихиру, стихиру надо сперва показать целиком, а до сих
пор её нигде целиком не показывали: поиск отдаёт фрагмент (`snippet` из FTS5),
устав — строку последования. Отсюда `/chants/[id]` и `getChant()` в
`@/lib/chants`: полный текст, подпись места, разрешённые ссылки (книга печатает
ирмос зачином — текст берётся из Ирмология, как в `/canons/[id]`).

### Три сущности, намеренно не слитые в одну

**Традиция** — знаменный распев малый, обиход партесный. Несёт свои голоса и
нотации: партесное многоголосие крюками не пишется, и предлагать для него
крюковую запись было бы обманом.

**Напев** — мелодия, адресуемая селектором: `{глас, жанр}` либо `{подобен, глас}`,
плюс необязательный **извод** (валаамский, киевский). Извод — уточнение, а не
отдельная традиция: местного нет — берётся общий напев ТОЙ ЖЕ традиции.

**Запись** — тот же напев в конкретной нотации. Крюки и ноты — не два напева, а
два письма одного; в партесе к записи добавляется голос.

Ключевое следствие: СТРОЕНИЕ напева (сколько шагов, какой растяжимый, на какой
приходится ударение) лежит на напеве, а не на записи. Иначе крюковая и линейная
записи одной стихиры могли бы разойтись в делении текста на слоги, и читатель
увидел бы два разных деления, не зная, которое верно.

### Все три признака уже были в корпусе

Заводить своё описание песнопения не понадобилось: глас — `groups.tone`, подобен
— `groups.podoben` (5515 групп; «Я́ко до́бля» — 291, «До́ме Евфра́фов» — 268), род —
`content_items.content_unit`. Род берётся как есть, без таблицы соответствий:
второе имя разошлось бы с корпусом на первой же новой книге.

**Подобен сильнее гласа.** Книга назвала подобен — поётся он; гласовый напев это
то, чем поют самогласны. Поставь мы гласовый выше, подобны не звучали бы никогда.

**Подобен без гласа не опознаётся.** «Яви́лся еси́» стоит в корпусе при разных
гласах, и без гласа это разные напевы под одним именем. Зачин сличается
нормализованным (`normalizeChurchSlavonic`): книга печатает его с ударениями и
запятыми — «Гроб Твой, Спа́се».

### Строки, а не «обычная и последняя»

Модель дважды правилась под настоящие данные, и оба раза не по мелочи.

Сперва она знала три рода колена — зачин, обычное, исход — и не выдержала
подобна: «До́ме Евфра́фов» это ПЯТЬ строк, у каждой своя мелодия. `lines` стал
списком.

Потом не выдержала обиходной схемы первого гласа: она печатает порядок строк как
**«‖: 1, 2, 3, 4 :‖ закл.»** — по кругу идут четыре строки, а пятая поётся один
раз в конце.

И наконец не выдержала третьего гласа тропарного: **«1, 3, ‖: 1, 2, 3 :‖ закл.»**
— строки идут НЕ ПОДРЯД, первая поётся и зачином, и в круге. Никаким
промежутком такое не выразить, а выписать строки подряд значило бы держать две
копии первой, расходящиеся при первой правке.

Поэтому порядок задаётся тремя списками НОМЕРОВ — `order: {head, cycle, tail}`, —
ровно так, как книга его и печатает. Пустой круг означает напев фиксированной
длины: так устроен подобен, и расхождение с текстом показывается, а не
сглаживается.

### Раскладка: распевные группы

Колено делится на РАСПЕВНЫЕ ГРУППЫ — обиход помечает их начала стрелками. Каждая
группа садится на своё ударение, а ЧИТОК внутри группы (одна нота, помеченная в
обиходе штрихом) принимает всё, что осталось. `stress` поэтому не «да/нет», а
`"first"` или `"last"` — с какого конца группа ищет своё ударение.

Групп в колене бывает до двух, и оба случая настоящие:

- «и вос-кре́сша из ме́ртвых» (глас 1, строка 3) — предраспев «и вос», распев на
  «кре́с», читок «ша из», распев на «ме́рт», заударное «вых»;
- «и подаде мирови ве́лию ми́лость» (глас 3, заключительное) — читок «и подаде
  мирови», остановка на «ве́лию», конечный распев на «ми́лость». Обе группы ищут
  ударение справа и садятся на два последних, а не спорят за одно.

Отдельной пометки для группы в данных нет: группу начинает сам шаг с распевом.
Правило выведено из книг, а не придумано, и все три разобранных колена ложатся
на него без натяжек; отдельная пометка была бы четвёртым способом сказать то же
самое и разошлась бы с распевами при первой правке.

Отрезок держится за свой распев и растягивается в ту сторону, где стоит читок.
Концы отрезков берутся от начала следующего, а не считаются отдельно: колено
делится нацело, и всякий зазор означал бы молча потерянный слог (есть тест на
четырёх длинах текста).

**Распев не садится туда, где напеву не хватит места.** «Пе́рвенец ме́ртвых
бы́сть» кончается ударным односложным словом, и распев, севший на последнее
ударение вообще, отнял бы слог у исхода. Книга поёт его на «ме́ртвых» — то есть
на последнем ударении, ПОСЛЕ которого напев ещё умещается. Требование это
предпочтение, а не запрет: у «возопи́м» другого ударения нет вовсе, и распев
садится на единственное, а лишние шаги остаются непропетыми.

### Первый настоящий напев: глас 3 тропарный

`obihod-msk/tone-3/troparion` — четырёхголосный обиход московской традиции
(греческий распев). Ноты сняты с партитуры Sibelius, экспортированной в
MusicXML; сама партитура с китайским текстом, и это оказалось неважно.

**Строки опознались по нотам, независимо от подписи книги.** Такты 1, 3 и 6
несут один остов сопрано, 2 и 5 другой, 4 и 7 третий, 8 свой — то есть
`1, 3, ‖: 1, 2, 3 :‖ закл.` подтверждается самой музыкой. Читок виден в файле
прямо: в такте 3 стоит целая нота на восемь долей, и под ней семь слогов подряд.

Чего из файла взять НЕЛЬЗЯ — раскладку по слогам: китайский текст ложится в тот
же распев, но не определяет его (в такте 3 двухнотный распев расщеплён на два
слога, потому что китайскому понадобился лишний). Раскладка снята со схемы и
подтекстовки тропаря и проверена на трёх разных коленах первой строки —
«Небе́сная», «держа́ву», «ме́ртвых»: распев везде сел на то же ударение, что и в
книге.

### Где сверять: раздел «Напевы»

`/tunes` и `/tunes/[id]` — служебный раздел для того, кто напевы вводит. Корпус
для сверки не годится: колена он размечает не везде, и того самого песнопения,
под которым напечатана схема, в нём может не оказаться размеченным вовсе — так и
вышло с тропарём третьего гласа (`/chants/2478`). Поэтому у напева есть
`sample` — образцовый текст с коленами, как их печатает книга.

Страница показывает не только ноты, но и РАСКЛАДКУ: какой слог каким шагом
поётся, читок серым, распев тёмно-красным. Ошибиться при снятии можно двояко — в
самих нотах и в том, куда они сели; первое видно на стане, второе только в
таблице.

### Варианты строк — третий род различия

Обиход помечает вертикальными стрелками варианты первой и четвёртой строк и
оговаривает, что оба равно распространены в московской традиции. Это ни
традиция (кто поёт), ни извод (где поют), а «как из двух принятых чтений спеть в
этот раз». Вариант заменяет ОДНУ строку и лежит отдельным списком `variants`:
вторым напевом его не сделать, иначе общие строки пришлось бы дублировать и они
разошлись бы при первой правке.

Ударения НЕ ищутся в словаре: текст корпуса уже размечен книгой, и снимать
разметку, чтобы восстановить её словарём, значило бы заменить свидетельство
догадкой. `@/lib/accents/core` даёт готовые `isVowel`, `isAccent`,
`unfoldPrecomposed` — вросшая вария (ѐ, ѝ) тоже ударение.

Слоги делятся по правилу открытого слога с поправкой на сонорные (Аванесов):
«Го-спо-ди», «у-слы-ши», но «се́рд-це», «со́лн-це», «ца́р-ствїе» — «рдц» и «лнц» в
начале слога не произносятся. Морфологии правило не знает: «пи-та́-ю-щи-хся», а
не «щих-ся». Для распева это безразлично — нот всё равно столько же.

### Нотации

**Крюки — текст, а не картинка.** Знамённая нотация есть в Юникоде (блок
U+1CF00–U+1CFCF, версия 14.0), и знамя — такой же символ, как буква: копируется,
ищется, ложится в базу. Своего шрифта не кладём: крюковые шрифты
распространяются каждый на своих условиях. Без шрифта строка осыплется в пустые
прямоугольники, поэтому страница говорит об этом словами.

**Линейная запись — ABC, рисует `abcjs`.** ABC выбран за то, что он ТЕКСТ: напев
остаётся строкой, которую можно сверить глазами, положить в тест и сравнить в
git. Размера у распева нет (`M:none`) — обиход поётся по тексту, а не по тактам.
Партес идёт двумя станами (`%%score {(V1 V2) (V3 V4)}`), как его и печатает
обиход: дискант с альтом на скрипичном, тенор с басом на басовом; подтекстовку
несёт нижний голос каждого стана. `abcjs` грузится динамически — иначе нотный
движок попадал бы в бандл ко всем страницам сайта.

Третьей нотацией (невмы) напрашивается Verovio: он умеет модуль MEI Neume и
кладётся туда же, в реестр нотаций, не ломая ни раскладку, ни данные.

### Колена размечены не везде

Раскладка держится на коленах, а корпус несёт их косой чертой лишь у 15 081
стихиры из 19 550 — у 4469 (23%) разметки нет. Запасной разбор по пунктуации
книге не равен: на «Пло́тию во́лею…» (item 14) он даёт восемь колен вместо семи,
потому что книга держит «утверди́ Правосла́вием Це́рковь Твою́, Христе́,» одним
коленом, а запятая перед «Христе́» рвёт его надвое — и порядок строк после этого
съезжает целиком. Запятая колена не кончает; кончает только черта или звёздочка.

### Что осталось

Мелодии в `src/data/tunes` — заготовки: строение выверено по корпусу, сами
напевы нужно сверить с обиходом и заменить. Гласы 2–8 знаменного и жанры сверх
трёх у партеса не заведены вовсе; страница в таком случае говорит прямо, каким
глас-подобен-род искала и не нашла.

Прослушивание (`abcjs` умеет синтез) не сделано намеренно: пока в данных
заготовки, звучать им нечем.

## Румынская синодальная 1914: подложка к кириллице (сделано 2026-09-02)

Румынская кириллица 1688 года — наш собственный набор со сканов, и читать её умеет не
всякий, кто читает по-румынски. Синодальное издание 1914 года — прямая наследница той же
традиции, латиницей; рядом с кириллицей оно встаёт подложкой: видно, что стоит в стихе,
не разбирая полуустава.

**Изданием, а не книгой библиотеки.** Модель для этого и перестраивалась 2026-08-30:
`bible_editions` держит сколько угодно изданий на язык. Заводить Библию книгой значило бы
вернуться к тому, что тогда разобрали и что «текло». Изданием всё нужное приходит само:
колонка рядом, шестое издание в согласовании нумераций, выдача через `/api/v2/bible`.
Карточка в библиотеке при этом заведена — как у церковнославянского и у 1688-го.

**Разведены по НАЧЕРТАНИЮ, а не по языку** — как `cu` и `cu_gr` у церковнославянского.
Код `ro` в [bookLanguages.ts](src/utils/bookLanguages.ts) уже был (пришёл с румынскими
Минеей и Октоихом), так что заводить `ro_lat` не понадобилось — и не следовало: в шапке
файла сказано, что коды обязаны совпадать буква в букву с `languages.py` в typikon-rules.

**Чтения дня не сдвинулись.** У языка `ro` теперь два издания, и «по умолчанию» осталось
за 1688-м. Попутно вскрылось, что общий импортёр ставил `isDefaultForLang: true` жёстко —
пока изданий было по одному на язык, это молчало, а со вторым румынским оба стали «по
умолчанию», и какое возьмут чтения, решал порядок сортировки, то есть случай. Теперь это
говорит сам файл издания.

### Откуда взят текст

[ro.wikisource.org/wiki/Biblia_1914](https://ro.wikisource.org/wiki/Biblia_1914) —
вычитанный людьми текст, CC BY-SA 4.0. **Не** archive.org: там то же издание лежит сырым
Tesseract-OCR, а этот урок был получен часом раньше на греческом, где невычитанная
оцифровка дала около шести тысяч описок.

Привоз — [fetch-romanian-1914.ts](src/scripts/fetch-romanian-1914.ts), дальше общим
импортёром. **80 книг, 36 341 стих**, 191 перенумерован правилами.

### Что поймалось при разборе

- **Заголовки разделов утекали в стих.** Они набраны по центру и стоят МЕЖДУ главами,
  поэтому попадали в кусок, идущий за последним стихом предыдущей главы: Быт. 1:31
  оканчивалось словами «==CAP. 2.== Sfințirea zilei a șaptea». Стих теперь обрывается
  на заголовке главы.
- **Порядок малых пророков у изданий разный.** У 1914-го западный (Иоиль перед Амосом),
  у 1688-го греческий (Амос перед Иоилем). Сопоставление книг по позиции молча положило
  бы текст Иоиля под Амоса — поэтому карта книг составлена по ИМЕНАМ.
- **Молитва Манассии напечатана сплошным текстом**, без нумерации стихов и без якорей
  разметки. Кладётся целиком одним стихом — так, как напечатана, а не дробится по нашему
  усмотрению. Славянская Библия её книгой не держит (только двенадцатой песнью
  библейской), поэтому заведена в приложении канона.
- Три книги, которые славянская держит внутри Даниила — Сусанна, Вил, Песнь трёх
  отроков, — у 1914-го напечатаны с теми же числами стихов, что и у 1688-го (64, 50, 67
  при 33 в третьей главе Даниила). Правила согласования те же, но записаны отдельно:
  издания разные, и совпадение сегодня не обещает совпадения после первой правки.

### Не сделано

- Сверка версификации 1914-го с эталоном не проводилась: правила заведены только
  структурные (три книги Даниила). Где издание расходится с церковнославянским внутри
  глав — предстоит померить, как в своё время мерили 1688-е.
- 1914-й не сделан языком выбора: он виден только в параллельном виде и в библиотеке.
  Если окажется, что читателю нужнее современный румынский, повышение — правка флага.
- Кириллическое издание к NFC по-прежнему не приводится, и это осознанно: там NFC
  собрал бы 112 724 грависа с буквой, а наши инструменты ударений читают их
  комбинирующим знаком.

## Зачины: указатель по первым словам (сделано 2026-09-02)

Раздел `/incipits` — «Зачины» в меню «Собрание». Строить было нечего: таблица
`text_incipits` в корпусе наполнена сборкой (`migrate_text_links.py`) и содержит 226 832
строки, 182 650 различных зачинов на шести языках. Веб к ней не обращался вовсе. Вся
работа — показать.

### Главное, что выяснилось до первой строки кода

`IDEAS.md` называл инципит «ключом отождествления текста между рукописями, изданиями и
традициями». Между изданиями одного языка — да, 44 182 связи `same-text`. **Между языками —
нет: ни один зачин из 182 650 не встречается на двух языках**, и так задумано самой сборкой.
Переводчик переставляет слова, и от греческого зачина в английском не остаётся ни корня
(«Κανόνα πίστεως» → «Christ our God has made you manifest»).

Поэтому раздел устроен на двух разных вещах: сам указатель — на зачине, а соответствия
между языками — на `text_links`, где связь хранится вместе с тем, на чём держится:

| связь | пар | как показываем |
|---|---:|---|
| `translation/edition/certain` | 24 130 | «заявлено изданием», с ключом AGES в подписи |
| `translation/structure/candidate` | 16 641 | «догадка по месту службы», отдельным блоком с предупреждением |

Разделять обязательно. Живая проверка: у места `menaion/m01-02/vespers/tropar/svyatomu#1`
строк поровну и глас совпал, поэтому связаны «Пра́вило ве́ры и о́браз кро́тости» свт. Сильвестру
и «Ἑτοιμάζου Ζαβουλών» предпразднства Богоявления — **разные песнопения**. Свалив их в одну
кучу с заявленным, раздел врал бы. Там же, где связи нет вовсе (славянский связан наружу
лишь на 9,2 % строк), страница говорит это прямо: молчание читатель принял бы за «связи не
бывает», а не за «мы её не построили».

### Решения, стоившие переделки

- **Нормализация запроса ПРОТИВОПОЛОЖНА поиску по песнопениям.** `text_incipits` строится
  через NFD со снятием Mn, то есть сводит «й» к «и» (зачинов с «й» в таблице ноль), а
  `normalizeChantQuery` в [chants.ts](src/lib/chants.ts) «й» намеренно сохраняет — там его не
  разбирает токенизатор FTS5. Возьми мы готовую функцию, «Радуйся» не нашло бы ничего
  никогда; со своей — находит 805 зачинов, записанных как «радуися». Ловушка перевода с
  Python рядом: там `[^\w\s]` оставляет кириллицу, в JavaScript `\w` только ASCII, и та же
  регулярка выкосила бы текст в пустую строку. Обе проверены тестами
  ([incipits.test.ts](src/lib/incipits.test.ts), 11 штук).
- **Диапазон вместо `LIKE 'префикс%'`.** С LIKE план вырождается в скан 122 тысяч строк;
  с `incipit >= ? AND incipit < ? || char(0x10FFFF)` берётся покрывающий индекс. Поиск — 9 мс,
  одна буква со счётом всех 12 982 ключей — 33 мс. Поэтому порога длины запроса здесь нет,
  в отличие от `/chants`: листать указатель с буквы — его собственный способ чтения.
- **Буквенный перечень обходом по индексу, а не `GROUP BY substr()`.** Группировка обязана
  прочитать все ключи языка и на холодном кэше заняла **7,5 секунды прямо на отрисовке**.
  Рекурсивный обход «первый зачин после буквы X» делает столько поисков, сколько букв:
  **15 мс**. Ценой чисел при буквах — посчитать их значит снова прочитать всё.
- **Буквы раскладываются по письменностям, крупные вперёд.** По коду знака латиница и
  греческий стоят в юникоде перед кириллицей, и славянский указатель открывался семью
  латинскими и двумя десятками греческих букв. Не прячем (они в корпусе есть), но ставим
  после своих.
- Списки отборов и алфавит считаются один раз на процесс: файл корпуса подменяется только
  вместе с перезапуском службы.

### Ручки API v2 (сделано 2026-09-02)

Две: `GET /api/v2/incipits?q=` — сам указатель, и
`GET /api/v2/incipits/{язык}/{зачин}` — резолвер, ради которого указатель и выносится
наружу. Ключ в адресе резолвера — сам зачин, как он лежит в корпусе; своего
идентификатора у зачина нет и не нужно, ключ и есть идентификатор, притом читаемый.
Раздел доступа — существующий `search` (ручки идут по всему корпусу), нового значения
в `SCOPES` не заводили.

Три решения, которые стоит помнить:

- **Указатель целиком ручка не отдаёт.** Пустой `q` отвергается с объяснением: перебор
  всех 182 650 ключей стоит 1,1 секунды на запрос, и открытой ручке этого делать нельзя.
  Кому нужен указатель целиком — выгрузка корпуса на `/data`, она для того и есть.
  Нормализация идёт ДО проверки на пустоту, иначе строка из одних знаков препинания
  попадала бы в «отдай всё».
- **`method` и `confidence` уходят наружу, а не сворачиваются в флаг «перевод».** Клиент,
  которому связь нужна для сличения, обязан видеть разницу между заявленным издателем и
  нашей догадкой; спрятав её, мы переложили бы свою неуверенность на чужой продукт молча.
  Ответ разделён на `correspondences.declared` и `correspondences.supposed`, у каждой
  связи есть `evidence` словами.
- **Перечень ручек в `/api/v2` не знал о песнопениях** — `chants` там не значился с самого
  начала, хотя ручка есть и работает. Дописан заодно.

Документация: раздел «Песнопения и зачины» на `/api` (его тоже не было — `chants` нигде
не был описан для человека), пути и схемы в `openapi.json`.

Проверено: без ключа `401`, пустой и мусорный `q` — `400` с объяснением, неизвестный язык —
`400`, несуществующий зачин — `404`, битая экранировка ключа — `400`, а не пятисотка.
Ссылки в `openapi.json` не висят в пустоту.

### Инвентаризация 2026-09-02: что построено и не показано

Свод по двум репозиториям с числами, снятыми запросами к `data.db`, Mongo и `nobles.db`
в тот же день, а не взятыми из этого файла. Вывод один и он неприятный: **собранного
заметно больше, чем показано читателю**. Несколько крупных таблиц наполнены и не имеют
наружу ни одной страницы.

Самый яркий случай — инципитарий. В `IDEAS.md` соседнего репозитория он числился
направлением, «которого мы ещё не касались», а на деле лежит таблицей `text_incipits`:
226 832 строки, 182 650 различных зачинов по шести языкам, с индексом, по которому
префиксный поиск бесплатен. Построен попутно, как рабочий ключ внутри сборки. Отсюда
приём, который стоит применять и к остальным замыслам: **прежде чем оценивать
направление, проверять, не собрано ли оно уже побочно**. Раздел «Зачины» делается
первым именно поэтому — он не строится, а публикуется.

Ниже — направления, каждое с указанием готовых данных под ним. Ни одно не требует
собирать что-то новое.

**Соединить то, что уже связано.**

- **Досье святого.** Пять разделов знают об одном лице и не показывают этого вместе:
  памяти в календаре со знаком службы, тексты службы, акафист, упоминания в житиях и
  Прологе, храмы с этим посвящением на карте, а для князей — правление из родословной
  и дата по хронологическому решателю. 837 святых, 1 519 памятей, 303 связки
  «акафист ↔ святой», 37 494 храма с престолами, 574 персоны родословной — и всё это
  уже связано идентификаторами. Ни одной новой строки данных. Побочно выходит аудит
  связности: где страница окажется пустой, там связь на самом деле не проставлена.
- **Где рядом сегодня служба.** Каждый приход публикует расписание в пустоту — на своей
  странице, для тех, кто уже знает адрес. У нас 64 854 храма с координатами в 125
  странах и готовый механизм приходского расписания с часовыми поясами. Агрегатор
  ближайших служб на сегодня — карта, поиск и подписка; такого нет ни у кого. Он же
  превращает приходскую функцию из одолжения настоятелю в причину вести расписание
  именно здесь.
- **Диффузия почитания на карте.** География посвящений сделана статичной. У 8 555
  храмов проставлен год постройки — этого хватает, чтобы провернуть карту по столетиям
  и увидеть, как расходится почитание святого: где появляется, как быстро расходится,
  где ареал кончается. Ось времени превращает витрину в наблюдение.

**Личный слой — самая широкая аудитория.**

- **Уставный план чтения Библии.** «Прочитать Новый Завет вместе с Церковью за год» —
  по рядовым зачалам, с отступкой и преступкой, а не по произвольной раскладке из
  приложений. Эта арифметика у нас посчитана верно, и на ней стоит продукт с аудиторией
  на порядки шире уставщиков: прогресс, продолжение с места остановки, офлайн,
  напоминание. 785 зачал, 1 067 перикоп, 192 106 стихов в шести изданиях; слой
  избранного и заметок уже есть, прогресс ложится туда же. Пока такой вещи нет,
  «доступность чтений» остаётся заявленным фокусом без массового следствия.
- **Отметка «был на службе».** Одна кнопка в календаре. Читателю — свой год как
  история, а не лента; проекту — первые цифры о фактической практике: где служат
  будничную утреню, в каких приходах есть вечернее богослужение. Социология
  богослужения из `IDEAS.md` требовала опроса и доверия; эта статистика набирается

**Клирос.**

- **Синхронная листалка последования.** Разные сборки из одних данных задумывались как

### Озвучка чтений (TTS) — разобрано 2026-08-24

**Что проверено по данным.** Русских текстов в базе нет вообще: 0 документов с современно-русской
лексикой. Корпус целиком церковнославянский — 2925 текстов в гражданской орфографии
(«На стра́жи мое́й ста́ну») и 305 в собственно ЦС-графике (с ѣ, ꙋ, ѧ, титлами). У 1874 текстов есть
`ruLink`, но это внешняя ссылка (azbyka.ru), а не наш контент. Поэтому вариант «начать с русских
текстов», который стоял в блоке 3 аудита, недоступен — посылка была неверной.

**Что это компенсирует.** У 2142 текстов из 3230 уже расставлены ударения. Для русского синтеза
ударение — главная нерешённая проблема, а на церковнославянской лексике («зело́», «усмотри́х»,
«о́блацех») движок ошибался бы почти в каждом втором слове. Формат, который ждут и Яндекс, и Silero
(`+` перед ударной гласной), получается из наших данных одной заменой:

```
/([аеёиоуыэюяАЕЁИОУЫЭЮЯ])́/g  →  "+$1"      «На стра́жи мое́й» → «На стр+ажи мо+ей»
```

Из 1 055 167 знаков ударения 144 235 стоят не после русской гласной, но 133 397 из них — в текстах
ЦС-графики (после ѣ, ꙋ, ѧ, ѡ, і, ѵ). То есть для гражданского корпуса преобразование чистое, а
305 ЦС-текстов всё равно требуют предварительной транслитерации в гражданку — она полезна и сама
по себе, поиск по ним сейчас тоже не работает.

**Что доступно с сервера** (проверка 2026-08-24, [check-tts-endpoints.sh](check-tts-endpoints.sh)):
доступно **всё, кроме Telegram**. Яндекс SpeechKit отвечает за 50–90 мс (`tts.api.cloud.yandex.net`
— HTTP 401 без ключа, то есть хост живой), Object Storage и IAM тоже. Сбер и T-Bank доступны, но их
цепочка идёт от корневого центра Минцифры — нужен корневой сертификат на сервере. Хосты офлайн-моделей
(Silero, HuggingFace, GitHub releases, PyPI) доступны, значит офлайн-путь тоже открыт.

Это снимает аргумент, которым я отговаривал от облачного синтеза: блокировка Telegram оказалась
точечной, а не общим ограничением исходящего трафика, и переносить её на другие API было неверно.

**Два открытых пути, оба рабочие:**
- **Яндекс SpeechKit** — лучшее качество русского голоса, понимает `+`-ударения из коробки, платно
  по символам (корпус — 12,7 млн символов, разово; при пререндере повторно платить не за что).
  Требует облачного аккаунта, сервисного аккаунта и биллинга.
- **Silero офлайн** — бесплатно, на CPU, русские голоса, те же `+`-ударения, никакой внешней
  зависимости в рантайме. Качество ниже яндексового; нужен Python и место под модель.

**Как это ложится в архитектуру.** В обоих случаях правильная схема — не синтез на лету, а пререндер:
скрипт в `src/scripts` генерирует mp3 на текст, файлы раздаёт nginx (как сейчас раздаются APK),
перегенерация — в тот же момент, когда админка сбрасывает кэш после правки (`/api/revalidate`).
На чтении — нулевая задержка и нулевая стоимость, файл кладётся в офлайн-кэш PWA. Масштаб: 2276
готовых текстов, 12,7 млн символов ≈ 235 часов звука ≈ 3–7 ГБ mp3; медианный текст — около двух минут.

**Следующий шаг — не код, а пилот.** Главный риск не технический: синтетический голос на
богослужебном тексте может оказаться неприемлем для части аудитории, и «почти правильно» здесь хуже,
чем никак. Озвучить 5–10 представительных текстов (синаксарь, житие, текст с плотной ЦС-лексикой,
плюс обязательно один без проставленных ударений — чтобы услышать разницу и понять, что даёт работа
над словарём ударений) и дать послушать тем, для кого это делается. Выбор движка имеет смысл делать
после этого ответа, а не до.

### Родословная (`nobles`) — направление развития с 2026-08-24

Выведена из-под статуса эксперимента: модуль развиваем наравне с чтениями, фичи вокруг него
предлагать можно. Что уже есть в коде: импорт из Wikidata
(`npm run nobles:import-wikidata`, `nobles:import-wikidata-rules`), связывание со святцами
dneslov (`nobles:link-dneslov`), поиск дубликатов (`nobles:find-duplicates`), разбор импортных
батчей в `/admin/nobles/import/[batchId]`, публичные страницы персон, семей, государств и правлений,
дерево на `family-chart`, FTS-поиск по SQLite.

Ближайшее, что вытекает из состояния кода (приоритеты за владельцем продукта):
- Довести импорт из Wikidata и дедупликацию до регулярного процесса — сейчас это разовые прогоны
  с ручным разбором в админке.
- Типы: большая часть накопленных ошибок `tsc` (`unknown` из `better-sqlite3.all()`) — именно в этом
  модуле, см. блок 5 аудита.
- Решить вопрос репозитория. Он не снимается тем, что модуль стал направлением: 129 файлов из ~494
  и отдельная база SQLite в общем продукте — это либо осознанный выбор «два направления в одном
  репозитории», либо кандидат на вынос в отдельный сервис/поддомен. Связь с основной базой идёт
  только через `dneslovId`, отделяется относительно чисто.

## Автопостинг в Telegram/VK (@blagoslovie) — написан 2026-08-13, ОТЛОЖЕН 2026-08-24

> **Статус: отложено.** С прод-сервера `api.telegram.org` недоступен, `curl` тоже не проходит.
> Проверка 2026-08-24 ([check-tts-endpoints.sh](check-tts-endpoints.sh)) показала, что блокировка
> **точечная, именно на Telegram**: всё остальное с сервера доступно — Яндекс, Сбер, даже OpenAI,
> ElevenLabs и Google. То есть дело не в общем ограничении исходящего трафика. Обходы написаны
> (релей на Cloudflare Workers, поддержка прокси), но заводить и обслуживать ещё один внешний узел
> ради этого сейчас не хотим.
> Возвращаемся к вопросу, скорее всего, после переезда прода на другой сервер — если оттуда
> Telegram доступен напрямую, направление включается почти без работы: код готов, нужны только
> `TELEGRAM_CHANNEL_ID`, два крона и прогон на реальных данных.
>
> Пока отложено, направление «доведение до пользователя» лучше двигать через iCal-фид и PWA —
> они не зависят от доступности внешнего API с сервера.

Первая реализация направления "Доведение до пользователя". Публикует проложные чтения (`song6`)
в Telegram-канал `@blagoslovie` по формату, который уже используется в канале.

**Схема:**
1. `npm run channel-posts:generate` (cron, ежедневно) — берёт `song6.items` дня (эндпоинт
   `/api/v1/days/{month}-{DD}`), при 1 памяти — один черновик на 9:00, при 2+ — первые две,
   вечерняя (18:00 накануне) и утренняя (9:00). Фото и название памяти (для хэштега) — через
   `dneslovId` текста и внешнее API dneslov.org (уже используется сайтом в `/saints/[id]`,
   `DneslovImages`), при отсутствии `dneslovId` — эвристика по родительному падежу
   (`src/scripts/lib/heroName.ts`, помечается `nameSource: "heuristic"` для проверки в админке).
   Черновики пишутся в новую коллекцию Mongo `channelPosts`, статус `draft`.
2. `/admin/channel-posts` — ревью черновиков: правка текста/фото/хэштегов, кнопка
   "Готово к отправке" → статус `ready`. Без подтверждения пост не публикуется.
3. `npm run channel-posts:publish` (cron, 9:00 и 18:00) — публикует всё `ready` с наступившим
   `scheduledAt` в Telegram (`sendPhoto`/`sendMessage`, обычный Bot API — без личной MTProto-сессии,
   стабильнее). VK — заглушка (`publishToVk` в `publish-channel-posts.ts`), пайплайн уже готов
   принять реальный вызов.

Скрипты — TypeScript, запускаются через `tsx` (добавлен в devDependencies). Переменные окружения
подгружают сами через `@next/env` (`src/scripts/lib/env.ts`) — тот же механизм, что у `next dev`/
`next start`, вручную `.env.production` не нужно ни экспортировать, ни передавать флагами.

**Почему VK — заглушка:** канал `@blagoslovie` в VK создан как тип "Канал", а API для этого типа
сообществ сейчас в закрытой альфе VK (не общедоступно, не зависит от настроек прав). Рабочий путь —
`wall.post` в классическую Группу/Паблик; решение, заводить ли отдельное сообщество под автопостинг
или ждать открытия API каналов, ещё не принято.

**Нужно для запуска на сервере:**
- `TELEGRAM_CHANNEL_ID` в `.env.production` (бот должен быть админом канала с правом публикации);
  `TELEGRAM_BOT_TOKEN` уже есть.
- Два крона: генератор раз в день, паблишер в 9:00 и 18:00.

**Если api.telegram.org недоступен напрямую** (проверено — блокировка на уровне хостера/региона,
`curl https://api.telegram.org` с сервера тоже не проходит) — два обхода, включаются через
`.env.production`, код уже готов ([src/lib/channelPosts/telegram.ts](src/lib/channelPosts/telegram.ts)):
- `TELEGRAM_API_BASE=https://<worker>.workers.dev` — свой бесплатный релей на Cloudflare Workers,
  код и инструкция по деплою в [telegram-relay/worker.js](telegram-relay/worker.js) (просто
  прозрачно перекладывает запрос на api.telegram.org, токен в воркере не хранится).
- `TELEGRAM_PROXY_URL=http://user:pass@host:port` — если уже есть HTTP/SOCKS5-прокси.

**Не проверено на реальных данных** — вся логика прогнана на моках (мок-ответы dneslov.org,
без обращения к прод-базе). Перед первым запуском стоит проверить `channel-posts:generate`
на нескольких настоящих днях и просмотреть черновики в `/admin/channel-posts` до включения крона публикации.

### Настройка крона

Редактируется командой (у пользователя `admin`, под которым крутится сам сайт — см. `typikon-web.service`):
```bash
crontab -e
```

В начало файла — `PATH`, иначе cron не найдёт `npm`/`node` из nvm (тот же путь, что и в systemd-юните):
```
PATH=/home/admin/.nvm/versions/node/v20.20.2/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

Дальше сами задания:
```
0 3 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:generate 2>&1 | logger -t channel-posts-gen
0 9,18 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:publish 2>&1 | logger -t channel-posts-pub
```
`.env.production` подгружать вручную не нужно — скрипты делают это сами через `@next/env`
(`src/scripts/lib/env.ts`), важен только `cd` в корень репозитория, где лежит `.env.production`.

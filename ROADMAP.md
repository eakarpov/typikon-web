  просто получается крупнее, чем нужно. Чинить не сейчас; если возьмёмся — скорее всего проще
  нормализовать сам `content` в БД (заменить `"\n \n"` → `"\n\n"` при импорте/миграцией), чем менять
  паттерн split на regex сразу в двух местах на разных платформах.

### Блок 1. Дешёвые победы

- **`<html lang="en">`** в [src/app/layout.tsx](src/app/layout.tsx) на русско-церковнославянском

  не попадают вообще. Для контентного сайта на ~3200 страниц это самая дешёвая органика,
  которую мы не берём. Заменить на `src/app/sitemap.ts`, строящий карту из Mongo по реальным

- **Поиск отдаёт всё и без ограничений** — [src/app/search/api.ts](src/app/search/api.ts)

  возвращает все совпавшие тексты целиком, вместе с полем `content` (тысячи символов на
  документ). UI при этом использует только `id` и `name`. Плюс rate limiting отсутствует —
  вместе это простой способ положить сервер.
- **Утечка sqlite-хендлов** — `init()` из [src/lib/sqlite.ts](src/lib/sqlite.ts) создаёт новый
  `Database` при каждом вызове (58 вызовов по коду), `db.close()` встречается один раз. В
  long-running процессе файловые дескрипторы копятся. Нужен синглтон на процесс.
- **`ignoreBuildErrors: true`** в [next.config.js](next.config.js) — типы в проде не проверяются
  вообще, при 247 `: any` по коду. Замер на 2026-08-24: `npx tsc --noEmit` даёт **171 ошибку**,
  большая часть — `unknown` из `better-sqlite3.all()` в модуле `nobles`. Снимать флаг можно только
  после разбора этой кучи, но знать её размер полезно уже сейчас.

### Блок 2. Архитектурный рычаг: сайт целиком динамический

Корневой [layout.tsx](src/app/layout.tsx) вызывает `verifySession()` и `getItem()` — это
заставляет Next рендерить **каждую** страницу динамически. Ни одной `revalidate` или
`generateStaticParams` в проекте нет (проверено, ноль вхождений): страница жития XII века ходит
в Mongo при каждом заходе анонима.

Что делать: вынести сессию из корневого layout (клиентский компонент или отдельный сегмент),
контентные маршруты — `/reading/[id]`, `/saints/[id]`, `/months/[id]`, `/library/[id]` — перевести
на ISR, инвалидация по хуку из админки при сохранении текста. Это самая крупная разовая выгода по
скорости и нагрузке, и она же делает осмысленным офлайн-кэш в PWA.

Рядом: **шрифты**. `public/fonts` — 1.2 МБ OTF, из них `myFont` тянет ~450 КБ (Regular + Bold)
до первой отрисовки текста на каждой странице чтения. Конвертация в woff2 даёт примерно двукратное
сокращение без потерь; сабсеттинг — больше, но аккуратно, чтобы не потерять церковнославянские
надстрочные знаки.

### Статус блока 2 — сделано 2026-08-24 (шрифты не трогали)

**Сессия убрана из рендера.** Корневой [layout.tsx](src/app/layout.tsx) больше не вызывает
`verifySession()`/`getItem()`; сессию забирает [SessionLoader](src/app/SessionLoader.tsx) с клиента
через новый `GET /api/session` и кладёт в тот же redux-стор, из которого меню читало её и раньше.
В `auth`-слайс добавлен флаг `isResolved` — без него у залогиненных на мгновение мигала кнопка
«Войти». `SessionChecker`/`SessionDispatcher` удалены как дублирующие. Важно: `SessionLoader` должен
лежать **внутри** `StoreProvider` — иначе react-redux падает уже на этапе пререндера.

**Что теперь кэшируется.** Пререндеренных маршрутов стало 19 против 2 (`/`, `/library`, `/calendar`,
`/triodion`, `/penticostarion`, `/rest-readings`, `/commons`, статические разделы). `/months/[id]` и
`/library/[id]` — ISR по первому запросу (`MISS` → `HIT`, проверено заголовком `x-nextjs-cache`).

Отдельная находка: **`export const revalidate` для динамического сегмента не работает без
`generateStaticParams`** — Next считает такой сегмент полностью динамическим и результат не кэширует
вовсе. Пустой массив (`generateStaticParams = async () => []`) включает генерацию по первому запросу
с последующим кэшированием, при этом сборка не тратит время на 2500 страниц.

**Выборки из базы кэшируются отдельно** ([src/lib/cache.ts](src/lib/cache.ts), `unstable_cache` с
тегами). Это то, что спасает страницы, которые остаются динамическими: `/reading/[id]` из-за
`?range`, а `/calendar/[id]`, `/weeks/[id]`, `/triodion/[id]`, `/calculator/[date]` — из-за cookie
языка Библии. Замеры на продовой сборке, первый запрос → последующие:

| маршрут | было | стало |
|---|---|---|
| `/calendar/march-30` | 271 мс | 23 мс |
| `/triodion/post-5-vt` | 435 мс | 33 мс |
| `/reading/dobrotolubie-30` | 78 мс | 18 мс |

Ошибки в кэш не попадают: `cachedTuple` пробрасывает их наружу, иначе сбой базы залипал бы на час.

**Инвалидация.** `POST /api/revalidate` (только админ, в проде без прав — 404) сбрасывает теги;
редакторы текстов и дней в админке дёргают его после сохранения
([src/lib/admin/revalidate.ts](src/lib/admin/revalidate.ts)). Отдельная ручка нужна потому, что API
админки живёт в pages-роутере, а `revalidateTag` работает только в app-роутере. Страховка по времени —
час для контента, 5 минут для главной (на ней церковная дата и список последних правок).

**Проверено:** тексты страниц продовой сборки сравнены с версией до изменений — на 14 маршрутах всех
типов единственное расхождение в том, что раньше в HTML попадал `Loading...` из Suspense, а теперь
контент отрендерен сразу. 32 адреса из карты сайта отдают 200. `tsc --noEmit` — 170 ошибок против
171 до начала работы, новых нет.

Что осталось за рамками:
- `/saints/[id]` не трогал — в файлах этого раздела лежит незакоммиченная работа по `nobles`.
- Инвалидация подвешена только на редакторы текстов и дней; книги, месяцы и недели правятся реже —
  их подхватит часовой таймаут.
- `CountMeta` на каждый просмотр страницы пишет в Mongo IP, URL и растущий массив `wasAt`
  ([src/app/api.ts](src/app/api.ts), `writeMetaData`). Рендер это не блокирует (запрос уходит с клиента
  после отрисовки), но документ на популярный URL растёт без ограничений, а собирать IP-адреса — это
  ещё и персональные данные. Стоит решить отдельно: ограничить массив или считать агрегатом.

### Блок 4. Что нужно решить, а не откладывать: `nobles` — РЕШЕНО 2026-08-24

129 файлов из ~494 в `src` относятся к родословной. При этом модуль был объявлен экспериментальным
и «не развиваем» — а последний коммит, незакоммиченные изменения в рабочем дереве и четыре новых

развития. Расхождение снято в сторону признания второго направления. Вопрос отдельного
репозитория/поддомена остаётся открытым — см. раздел «Родословная (`nobles`)» ниже.

### Markdown на странице чтения (флаг `newUi`) — сделано 2026-08-27

Флаг `newUi` («Новый UI (Markdown)») был заведён давно, но жил только в админском
редакторе: страница чтения о нём не знала, и стоял он у 1 текста из 3327. Теперь
[ReadingContent](src/app/reading/[id]/ReadingContent.tsx) при `newUi` рендерит абзац
через `react-markdown`.

Разделение обязанностей: **markdown отвечает за начертание** (жирный, курсив),
**наши метки — за доменное** (`{N}` в массив сносок, `{st|}`/`{pl|}`, `{p|}` колонтитул,
`{a|}` якорь). Markdown таких понятий не выражает, и remark-плагин на каждую метку был бы
тем же велосипедом в другой обёртке. Поэтому строковые куски, которые markdown отдаёт
внутрь своих узлов, прогоняются через ту же пару `renderMarkup` + подсветка заметок,
что и обычные абзацы.

Что сохранено намеренно: абзац остаётся **нашим** контейнером с `data-paragraph-index`
(по нему работают пословное выделение, «сообщить об ошибке» и заметки), а markdown-абзац
рендерится фрагментом — вложенного `<p>` не возникает. Нумерация абзацев прежняя,
`content.split("\n\n")`, так что сохранённые заметки не поедут. Момент выбран удачно:
пользовательских заметок сейчас 0, публичных примечаний 2.

**Выделение в церковнославянских текстах — рубрикацией, а не начертанием.** У шрифта
Monomakh одно начертание, жирного и курсива в нём нет, браузер рисует их синтетически и
почти неразличимо. Поэтому при `csSource` `**жирный**` выводится киноварью, `*курсив*` —
приглушённым цветом, как рубрики в самих богослужебных книгах.

Первым текстом на markdown переведён **Алфавитный указатель**: 465 заголовков статей
(`%(…%)` → `**…**`) и 100 подрубрик (`%[…%]` → `*…*`). Ифику и Правила не трогали —
у них в оригинале 0 и 1 выделение соответственно, переводить нечего.

Попутно: во всех заменах `renderMarkup` проставлены React-ключи (раньше их не было,
и консоль ругалась на `FootnoteLink`).

**Нарезан по буквам — 2026-08-27.** Профиль `ukazatel` в `split-book`: раздел открывает
абзац из одной буквы с точкой. Вышло **27 разделов** (`pravila-ukazatel-1…27`, названия
«Указатель: А» и так далее), прежний адрес `/reading/alfavit-duhovny-1` стал их оглавлением.
Медиана раздела около 3 тыс. знаков, самый крупный — «С» на 21,5 тыс.

Разделов 27, а не 26: буква «Є» встречается дважды. Первый блок — Е (Евагрій, Евангеліе),
второй, стоящий между Ч и Ѳ, — это Э (Економъ, Епітімія), в церковнославянской печати
оба набраны через Є. Названия оставлены как в книге; если нужно различать в списке,
переименовать — одна правка в базе. Там же «Оꙋ» — это У.

Попутно чинилось: нарезчик не переносил в новые тексты `newUi` и `contentType`,

### Чистка HIP и нарезка на главы — сделано 2026-08-27

**Что оказалось на самом деле.** Тексты были не просто «не разбиты», а залиты с orthlib
в сыром формате HIP: читатель видел маркеры разрыва строк `//` (6951 штука в Ифике),
колонтитулы `(л. а҃)`, сноски в фигурных скобках, переключатели `<::рꙋс>`, шапку OCR.
Сырую разметку несли ровно четыре текста базы — Ифика, «Алфавит» и два текста Книги
правил; остальные крупные книги (Добротолюбие, Лествица, ПВЛ, Маргарит) чистые.

**Приведение к юникоду** ([src/scripts/lib/hip.ts](src/scripts/lib/hip.ts), запуск —
`npm run db:normalize-hip`). Целью взят не учебник, а сам корпус: замерены 296 чистых
церковнославянских текстов (3,4 млн знаков), и замены приводят батч к их норме.
Снято 24 157 паразитных титл перед ударением (в корпусе такой пары нет ни разу; плотность
титл в Ифике была 7,8% против 0,42% по корпусу, после чистки 0,61%), 12 924 ASCII-ударения
(`` ` ``→вария, `^`→камора), 13 792 латинские подстановки (i→і, f→ѳ, W→Ѡ, S→Ѕ, V→Ѵ, JЬ→Ѣ,
Jа→Ꙗ), 720 числовых знаков (`#`→҂, `_пс`→ѱ, `_кс`→ѯ). 754 сноски уехали в `footnotes`,
822 колонтитула стали `{p|л. а҃}` — привязка к печатным страницам сохранена, из потока
чтения ушла. Исходник каждого текста лежит в поле `hipSource`, прогон обратим.

Не тронуто и напечатано списком: 19 мест в Ифике с `\@` и `[?]`. `\@` парами обрамляет
слово, к которому дана сноска-перевод, но границы стоят непоследовательно — по одному
тексту читается неоднозначно, гадать не стали.

**Нарезка** ([src/scripts/split-book.ts](src/scripts/split-book.ts), `npm run db:split-book
-- --book=ifika`). Прежний адрес каждого разрезанного текста стал оглавлением части

- **Ифика** — 70 разделов: 67 глав (медиана 3 тыс. знаков), две таблицы-вставки и

  короткий абзац без табуляции, без ссылки на сноску в начале и без номера с двоеточием.
  Оставшиеся ложные срабатывания перечислены поимённо в `NOT_A_HEADING`.
- **Книга правил** — 31 раздел и 3 оглавления, 757 правил, каждое с якорем `{a|N}`:

### Упоминания святых доведены до читателя — 2026-08-27

Граф связей был в базе, но наружу выходил одной стороной: со страницы святого было

**Поправка к цифрам.** «2468 текстов с `dneslovId`» — неверно: в счёт попадала пустая

**Имена святых** — [src/lib/dneslov.ts](src/lib/dneslov.ts). Кэш на сутки (тег

(память `10` не отвечает нигде, `102` отвечает по https и висит по http, разом это
меняется за минуты). Дело не в схеме, а в нестабильности сервиса, поэтому запрос
пробует https, затем http. Раньше `getDneslovObject` всегда ходил по http —
`process.env.NODE_ENV ? http : https` истинно всегда, задумано было обратное.

### Ударения: проверка расстановки — 2026-08-28

Знак ударения — отдельный символ ПОСЛЕ своей гласной, и при наборе или распознавании
он легко съезжает на соседнюю букву. Глазами это не вычитывается: на экране разница
в пиксель. Зато словарь ударных форм, собранный по самому корпусу, отличает «яќо» от
«я́ко» мгновенно — 12 тысяч правильных написаний против трёх десятков сбитых.

**Поправка к оценке.** Первый замер дал «21 320 сбитых знаков в 1225 документах» —
цифра завышена вчетверо с лишним, и виноват был сам замер: разбор рвал слова на буквах
Cyrillic Extended-C, считал ошибкой ударение, отделённое от гласной псили, и включал
румынскую Библию. Настоящее число — **1 997 слов**.

**Что сделано.** Исправлено **1 692 слова в 795 документах**, 291 оставлено человеку.
Скрипт [fix-accent-marks.ts](src/scripts/fix-accent-marks.ts) (`npm run db:fix-accents`),
общее ядро — [src/scripts/lib/accents.ts](src/scripts/lib/accents.ts), 14 тестов.

| основание правки | слов |
|---|---|
| словарь знает одно положение ударения | 1 045 |
| одно положение перевешивает остальные на порядок | 382 |
| лишний знак при другом, стоящем верно | 215 |
| сдвоенный знак подряд | 50 |
| **оставлено:** нет в словаре | 147 |
| **оставлено:** настоящее разночтение (го́ре / горе́) | 93 |
| **оставлено:** верная форма встретилась лишь однажды | 46 |
| **оставлено:** больше двух знаков в слове | 5 |

**Как чинится.** Знак не переставляется наугад: по слову без надстрочной разметки
ищется правильная форма в словаре, из неё берётся НОМЕР ударной гласной, и в исходном
слове знак ставится после той же по счёту гласной. Само слово словарной формой не
подменяется — иначе терялись бы ерок, титло и прочая разметка, которой в словарной
форме может не оказаться.

Страховки: dry-run по умолчанию, снимок прежнего содержимого перед записью, и главное —
инвариант «правка обязана менять только знаки ударения». Если снять их и слово выходит
другим, правка отклоняется при любой уверенности словаря. За оба прогона инвариант не
отклонил ни одной правки; повторный запуск находит 0 к исправлению.

**Что выяснилось про сам корпус** — всё это записано в ядре, чтобы следующий скрипт
не наступил заново:

- **Знаков ударения три, а не один.** Оксия U+0301, вария U+0300, камора U+0311.
  В Елизаветинской Библии вария стоит в 64 тысячах стихов, камора в 11 тысячах —
  проверка «по U+0301» четверти разметки не видит.
- **Вария часто вросшая.** ѐ (U+0450) и ѝ (U+045D) — это «е» и «и» с уже приросшим
  тупым ударением: 221 и 234 текста, 10 190 и 12 756 стихов. Считать их обычными
  буквами — значит потерять целый пласт ударных форм в словаре.
- **А ѓ (U+0453) и ќ (U+045C) — всегда ошибка.** Македонские буквы, согласная с
  приросшим ударением; нашлись в трёх текстах и до этой правки были невидимы вовсе,
  потому что одним символом.
- **Между гласной и ударением законно стоит псили** («а҆́ще»), поэтому проверять по
  непосредственно предыдущему символу нельзя — нужно отступать назад через всю диакритику.
- **Разложенные ї и й.** В Лествице и Маргарите они записаны как і+U+0308 и и+U+0306,
  а не одним знаком.
- **Ерок U+033E** заменяет ъ внутри слова («и҆з̾ ни́хъ») — слово на нём не делится.
- **Буквы Cyrillic Extended-C** (ᲂ, ᲅ, Ᲊ) стоят в Маргарите, Ифике и Алфавите. Разбор,
  который их не знает, рвёт слово посередине и видит обрывок.
- **Слова под титлом — сокращения и числа** (бж҃їѧ, к҃є = 25). Ударение к ним
  неприменимо, из проверки исключены: 75 слов.
- **ᲂ, ᲇ и ᲈ — гласные**, а не диковинные согласные: это о, ѣ и ꙋ старой графики,
  и в Маргарите ударение стоит прямо на них. Пропущено при первом заходе; из-за
  этого 13 верных написаний числились ошибками, а одно (`єгᲂ́` в `margarit-17`)
  успело «починиться» и было возвращено из снимка. Остальные буквы того же блока
  (ᲀ, ᲁ, ᲃ, ᲄ, ᲅ, ᲆ) — согласные и ъ.
- **Половина стихов — румынские.** Из 73 241 стиха 36 280 принадлежат «Сфънта
  Скриптура» (валашская кириллица 1688): другая орфография, свой набор знаков.
  Ни в словарь, ни в проверку.

**Словарь ударений** собирается только из слов без замечаний: иначе сбитая форма
голосовала бы сама за себя, а у редкого слова могла бы оказаться единственной.
Тем же кодом, что и артефакт, — см. следующий раздел.

**Осталось из плана по ударениям:** 28 неразмеченных текстов (решение отложено),
словарь как раздел публичного API и озвучка, ради которой всё это и затевалось.

### Ударения: словарь как артефакт — 2026-08-28

`npm run accents:build` ([build-accent-dictionary.ts](src/scripts/build-accent-dictionary.ts))
собирает словарь в файл. До этого он существовал только внутри текстов: каждый скрипт
перебирал весь корпус заново (полминуты) и заново решал, что считать ударением.

**Что в файле.** Ключ — слово без надстрочной разметки; значение — варианты
УДАРЕНИЯ, а не написания: `[номер ударной гласной, знак, частота, написание]`.

```
"глаголет": [[1, "́", 1100, "глаго́лет"]]
"руку":     [[0, "́", 173, "ру́ку"], [1, "́", 138, "руку́"], [1, "̀", 1, "руку̀"]]
```

**Группировка по положению ударения, а не по написанию** — главное решение здесь.
«а́дова» и «а҆́дова» различаются звательцем, ударение в них на одной и той же гласной,
и считать их спорной парой нельзя. Переход на положения снял **1408 ложных
разночтений** и сразу же дал 16 новых починок в проверке расстановки: слова вроде
«амин́ь», «ап́остола», «Избав́итель» до этого блокировались тем, что варианты
написания дробили счёт.

| | основ |
|---|---|
| всего | 182 812 |
| ударение везде на одной гласной | 174 707 |
| одно положение перевешивает на порядок | 1 881 |
| настоящее разночтение | 6 224 |

Ударных вхождений — 1 612 947: оксия 1 417 279, вария 164 263, камора 31 405.
Это чистое число, без румынской Библии и без слов со сбитым знаком.

**Файл воспроизводим:** ни времени сборки, ни путей внутрь не пишется, две сборки
на одной базе дают побайтово одинаковый результат (проверено по sha256). Размер —
10,7 МБ, `--pretty` для чтения глазами.

**Где ему жить — решать владельцу.** Сейчас он ложится в `script-data/`, а этот
каталог целиком в `.gitignore`, то есть файл остаётся локальным: ни в репозиторий,
ни на сервер он так не попадёт. Для пункта 5 плана (словарь как раздел публичного
API) нужно либо положить его в отслеживаемый каталог, либо загружать в Mongo и
возить вместе с базой. Это меняет и релиз, и то, что проект отдаёт наружу, поэтому
скрипт просто печатает предупреждение и ничего не решает сам.

**Заодно вынесено в общее** — [src/scripts/lib/corpus.ts](src/scripts/lib/corpus.ts):
чтение корпуса для работы с ударениями. Два места, где легко ошибиться, теперь
закрыты в одном: содержимое лежит в двух коллекциях (у библейских книг текст не в
`texts.content`, а построчно в `verses`), и половину стихов надо отбросить как
румынские. Сборка словаря и проверка расстановки берут корпус отсюда.

### Ударения: дописано пропущенное — 2026-08-28

Пункт 3 плана, в урезанном виде: только тексты, которые уже размечены. Скрипт —
[add-missing-accents.ts](src/scripts/add-missing-accents.ts) (`npm run accents:add`).

**Дописано 5 128 ударений в 1 217 текстах.** Самый наглядный случай — «Паренесис»,
где одно и то же слово стоит в строке дважды: «Испо́лните очеса́ ва́ша слез, и а́бие
отве́рзутся **очеса** ва́ша у́мная». Наборщик отвлёкся; глазами такое не выловить.

**Что считается пропуском.** Не «слово без знака» — в церковнославянском наборе
предлоги и частицы знака не несут, и первый замер выдал верхушку из «и», «не», «же»,
«бо», «на». Правило взято из самого корпуса: слову ударение положено, если оно
размечено не реже чем в девяти случаях из десяти («рече́» — 9 466 раз из 10 003,
«же» — 4 из 29 тысяч). Всего таких пропусков по собранию — 33 374, но две трети
приходятся на 28 текстов, которые не размечали никогда.

| состояние текста | текстов | не хватало |
|---|---|---|
| размечено полностью (≥99%) | 1 357 | 1 266 |
| редкие пропуски (90–99%) | 841 | 5 372 |
| размечено частично (30–90%) | 37 | 6 330 |
| **не размечено вовсе (<30%)** | **28** | **20 252** |

Работали только с верхними двумя полосами. Нижние две не трогали сознательно:
расставить ударения в тексте, где их не было (крупнейший — «Повесть временных лет»,
11 141 слово), — это работа за наборщика, а не исправление недосмотра. Отдельное
решение, отдельный разговор.

**Три отсечки, которые пришлось завести, глядя на живые примеры:**

- **Киноварь `{k|…}`** — уставные пометы, которые страница чтения печатает красным.
  В богослужебных книгах их не размечают: внутри киновари знак стоит у 39% слов
  против 98% снаружи. Отложено 275 слов в 46 текстах.
- **Неразмеченные куски внутри размеченного текста** — заголовок («Иже во святых
  отца нашего Иоанна, Архиепископа Константинопольскаго…») или цитируемое зачало,
  которое дальше толкуется («В начале бе Слово»). Поставить знак одному слову такой
  строки — сделать её наполовину размеченной, то есть хуже, чем было. Судим по
  соседям, и **соседи берутся только из той же строки**: без этого условия окно
  дотягивается из заголовка в размеченный текст следом и признаёт заголовок
  размеченным. Отложено 123 слова.
- **Живые разночтения** — 1 113 слов, где корпус даёт два положения ударения
  (`ру́ку` и `руку́`). Только вручную.

**Прогон сходится не с первого раза:** дописанный знак поднимает плотность вокруг
себя, и место, отложенное как неразмеченный кусок, на следующем проходе проверку
проходит. Пять проходов: 5101, 19, 4, 2, 2, 0. Разрастись это не может — строка, где
размечено меньше половины слов, не проходит проверку ни на каком проходе.

**Страховки те же:** dry-run по умолчанию, снимок содержимого перед записью, полный
список правок в TSV и инвариант — снимаем дописанный знак и обязаны получить
исходное слово в точности, причём добавлен должен быть ровно один знак. Опора нигде
не ниже девяти верных написаний; половина правок опирается на тысячу и больше.

После дописывания проверка расстановки (`npm run db:fix-accents`) находит 0 к
исправлению — новых сбитых знаков не появилось.

### Словарь ударений: публичный API — 2026-08-28

`/api/v2/accents` — 293 891 основа церковнославянских ударений. Раздел собран из
**трёх** источников, и это главное, что выяснилось при проектировании.

**Словарь ЦС сам размечен ударениями.** `typikon-csl.lexems` — 33 985 лексем и
148 210 порождённых по парадигмам форм, причём с ударениями, а поле `lexems.search`
— это в точности наш `accentKey`. То есть две базы говорят об одном и том же на одном
языке ключей, и до сих пор мы этого не использовали.

**Третий источник — корпус песнопений.** Октоих, Минеи, Триоди, Часослов лежат в
SQLite проекта typikon-rules (`RULES_DB`, см. [rulesDb.ts](src/lib/rulesDb.ts)) и тоже
размечены ударениями: 98 476 текстов, 2,8 млн слов, из них **2,12 млн размеченных** —
по весу свидетельств почти как весь книжный корпус (1,6 млн). Даёт 33 338 основ,
которых нет больше нигде: гимнография держит свою лексику («богоневе́стная»,
«живоприе́мному», «уневе́стивый»). Корпус на удивление чистый: сбитых знаков — 27 штук
на 2,1 миллиона.

| источник | основ |
|---|---|
| книжные чтения (Mongo, с частотами) | 182 812 |
| песнопения (SQLite typikon-rules, с частотами) | 85 922 |
| словарь ЦС (парадигмы, с грамматикой) | 138 629 |
| знают хотя бы двое | 95 276 |
| **вместе** | **293 891** |

Пересечения всюду частичные: словарь склоняет формы, которых в книгах ни разу не
встретилось; корпус знает употребление, которого нет в парадигмах; песнопения —
третий словарь поверх обоих.

**Частоты книг и песнопений не складываются.** Это главное решение по третьему
источнику. Жанр переворачивает большинство на омографах:

| слово | в чтениях | в песнопениях |
|---|---|---|
| спасе | `спасе́` ×50 (аорист) | `спа́се` ×2024 (звательный) |
| души | `души́` ×545 (ед. род.) | `ду́ши` ×3001 (мн. им.) |
| сердца | `се́рдца` ×814 | `сердца́` ×1293 |
| горе | `го́ре` ×342 (скорбь) | `горе́` ×676 (вверх) |
| лука | `лука́` ×57 (оружие) | `лу́ка` ×223 (имя) |

Сложенная частота дала бы невнятную середину вместо двух внятных ответов. Поэтому
`corpus` и `chants` — отдельные поля, и доля считается внутри источника. Потребитель
берёт тот, который отвечает его тексту.

Запись `спасе` показывает, зачем нужен и третий: словарь объясняет, отчего разница —
`спасе́` это `спасти́` aor. 2p/3p, а `спа́се` это `спа́съ` sg.voc. Два разных слова с
одинаковым написанием без знаков.

**Источники не сливаются в одну «истину».** Там, где знают хотя бы двое (95 276 основ),
ударная гласная совпадает в 97,6% случаев; 2 333 расхождения — разной природы:

- **законные омографы**: «зе́мли» (мн. им.) и «землѝ» (ед. род.) без знаков пишутся
  одинаково; так же «лица», «словеса», «дѣла», «горѣ», «души»;
- **ошибки порождения в словаре**, видные по самому словарю: у лексемы `твори́ти`
  форма `тво́рити`, у `или́` — `и́ли`, у `ѕѣлѡ́` — `ѕѣ́лѡ`. Ещё `наи́паче` против
  корпусного `наипа́че` (522 вхождения), `є́си` против `є҆сѝ` (3 289).

Весомых расхождений корпуса со словарём — где корпус видел слово 50 раз и больше —
**121**. Это готовый список правок для словарного опыта, но разобрать его может только
человек.

Поэтому ручка отдаёт **происхождение, а не приговор**: `corpus` и `chants` с частотами,
`lexicon` с грамматикой и признак `agree` (сошлись ли все знающие слово источники на
одной гласной). Потребитель синтеза берёт источник своего жанра; исследователь видит
разнобой как разнобой.

**Где лежит.** `typikon-csl.accents` — соседняя коллекция рядом со словарём, ключ
слова это `_id`. Своей базы не заводили: у `typikon-csl` общее с ударениями
пространство ключей, свой релиз (`csl-db-release.sh` делает `mongodump` всей базы,
так что коллекция едет на сервер без единой новой строки в выкладке) и та же
редкость пересчёта.

Имена полей в хранении короткие (`c` — книги, `h` — песнопения, `x` — словарь, `a` —
согласие; внутри `v`, `m`, `s`, `n`, `l`, `p`): записей почти триста тысяч, и при
длинных именах коллекция занимала 53,6 МБ уже на двух источниках, раздувая
`typikon-csl` с 8 МБ до 70. С короткими и с тремя источниками — 47,5 МБ, база 63,9 МБ. Наружу всё разворачивается в
читаемый вид в [store.ts](src/lib/accents/store.ts), так что короткие имена не выходят
за пределы модуля.

**Ядро переехало** из `src/scripts/lib/accents.ts` в
[src/lib/accents/core.ts](src/lib/accents/core.ts): из `src/scripts` приложению
импортировать нельзя, а разбор слова нужен теперь и API, и скриптам.

**Ручки.**

- `GET /api/v2/accents/{слово}` — одно слово. Слать можно как есть, с ударениями и в
  любой графике: `а҆́ще`, `аще` и `А́ЩЕ` — один запрос.
- `GET /api/v2/accents?words=аще,земли,зело` — до 200 слов, ответ в порядке запроса.
- `GET /api/v2/accents` — сводка, оговорка и ссылка на выгрузку.

**Промах — это `200` с `known: false`, а не `404`.** Сознательное отступление от
остального v2: имён собственных, редких форм и опечаток исходника в словаре нет и не
будет, для синтеза «не знаю» — рабочий ответ на каждое десятое слово, и заставлять
клиента ловить на этом ошибку значит мешать нормальную работу с поломкой.

Постраничного обхода нет намеренно: четверть миллиона записей по двести за раз — это
больше тысячи запросов ради того, что отдаётся одним файлом.

**Доступ** — как у всего остального: новый раздел `accents` в `SCOPES` и в
`FREE_SCOPES`. Без ключа 60 запросов в час (нынешний `ANONYMOUS_ALLOWANCE`, править
ничего не пришлось), по ключу — обычные тарифы. Ключи с `ALL_SCOPES` получили раздел
сами; в выдаче ключей раздел появился автоматически, она строится по `SCOPES`.

**Оговорка в самом ответе:** словарь описательный, а не нормативный. Он говорит, как
слово размечено в этом собрании и сколько раз, а не как правильно. Без этой строки его
начнут цитировать как источник нормы.

**Ссылка на выгрузку показывается только когда файл выложен** — по переменной
`ACCENTS_DUMP_URL`. Обещать в API адрес, которого нет, хуже, чем промолчать.
Сам файл пишет `npm run accents:load -- --dump путь.json` (48 МБ, из тех же записей,
что ложатся в коллекцию, — выгрузка и API не разъезжаются).

**Оговорка про чужой файл.** `build_db.py` в typikon-rules удаляет `data.db` и строит
заново, и чтение посреди пересборки даёт неполный срез — на этом и попались: тот же
файл отдал сперва 91 450 текстов вместо 98 476, а следом «database is locked».
Загрузчик поэтому печатает число прочитанных текстов и переживает недоступность файла,
собирая словарь без песнопений. Локально нужен `NODE_ENV=development`: иначе скрипт
читает `.env.production`, где `RULES_DB` указывает на путь сервера, и песнопения молча
выпадут.

**Осталось на стороне сервера:** раздача файла nginx'ом. По образцу apk
(`location /app/` → `/var/www/typikon-app-releases/`) — `location /data/` →
`/var/www/typikon-data/`, копирование в релизе и `ACCENTS_DUMP_URL` в окружении.

**Не делалось:** разметка целого отрывка (`POST /api/v2/accents/text`). Требует
разрешить `POST` в CORS (сейчас в `baseHeaders` только `GET, OPTIONS`) и перенести на
сервер разбор, который живёт в скриптах. Вторая очередь. Пока батч по словам закрывает
тот же сценарий, если клиент режет текст сам.

### Публичный API как продукт

Сделано: `/api/v2` с явной лицензией, описанием ручек (`/api`, `openapi.json`) и
стабильными адресами; `/api/v1` объявлен устаревшим и считает оставшихся клиентов.

Доступ отмерен по трём уровням (`src/lib/api/v2/tokens.ts` — правила, `access.ts` — их
применение к запросу):

| кто | сколько | разделы |
|---|---|---|
| свои страницы (Sec-Fetch-Site) | 120/мин с адреса | все |
| ключ, тариф `free` (профиль) | 30/мин, 10 000/сутки | все |
| без ключа | 60/час с адреса | все, кроме поиска |

Ключи пользователь заводит себе сам в профиле (до пяти). Ключи приложения и партнёров
выпускаются в админке (`/admin/api-tokens`: общий список с расходом, правка чисел,
отзыв и возврат) либо тем же скриптом с сервера:
`npm run api:token -- issue --name "Android" --tier app --apply`, там же `list`, `set`
и `revoke`. Отзыв доходит до API не позже чем через полминуты — столько живёт кэш
ключей; из профиля кэш сбрасывается сразу, но полагаться стоит на полминуты: админка
и публичный API — разные сборки, общей памяти у них может не быть.

Что осталось по этой теме:

- **Приложение пока ходит в v1 и без ключа.** Следующий шаг на его стороне: перейти на
  v2 и представляться ключом тарифа `app` — тогда доля клиентов без ключа станет видна
  так же, как сейчас видна доля без `X-Typikon-App`, и v1 можно будет закрывать.
- Счётчики частоты живут в памяти процесса — при переезде на несколько процессов их
  придётся выносить наружу (суточный расход уже в базе и переживёт).
- Отдельной страницы «мои ключи» с историей расхода по дням нет: в профиле видно
  только сегодняшнее число. Появится нужда — данные для этого уже пишутся
  (`typikon-users.apiTokenUsage`, по суткам).

Читателю неоткуда узнать, что корпус пополнился: правки тихие, а страница «О проекте»
со списком версий обновлялась руками и отстала. Поэтому — отдельная лента.

- Читают четверо: лента `/news`, отдельная запись `/news/{alias}`, фид

  без ключа) —
  все из одной кэшированной выборки, сбрасываемой тегом `news` при правке.
- Вкладки профиля открываются якорем: `/profile#tokens` ведёт сразу к ключам API, а не
  к чужим заметкам. Этим пользуются новость про публичный API и страница `/api`.

  иначе она горела бы у всех и всегда и перестала бы что-либо значить.
- Дата публикации ставится один раз: правка выложенной новости не поднимает её наверх
  ленты и не зажигает точку повторно.

## Обслуживание базы: какие скрипты и в каком порядке

Все — с холостым прогоном по умолчанию: без `--apply` печатают план и ничего не меняют.
Порядок важен, скрипты зависят друг от друга.

| команда | что делает | когда гонять |
|---|---|---|
| `npm run db:fix-aliases` | разводит документы с общим alias номерами `-1`, `-2` | до `db:indexes`, иначе уникальный индекс не встанет |
| `npm run db:indexes` | заводит индексы Mongo | после каждого `mongorestore --drop` |
| `npm run db:search-index` | заполняет `searchName`/`searchContent` и текстовый индекс | после массовых импортов текстов **и после любой правки `normalizeChurchSlavonic`** — иначе запрос нормализуется по новым правилам, а сохранённые копии останутся по старым |
| `npm run db:fix-triodion` | перестраивает подготовительный период Триоди | один раз |
| `npm run db:fix-paragraphs` | приводит границы абзацев к `\n\n` | один раз и после импортов |
| `npm run db:anonymize-logs` | заменяет сырые IP хэшем, подрезает `wasAt` | один раз |
| `npm run db:optimize-logs` | схлопывает адреса, сворачивает старое в помесячные итоги | по мере роста журнала |
| `npm run news:import-about` | переносит список версий со страницы «О проекте» в ленту новостей | один раз, после выкладки раздела новостей |
| `npm run release:rules-db` | везёт на сервер корпус песнопений (`data.db` проекта typikon-rules) | после каждой пересборки корпуса |
| `npm run release:ordo` | везёт службу сборки последования (`src/` и `rules/` проекта typikon-rules) | после правки кода сборки |
| `npm run release:ustav` | правка устава целиком: корпус, потом служба | после правки `rules/**.yaml` — вместо двух команд выше |
| `npm run mentions:find` | ищет кандидатов на упоминания святых | по желанию, дальше ревью в `/admin/mentions` |
| `npm run mentions:backfill` | дописывает к уже проставленным упоминаниям фрагмент текста | после ревью, если связи ставились до 2026-08-27 |
| `npm run db:fix-accents` | чинит съехавшие знаки ударения по словарю корпуса | после крупных импортов; по умолчанию только отчёт |
| `npm run accents:build` | словарь ударений ТОЛЬКО по корпусу, файлом | для замеров самого корпуса |
| `npm run accents:load` | публичный словарь (книги + песнопения + `lexems`) в `typikon-csl.accents` | после правок любого из трёх источников; локально с `NODE_ENV=development`, иначе песнопения выпадут; `--dump` заодно пишет файл выгрузки |
| `npm run accents:add` | дописывает пропущенные ударения в размеченных текстах | после импортов; повторять до «дописывать нечего» |

Флаги пробрасываются через `--`: `npm run db:indexes -- --apply`.

### Служба устава: последование собирает Python, а не сайт

Раздел `/ustav` показывает службу, собранную по Типикону: канву, наполненную
песнопениями книг, и рядом — правила, которые её так сложили. Собирает её не
сайт, а отдельный процесс `typikon-ordo` (`src/ordo_service.py` проекта
typikon-rules), поднятый systemd на 127.0.0.1:8767; адрес — в `ORDO_SERVICE_URL`.
Код лежит в `/var/www/typikon.su/typikon-ordo` — рядом с сайтом и корпусом, а
не в домашнем каталоге: служба системная, принадлежать одному человеку ей
незачем. Рядом, а не внутри `typikon-web`: там своё рабочее дерево git.

Почему не переписать сборку сюда. Устав — конструктор, а не выборка: сколько
единиц петь, откуда их брать и что чем подменяется, решают правила, написанные
руками в `rules/typikon`, и разбирают их полторы тысячи строк на Python.
Второй конструктор разошёлся бы с первым на первой же правке правила — а
правила правятся постоянно, устав ещё достраивается.

Наружу служба не смотрит и в nginx не проксируется: она читает файлы правил по
имени из запроса и про ключи доступа ничего не знает. Сайт ходит к ней сам, с
того же хоста, и отдаёт наружу уже разобранное. Текст правила для «лестницы»
проходит через внутреннюю ручку `/api/ordo/rule`, где путь проверяется второй
раз.

Корпус служба берёт тот же, что и сайт (`RULES_DB`), — второй копии файла на
сервере нет.

**Как доносить правку устава.** Правила живут на сервере в двух видах, и это не
дублирование: `build_db.py` разбирает `rules/**.yaml` в таблицы `ordo_steps`,
`typikon_allocation` и прочие — сборка читает их, а не файлы, и едут они внутри
корпуса; сами же файлы нужны «лестнице», которая показывает их текст, и едут со
службой. Выложить одно без другого — значит получить страницу, где показанное
правило не соответствует собранной службе, причём разойдутся они молча.

Поэтому на правку устава есть одна команда:

```
cd ../typikon-rules && python3 src/build_db.py   # правила -> таблицы
cd ../typikon-web   && npm run release:ustav     # корпус, затем служба
```

`release:ustav` сам проверяет, что корпус не старше правил: если `rules/` правили
после пересборки, он откажется — в базе лежал бы прежний устав, а «лестница»
показывала бы новые файлы.

Отдельные `release:rules-db` и `release:ordo` остаются для случаев, когда меняется
что-то одно: разобрана новая книга (корпус без кода) или поправлен код сборки
(служба без 91 МБ корпуса).

---

### Что нужно на сервере один раз

Выкладка идёт по ssh без терминала, и обычный `sudo` там пароль не спросит —
скажет «a terminal is required» и упадёт. Поэтому скрипты пользуются `sudo -n`:
он либо срабатывает молча, либо сразу отказывает, и тогда скрипт печатает, что
именно доделать руками, и **завершается с ошибкой**. Молча пропустить
привилегированный шаг нельзя: файл доедет, а сайт продолжит читать прежний
корпус по уже открытому дескриптору, и выкладка будет выглядеть удавшейся.

Проверить, есть ли право (на сервере, под admin):

```
sudo -n true && echo "есть" || echo "нет"
```

Если нет — из-под root, одной строкой в `/etc/sudoers.d/typikon`:

```
admin ALL=(root) NOPASSWD: /bin/systemctl restart typikon-web, /bin/systemctl restart typikon-ordo
```

(путь к `systemctl` сверить через `command -v systemctl` — на части систем это
`/usr/bin/systemctl`.)

Каталог под корпус заводить не нужно: он ложится в `/var/www/typikon.su/`,
рядом с каталогом сайта, куда admin и так пишет при каждой выкладке. Если
вдруг окажется, что писать туда нельзя, скрипт скажет об этом и предложит
`chown` или `setfacl` — но обычно этого шага нет.

Юнит `typikon-ordo.service` ставится из-под root — но однажды: меняется он
редко, и `release:ordo` переставляет его сам только тогда, когда право есть.

Замечание про уже существующее: `rebuild-remote.sh` вызывает
`sudo systemctl restart typikon-web.service` тем же способом и **без `set -e`**.
Если права нет, этот вызов всё это время молча не отрабатывал, а выкладка
считалась успешной — стоит проверить тем же `sudo -n true`.

### Второе хранилище: корпус песнопений

Раздел `/chants` и ручка `/api/v2/chants` читают не Mongo, а отдельный файл
SQLite — корпус проекта typikon-rules (`RULES_DB` в окружении). Это песнопения
книг, разобранные по местам службы: 95 тысяч строк Октоиха, Миней, Триодей и
Ирмология с памятями, знаками и гласами.

Лежит он в `/var/www/typikon.su/data.db` — **рядом** с каталогом сайта, а не
внутри него, и разница тут не в аккуратности. У `nobles.db` один читатель —
сайт, и жить внутри его каталога выкладки ему не мешает. У корпуса читателей
два: сайт и служба устава, выкладываемые порознь. А в каталоге сайта идут
`git pull`, `npm i` и сборка, и сделанный там `git clean -fdx` (обычный приём,
когда сборка сломалась) снёс бы 91 МБ корпуса разом у обоих разделов, ничем
себя не объяснив — `-x` удаляет и то, что перечислено в `.gitignore`.

Соседний каталог этого не касается, а главное — принадлежит тому же admin,
который выкладывает: корпус доставляется вообще без root. Пробовали
`/var/lib/typikon` — по уму место верное, но каталог там заводится только
из-под root, и ради одного файла это лишний шаг при каждой новой машине.

Почему файлом, а не в Mongo. Корпус целиком пересобирается из разобранных книг
и правил устава (`python3 src/build_db.py` в typikon-rules), руками в него не
правят, через админку не редактируют. Это артефакт сборки: класть его в Mongo
значило бы денормализовать реляционные связи и переиндексировать 95 тысяч
документов после каждой пересборки.

Поиск по нему держится на FTS5: токенизатор `unicode61 remove_diacritics 2`
снимает ударения при разборе на слова — и в тексте, и в запросе, — поэтому
нормализованные копии полей, какие приходится держать для Mongo
(`searchName`/`searchContent`), здесь не нужны.

Порядок: пересобрать корпус в typikon-rules -> `npm run release:rules-db`.
Скрипт сам проверяет, что индекс на месте, и перезапускает приложение: файл
открывается один раз на процесс, и без перезапуска новый корпус не увидят.

---

Все скрипты, меняющие контент, после записи сбрасывают кэш выборок через
`POST /api/revalidate`. Для этого нужен `REVALIDATE_TOKEN` в окружении — без него
скрипт предупредит, что сайт будет отдавать прежние данные до истечения кэша (час).

## Идеи развития продукта

**Фокус (2026-08-13, уточнён 2026-08-24):** доступность чтений, их связность между собой и
доведение до пользователя. Словарь/склонения остаётся экспериментом, который целенаправленно не
развиваем. Родословная (`nobles`) с 2026-08-24 **выведена из-под статуса эксперимента** и принята
как направление развития — см. раздел ниже.

### Доступность чтений
- **PWA / офлайн-режим** — чтение без интернета: кэширование текстов service worker'ом,
  установка сайта как приложения. Закрывает разрыв с тем, что офлайн сейчас есть только в Android-приложении.
- **iOS-приложение** — сейчас есть только Android (`public/app` → теперь `/var/www/typikon-app-releases`);
  часть аудитории на iPhone просто не имеет доступа к мобильному опыту.
- **Аудио / TTS чтений** — актуально для пожилых прихожан и незрячих; синтез вместо записи дикторов.
  Разобрано 2026-08-24, см. отдельный раздел «Озвучка чтений» ниже.
- **Настройки читаемости** — сделано 2026-08-28, см. раздел «Настройки читаемости»: размер, интервал,
  ширина колонки, выключка и цветовые пары. Не сделан режим сосредоточенного чтения и полная тёмная тема.

### Связность чтений
- **Единая лента дня** — сейчас день/триодь/жития/библиотека — разные разделы; можно собрать чтения дня
  в одну последовательную ленту вместо навигации по отдельным страницам.
- **Граф цитирования** — сноски и ссылки между текстами уже есть (`FootnoteLink`); можно углубить до
  "где ещё цитируется этот отрывок" / "похожие чтения" на основе существующих связей.
  Часть по святым сделана 2026-08-27, см. «Упоминания святых доведены до читателя»:
  блок связей под чтением, указатель `/saints`, страницы святых в карте сайта.
- **Персональные подборки/маршруты** — возможность собрать свою последовательность чтений
  (не только официальный порядок дня), сохранить и продолжить с места остановки.
- **Несколько текстов в слот** и **алиасы страниц** — были в старых планах (`NOTES.md`), всё ещё актуальны
  и хорошо ложатся в тему связности контента.

### Доведение до пользователя

### Озвучка чтений (TTS) — разобрано 2026-08-24

**Что проверено по данным.** Русских текстов в базе нет вообще: 0 документов с современно-русской
лексикой. Корпус целиком церковнославянский — 2925 текстов в гражданской орфографии
(«На стра́жи мое́й ста́ну») и 305 в собственно ЦС-графике (с ѣ, ꙋ, ѧ, титлами). У 1874 текстов есть
`ruLink`, но это внешняя ссылка (azbyka.ru), а не наш контент. Поэтому вариант «начать с русских
текстов», который стоял в блоке 3 аудита, недоступен — посылка была неверной.

**Что это компенсирует.** У 2142 текстов из 3230 уже расставлены ударения. Для русского синтеза
ударение — главная нерешённая проблема, а на церковнославянской лексике («зело́», «усмотри́х»,
«о́блацех») движок ошибался бы почти в каждом втором слове. Формат, который ждут и Яндекс, и Silero
(`+` перед ударной гласной), получается из наших данных одной заменой:

```
/([аеёиоуыэюяАЕЁИОУЫЭЮЯ])́/g  →  "+$1"      «На стра́жи мое́й» → «На стр+ажи мо+ей»
```

Из 1 055 167 знаков ударения 144 235 стоят не после русской гласной, но 133 397 из них — в текстах
ЦС-графики (после ѣ, ꙋ, ѧ, ѡ, і, ѵ). То есть для гражданского корпуса преобразование чистое, а
305 ЦС-текстов всё равно требуют предварительной транслитерации в гражданку — она полезна и сама
по себе, поиск по ним сейчас тоже не работает.

**Что доступно с сервера** (проверка 2026-08-24, [check-tts-endpoints.sh](check-tts-endpoints.sh)):
доступно **всё, кроме Telegram**. Яндекс SpeechKit отвечает за 50–90 мс (`tts.api.cloud.yandex.net`
— HTTP 401 без ключа, то есть хост живой), Object Storage и IAM тоже. Сбер и T-Bank доступны, но их
цепочка идёт от корневого центра Минцифры — нужен корневой сертификат на сервере. Хосты офлайн-моделей
(Silero, HuggingFace, GitHub releases, PyPI) доступны, значит офлайн-путь тоже открыт.

Это снимает аргумент, которым я отговаривал от облачного синтеза: блокировка Telegram оказалась
точечной, а не общим ограничением исходящего трафика, и переносить её на другие API было неверно.

**Два открытых пути, оба рабочие:**
- **Яндекс SpeechKit** — лучшее качество русского голоса, понимает `+`-ударения из коробки, платно
  по символам (корпус — 12,7 млн символов, разово; при пререндере повторно платить не за что).
  Требует облачного аккаунта, сервисного аккаунта и биллинга.
- **Silero офлайн** — бесплатно, на CPU, русские голоса, те же `+`-ударения, никакой внешней
  зависимости в рантайме. Качество ниже яндексового; нужен Python и место под модель.

**Как это ложится в архитектуру.** В обоих случаях правильная схема — не синтез на лету, а пререндер:
скрипт в `src/scripts` генерирует mp3 на текст, файлы раздаёт nginx (как сейчас раздаются APK),
перегенерация — в тот же момент, когда админка сбрасывает кэш после правки (`/api/revalidate`).
На чтении — нулевая задержка и нулевая стоимость, файл кладётся в офлайн-кэш PWA. Масштаб: 2276
готовых текстов, 12,7 млн символов ≈ 235 часов звука ≈ 3–7 ГБ mp3; медианный текст — около двух минут.

**Следующий шаг — не код, а пилот.** Главный риск не технический: синтетический голос на
богослужебном тексте может оказаться неприемлем для части аудитории, и «почти правильно» здесь хуже,
чем никак. Озвучить 5–10 представительных текстов (синаксарь, житие, текст с плотной ЦС-лексикой,
плюс обязательно один без проставленных ударений — чтобы услышать разницу и понять, что даёт работа
над словарём ударений) и дать послушать тем, для кого это делается. Выбор движка имеет смысл делать
после этого ответа, а не до.

### Родословная (`nobles`) — направление развития с 2026-08-24

Выведена из-под статуса эксперимента: модуль развиваем наравне с чтениями, фичи вокруг него
предлагать можно. Что уже есть в коде: импорт из Wikidata
(`npm run nobles:import-wikidata`, `nobles:import-wikidata-rules`), связывание со святцами

дерево на `family-chart`, FTS-поиск по SQLite.

Ближайшее, что вытекает из состояния кода (приоритеты за владельцем продукта):
- Довести импорт из Wikidata и дедупликацию до регулярного процесса — сейчас это разовые прогоны

- Типы: большая часть накопленных ошибок `tsc` (`unknown` из `better-sqlite3.all()`) — именно в этом

- Решить вопрос репозитория. Он не снимается тем, что модуль стал направлением: 129 файлов из ~494

  репозитории», либо кандидат на вынос в отдельный сервис/поддомен. Связь с основной базой идёт

## Автопостинг в Telegram/VK (@blagoslovie) — написан 2026-08-13, ОТЛОЖЕН 2026-08-24

> **Статус: отложено.** С прод-сервера `api.telegram.org` недоступен, `curl` тоже не проходит.
> Проверка 2026-08-24 ([check-tts-endpoints.sh](check-tts-endpoints.sh)) показала, что блокировка
> **точечная, именно на Telegram**: всё остальное с сервера доступно — Яндекс, Сбер, даже OpenAI,
> ElevenLabs и Google. То есть дело не в общем ограничении исходящего трафика. Обходы написаны
> (релей на Cloudflare Workers, поддержка прокси), но заводить и обслуживать ещё один внешний узел
> ради этого сейчас не хотим.
> Возвращаемся к вопросу, скорее всего, после переезда прода на другой сервер — если оттуда
> Telegram доступен напрямую, направление включается почти без работы: код готов, нужны только
> `TELEGRAM_CHANNEL_ID`, два крона и прогон на реальных данных.
>
> Пока отложено, направление «доведение до пользователя» лучше двигать через iCal-фид и PWA —
> они не зависят от доступности внешнего API с сервера.

Первая реализация направления "Доведение до пользователя". Публикует проложные чтения (`song6`)
в Telegram-канал `@blagoslovie` по формату, который уже используется в канале.

**Схема:**
1. `npm run channel-posts:generate` (cron, ежедневно) — берёт `song6.items` дня (эндпоинт
   `/api/v1/days/{month}-{DD}`), при 1 памяти — один черновик на 9:00, при 2+ — первые две,
   вечерняя (18:00 накануне) и утренняя (9:00). Фото и название памяти (для хэштега) — через
   `dneslovId` текста и внешнее API dneslov.org (уже используется сайтом в `/saints/[id]`,
   `DneslovImages`), при отсутствии `dneslovId` — эвристика по родительному падежу
   (`src/scripts/lib/heroName.ts`, помечается `nameSource: "heuristic"` для проверки в админке).
   Черновики пишутся в новую коллекцию Mongo `channelPosts`, статус `draft`.
2. `/admin/channel-posts` — ревью черновиков: правка текста/фото/хэштегов, кнопка
   "Готово к отправке" → статус `ready`. Без подтверждения пост не публикуется.
3. `npm run channel-posts:publish` (cron, 9:00 и 18:00) — публикует всё `ready` с наступившим
   `scheduledAt` в Telegram (`sendPhoto`/`sendMessage`, обычный Bot API — без личной MTProto-сессии,
   стабильнее). VK — заглушка (`publishToVk` в `publish-channel-posts.ts`), пайплайн уже готов
   принять реальный вызов.

Скрипты — TypeScript, запускаются через `tsx` (добавлен в devDependencies). Переменные окружения
подгружают сами через `@next/env` (`src/scripts/lib/env.ts`) — тот же механизм, что у `next dev`/
`next start`, вручную `.env.production` не нужно ни экспортировать, ни передавать флагами.

**Почему VK — заглушка:** канал `@blagoslovie` в VK создан как тип "Канал", а API для этого типа
сообществ сейчас в закрытой альфе VK (не общедоступно, не зависит от настроек прав). Рабочий путь —
`wall.post` в классическую Группу/Паблик; решение, заводить ли отдельное сообщество под автопостинг
или ждать открытия API каналов, ещё не принято.

**Нужно для запуска на сервере:**
- `TELEGRAM_CHANNEL_ID` в `.env.production` (бот должен быть админом канала с правом публикации);
  `TELEGRAM_BOT_TOKEN` уже есть.
- Два крона: генератор раз в день, паблишер в 9:00 и 18:00.

**Если api.telegram.org недоступен напрямую** (проверено — блокировка на уровне хостера/региона,
`curl https://api.telegram.org` с сервера тоже не проходит) — два обхода, включаются через
`.env.production`, код уже готов ([src/lib/channelPosts/telegram.ts](src/lib/channelPosts/telegram.ts)):
- `TELEGRAM_API_BASE=https://<worker>.workers.dev` — свой бесплатный релей на Cloudflare Workers,
  код и инструкция по деплою в [telegram-relay/worker.js](telegram-relay/worker.js) (просто
  прозрачно перекладывает запрос на api.telegram.org, токен в воркере не хранится).
- `TELEGRAM_PROXY_URL=http://user:pass@host:port` — если уже есть HTTP/SOCKS5-прокси.

**Не проверено на реальных данных** — вся логика прогнана на моках (мок-ответы dneslov.org,
без обращения к прод-базе). Перед первым запуском стоит проверить `channel-posts:generate`
на нескольких настоящих днях и просмотреть черновики в `/admin/channel-posts` до включения крона публикации.

### Настройка крона

Редактируется командой (у пользователя `admin`, под которым крутится сам сайт — см. `typikon-web.service`):
```bash
crontab -e
```

В начало файла — `PATH`, иначе cron не найдёт `npm`/`node` из nvm (тот же путь, что и в systemd-юните):
```
PATH=/home/admin/.nvm/versions/node/v20.20.2/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

Дальше сами задания:
```
0 3 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:generate 2>&1 | logger -t channel-posts-gen
0 9,18 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:publish 2>&1 | logger -t channel-posts-pub
```
`.env.production` подгружать вручную не нужно — скрипты делают это сами через `@next/env`
(`src/scripts/lib/env.ts`), важен только `cd` в корень репозитория, где лежит `.env.production`.

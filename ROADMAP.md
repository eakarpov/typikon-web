  `[...nextauth]`, реальный логин идёт через Google Identity Services → `POST /api/login`. Можно
  удалять `next-auth` из зависимостей и `src/app/api/auth/route.ts` целиком.

  по явному запросу и с предупреждением всех, кто клонирует репозиторий.
- **Разделение абзацев в `texts.content` непоследовательно** (обнаружено 2026-08-19, при работе над
  "сообщить об ошибке"): часть импортированных текстов хранит границу абзаца как `"\n \n"` (перевод
  строки, пробел, перевод строки), а не `"\n\n"`. И веб (`ReadingContent.tsx`, `data-paragraph-index`),

  для таких текстов весь текст (тысячи символов) становится одним "абзацем" вместо нескольких. На
  корректность самого функционала (выбор слова/подсветка, статьи/оглавление) не влияет — контейнер
  просто получается крупнее, чем нужно. Чинить не сейчас; если возьмёмся — скорее всего проще
  нормализовать сам `content` в БД (заменить `"\n \n"` → `"\n\n"` при импорте/миграцией), чем менять
  паттерн split на regex сразу в двух местах на разных платформах.

### Блок 1. Дешёвые победы

- **`<html lang="en">`** в [src/app/layout.tsx](src/app/layout.tsx) на русско-церковнославянском
  сайте — влияет на выдачу, скринридеры и переносы.
- **`public/sitemap.xml` статичен и мёртв** — 2493 URL, сгенерирован внешним сервисом
  mysitemapgenerator, у всех записей `lastmod = 2024-02-20`. Новые чтения и жития в индекс
  не попадают вообще. Для контентного сайта на ~3200 страниц это самая дешёвая органика,
  которую мы не берём. Заменить на `src/app/sitemap.ts`, строящий карту из Mongo по реальным
  `updatedAt`.
- **Поиск отдаёт всё и без ограничений** — [src/app/search/api.ts](src/app/search/api.ts)
  делает `$text` без `limit`, без `projection` и без пагинации: на запрос из трёх букв
  возвращает все совпавшие тексты целиком, вместе с полем `content` (тысячи символов на
  документ). UI при этом использует только `id` и `name`. Плюс rate limiting отсутствует —
  вместе это простой способ положить сервер.
- **Утечка sqlite-хендлов** — `init()` из [src/lib/sqlite.ts](src/lib/sqlite.ts) создаёт новый
  `Database` при каждом вызове (58 вызовов по коду), `db.close()` встречается один раз. В
  long-running процессе файловые дескрипторы копятся. Нужен синглтон на процесс.
- **`ignoreBuildErrors: true`** в [next.config.js](next.config.js) — типы в проде не проверяются
  вообще, при 247 `: any` по коду. Замер на 2026-08-24: `npx tsc --noEmit` даёт **171 ошибку**,
  большая часть — `unknown` из `better-sqlite3.all()` в модуле `nobles`. Снимать флаг можно только
  после разбора этой кучи, но знать её размер полезно уже сейчас.

### Блок 2. Архитектурный рычаг: сайт целиком динамический

Корневой [layout.tsx](src/app/layout.tsx) вызывает `verifySession()` и `getItem()` — это
заставляет Next рендерить **каждую** страницу динамически. Ни одной `revalidate` или
`generateStaticParams` в проекте нет (проверено, ноль вхождений): страница жития XII века ходит
в Mongo при каждом заходе анонима.

Что делать: вынести сессию из корневого layout (клиентский компонент или отдельный сегмент),
контентные маршруты — `/reading/[id]`, `/saints/[id]`, `/months/[id]`, `/library/[id]` — перевести
на ISR, инвалидация по хуку из админки при сохранении текста. Это самая крупная разовая выгода по
скорости и нагрузке, и она же делает осмысленным офлайн-кэш в PWA.

Рядом: **шрифты**. `public/fonts` — 1.2 МБ OTF, из них `myFont` тянет ~450 КБ (Regular + Bold)
до первой отрисовки текста на каждой странице чтения. Конвертация в woff2 даёт примерно двукратное
сокращение без потерь; сабсеттинг — больше, но аккуратно, чтобы не потерять церковнославянские
надстрочные знаки.

### Статус блока 2 — сделано 2026-08-24 (шрифты не трогали)

**Сессия убрана из рендера.** Корневой [layout.tsx](src/app/layout.tsx) больше не вызывает
`verifySession()`/`getItem()`; сессию забирает [SessionLoader](src/app/SessionLoader.tsx) с клиента
через новый `GET /api/session` и кладёт в тот же redux-стор, из которого меню читало её и раньше.
В `auth`-слайс добавлен флаг `isResolved` — без него у залогиненных на мгновение мигала кнопка
«Войти». `SessionChecker`/`SessionDispatcher` удалены как дублирующие. Важно: `SessionLoader` должен
лежать **внутри** `StoreProvider` — иначе react-redux падает уже на этапе пререндера.

**Что теперь кэшируется.** Пререндеренных маршрутов стало 19 против 2 (`/`, `/library`, `/calendar`,
`/triodion`, `/penticostarion`, `/rest-readings`, `/commons`, статические разделы). `/months/[id]` и
`/library/[id]` — ISR по первому запросу (`MISS` → `HIT`, проверено заголовком `x-nextjs-cache`).

Отдельная находка: **`export const revalidate` для динамического сегмента не работает без
`generateStaticParams`** — Next считает такой сегмент полностью динамическим и результат не кэширует
вовсе. Пустой массив (`generateStaticParams = async () => []`) включает генерацию по первому запросу
с последующим кэшированием, при этом сборка не тратит время на 2500 страниц.

**Выборки из базы кэшируются отдельно** ([src/lib/cache.ts](src/lib/cache.ts), `unstable_cache` с
тегами). Это то, что спасает страницы, которые остаются динамическими: `/reading/[id]` из-за
`?range`, а `/calendar/[id]`, `/weeks/[id]`, `/triodion/[id]`, `/calculator/[date]` — из-за cookie
языка Библии. Замеры на продовой сборке, первый запрос → последующие:

| маршрут | было | стало |
|---|---|---|
| `/calendar/march-30` | 271 мс | 23 мс |
| `/triodion/post-5-vt` | 435 мс | 33 мс |
| `/reading/dobrotolubie-30` | 78 мс | 18 мс |

Ошибки в кэш не попадают: `cachedTuple` пробрасывает их наружу, иначе сбой базы залипал бы на час.

**Инвалидация.** `POST /api/revalidate` (только админ, в проде без прав — 404) сбрасывает теги;
редакторы текстов и дней в админке дёргают его после сохранения
([src/lib/admin/revalidate.ts](src/lib/admin/revalidate.ts)). Отдельная ручка нужна потому, что API
админки живёт в pages-роутере, а `revalidateTag` работает только в app-роутере. Страховка по времени —
час для контента, 5 минут для главной (на ней церковная дата и список последних правок).

**Проверено:** тексты страниц продовой сборки сравнены с версией до изменений — на 14 маршрутах всех
типов единственное расхождение в том, что раньше в HTML попадал `Loading...` из Suspense, а теперь
контент отрендерен сразу. 32 адреса из карты сайта отдают 200. `tsc --noEmit` — 170 ошибок против
171 до начала работы, новых нет.

Что осталось за рамками:
- `/saints/[id]` не трогал — в файлах этого раздела лежит незакоммиченная работа по `nobles`.
- Инвалидация подвешена только на редакторы текстов и дней; книги, месяцы и недели правятся реже —
  их подхватит часовой таймаут.
- `CountMeta` на каждый просмотр страницы пишет в Mongo IP, URL и растущий массив `wasAt`
  ([src/app/api.ts](src/app/api.ts), `writeMetaData`). Рендер это не блокирует (запрос уходит с клиента
  после отрисовки), но документ на популярный URL растёт без ограничений, а собирать IP-адреса — это
  ещё и персональные данные. Стоит решить отдельно: ограничить массив или считать агрегатом.

### Блок 4. Что нужно решить, а не откладывать: `nobles` — РЕШЕНО 2026-08-24

129 файлов из ~494 в `src` относятся к родословной. При этом модуль был объявлен экспериментальным
и «не развиваем» — а последний коммит, незакоммиченные изменения в рабочем дереве и четыре новых

уходит время, — самая дорогая позиция в этом списке.

**Решение (2026-08-24):** родословная выведена из-под статуса эксперимента и принята как направление
развития. Расхождение снято в сторону признания второго направления. Вопрос отдельного
репозитория/поддомена остаётся открытым — см. раздел «Родословная (`nobles`)» ниже.

### Что удалось найти в сети (и чего там нет)

## Обслуживание базы: какие скрипты и в каком порядке

Все — с холостым прогоном по умолчанию: без `--apply` печатают план и ничего не меняют.
Порядок важен, скрипты зависят друг от друга.

| команда | что делает | когда гонять |
|---|---|---|
| `npm run db:fix-aliases` | разводит документы с общим alias номерами `-1`, `-2` | до `db:indexes`, иначе уникальный индекс не встанет |
| `npm run db:indexes` | заводит индексы Mongo | после каждого `mongorestore --drop` |
| `npm run db:search-index` | заполняет `searchName`/`searchContent` и текстовый индекс | после массовых импортов текстов |
| `npm run db:fix-triodion` | перестраивает подготовительный период Триоди | один раз |
| `npm run db:fix-paragraphs` | приводит границы абзацев к `\n\n` | один раз и после импортов |
| `npm run db:anonymize-logs` | заменяет сырые IP хэшем, подрезает `wasAt` | один раз |
| `npm run db:optimize-logs` | схлопывает адреса, сворачивает старое в помесячные итоги | по мере роста журнала |
| `npm run mentions:find` | ищет кандидатов на упоминания святых | по желанию, дальше ревью в `/admin/mentions` |

Флаги пробрасываются через `--`: `npm run db:indexes -- --apply`.

Все скрипты, меняющие контент, после записи сбрасывают кэш выборок через
`POST /api/revalidate`. Для этого нужен `REVALIDATE_TOKEN` в окружении — без него
скрипт предупредит, что сайт будет отдавать прежние данные до истечения кэша (час).

## Идеи развития продукта

**Фокус (2026-08-13, уточнён 2026-08-24):** доступность чтений, их связность между собой и
доведение до пользователя. Словарь/склонения остаётся экспериментом, который целенаправленно не
развиваем. Родословная (`nobles`) с 2026-08-24 **выведена из-под статуса эксперимента** и принята
как направление развития — см. раздел ниже.

### Доступность чтений
- **PWA / офлайн-режим** — чтение без интернета: кэширование текстов service worker'ом,
  установка сайта как приложения. Закрывает разрыв с тем, что офлайн сейчас есть только в Android-приложении.
- **iOS-приложение** — сейчас есть только Android (`public/app` → теперь `/var/www/typikon-app-releases`);
  часть аудитории на iPhone просто не имеет доступа к мобильному опыту.
- **Аудио / TTS чтений** — актуально для пожилых прихожан и незрячих; синтез вместо записи дикторов.
  Разобрано 2026-08-24, см. отдельный раздел «Озвучка чтений» ниже.
- **Настройки читаемости** — шрифт уже есть (`ChooseFontPicker`), можно добавить размер/контраст/тёмную тему,
  режим сосредоточенного чтения.

### Связность чтений
- **Единая лента дня** — сейчас день/триодь/жития/библиотека — разные разделы; можно собрать чтения дня
  в одну последовательную ленту вместо навигации по отдельным страницам.
- **Граф цитирования** — сноски и ссылки между текстами уже есть (`FootnoteLink`); можно углубить до
  "где ещё цитируется этот отрывок" / "похожие чтения" на основе существующих связей.
- **Персональные подборки/маршруты** — возможность собрать свою последовательность чтений
  (не только официальный порядок дня), сохранить и продолжить с места остановки.
- **Несколько текстов в слот** и **алиасы страниц** — были в старых планах (`NOTES.md`), всё ещё актуальны
  и хорошо ложатся в тему связности контента.

### Доведение до пользователя
- **Telegram-бот** — ОТЛОЖЕН 2026-08-24 вместе с автопостингом: с прод-сервера `api.telegram.org`
  недоступен. Код и обходы готовы, возвращаемся, скорее всего, после переезда прода.
- **Push-уведомления** — в вебе (PWA) и в приложении, привязать к времени начала дня по календарю.
- **Email-дайджест** — SMTP уже настроен (`nodemailer` используется для других писем).
- **Подписка на календарь** — iCal/Google Calendar фид с чтениями и памятями святых на день,
  доставка через уже существующий у пользователя календарь, а не через сайт. С отложенным Telegram
  это и email-дайджест — рабочие пути направления: они не зависят от того, дотягивается ли сервер
  до внешнего API.

### Технический долг / инфраструктура (сопутствует, не блокирует)

### Озвучка чтений (TTS) — разобрано 2026-08-24

**Что проверено по данным.** Русских текстов в базе нет вообще: 0 документов с современно-русской
лексикой. Корпус целиком церковнославянский — 2925 текстов в гражданской орфографии
(«На стра́жи мое́й ста́ну») и 305 в собственно ЦС-графике (с ѣ, ꙋ, ѧ, титлами). У 1874 текстов есть
`ruLink`, но это внешняя ссылка (azbyka.ru), а не наш контент. Поэтому вариант «начать с русских
текстов», который стоял в блоке 3 аудита, недоступен — посылка была неверной.

**Что это компенсирует.** У 2142 текстов из 3230 уже расставлены ударения. Для русского синтеза
ударение — главная нерешённая проблема, а на церковнославянской лексике («зело́», «усмотри́х»,
«о́блацех») движок ошибался бы почти в каждом втором слове. Формат, который ждут и Яндекс, и Silero
(`+` перед ударной гласной), получается из наших данных одной заменой:

```
/([аеёиоуыэюяАЕЁИОУЫЭЮЯ])́/g  →  "+$1"      «На стра́жи мое́й» → «На стр+ажи мо+ей»
```

Из 1 055 167 знаков ударения 144 235 стоят не после русской гласной, но 133 397 из них — в текстах
ЦС-графики (после ѣ, ꙋ, ѧ, ѡ, і, ѵ). То есть для гражданского корпуса преобразование чистое, а
305 ЦС-текстов всё равно требуют предварительной транслитерации в гражданку — она полезна и сама
по себе, поиск по ним сейчас тоже не работает.

**Что доступно с сервера** (проверка 2026-08-24, [check-tts-endpoints.sh](check-tts-endpoints.sh)):
доступно **всё, кроме Telegram**. Яндекс SpeechKit отвечает за 50–90 мс (`tts.api.cloud.yandex.net`
— HTTP 401 без ключа, то есть хост живой), Object Storage и IAM тоже. Сбер и T-Bank доступны, но их
цепочка идёт от корневого центра Минцифры — нужен корневой сертификат на сервере. Хосты офлайн-моделей
(Silero, HuggingFace, GitHub releases, PyPI) доступны, значит офлайн-путь тоже открыт.

Это снимает аргумент, которым я отговаривал от облачного синтеза: блокировка Telegram оказалась
точечной, а не общим ограничением исходящего трафика, и переносить её на другие API было неверно.

**Два открытых пути, оба рабочие:**
- **Яндекс SpeechKit** — лучшее качество русского голоса, понимает `+`-ударения из коробки, платно
  по символам (корпус — 12,7 млн символов, разово; при пререндере повторно платить не за что).
  Требует облачного аккаунта, сервисного аккаунта и биллинга.
- **Silero офлайн** — бесплатно, на CPU, русские голоса, те же `+`-ударения, никакой внешней
  зависимости в рантайме. Качество ниже яндексового; нужен Python и место под модель.

**Как это ложится в архитектуру.** В обоих случаях правильная схема — не синтез на лету, а пререндер:
скрипт в `src/scripts` генерирует mp3 на текст, файлы раздаёт nginx (как сейчас раздаются APK),
перегенерация — в тот же момент, когда админка сбрасывает кэш после правки (`/api/revalidate`).
На чтении — нулевая задержка и нулевая стоимость, файл кладётся в офлайн-кэш PWA. Масштаб: 2276
готовых текстов, 12,7 млн символов ≈ 235 часов звука ≈ 3–7 ГБ mp3; медианный текст — около двух минут.

**Следующий шаг — не код, а пилот.** Главный риск не технический: синтетический голос на
богослужебном тексте может оказаться неприемлем для части аудитории, и «почти правильно» здесь хуже,
чем никак. Озвучить 5–10 представительных текстов (синаксарь, житие, текст с плотной ЦС-лексикой,
плюс обязательно один без проставленных ударений — чтобы услышать разницу и понять, что даёт работа
над словарём ударений) и дать послушать тем, для кого это делается. Выбор движка имеет смысл делать
после этого ответа, а не до.

### Родословная (`nobles`) — направление развития с 2026-08-24

Выведена из-под статуса эксперимента: модуль развиваем наравне с чтениями, фичи вокруг него
предлагать можно. Что уже есть в коде: импорт из Wikidata
(`npm run nobles:import-wikidata`, `nobles:import-wikidata-rules`), связывание со святцами
dneslov (`nobles:link-dneslov`), поиск дубликатов (`nobles:find-duplicates`), разбор импортных
батчей в `/admin/nobles/import/[batchId]`, публичные страницы персон, семей, государств и правлений,
дерево на `family-chart`, FTS-поиск по SQLite.

Ближайшее, что вытекает из состояния кода (приоритеты за владельцем продукта):
- Довести импорт из Wikidata и дедупликацию до регулярного процесса — сейчас это разовые прогоны
  с ручным разбором в админке.
- Типы: большая часть накопленных ошибок `tsc` (`unknown` из `better-sqlite3.all()`) — именно в этом
  модуле, см. блок 5 аудита.
- Решить вопрос репозитория. Он не снимается тем, что модуль стал направлением: 129 файлов из ~494
  и отдельная база SQLite в общем продукте — это либо осознанный выбор «два направления в одном
  репозитории», либо кандидат на вынос в отдельный сервис/поддомен. Связь с основной базой идёт
  только через `dneslovId`, отделяется относительно чисто.

### Осознанно не в фокусе
- Словарь / морфология / склонения — эксперимент, не развиваем дальше как отдельное направление.

## Автопостинг в Telegram/VK (@blagoslovie) — написан 2026-08-13, ОТЛОЖЕН 2026-08-24

> **Статус: отложено.** С прод-сервера `api.telegram.org` недоступен, `curl` тоже не проходит.
> Проверка 2026-08-24 ([check-tts-endpoints.sh](check-tts-endpoints.sh)) показала, что блокировка
> **точечная, именно на Telegram**: всё остальное с сервера доступно — Яндекс, Сбер, даже OpenAI,
> ElevenLabs и Google. То есть дело не в общем ограничении исходящего трафика. Обходы написаны
> (релей на Cloudflare Workers, поддержка прокси), но заводить и обслуживать ещё один внешний узел
> ради этого сейчас не хотим.
> Возвращаемся к вопросу, скорее всего, после переезда прода на другой сервер — если оттуда
> Telegram доступен напрямую, направление включается почти без работы: код готов, нужны только
> `TELEGRAM_CHANNEL_ID`, два крона и прогон на реальных данных.
>
> Пока отложено, направление «доведение до пользователя» лучше двигать через iCal-фид и PWA —
> они не зависят от доступности внешнего API с сервера.

Первая реализация направления "Доведение до пользователя". Публикует проложные чтения (`song6`)
в Telegram-канал `@blagoslovie` по формату, который уже используется в канале.

**Схема:**
1. `npm run channel-posts:generate` (cron, ежедневно) — берёт `song6.items` дня (эндпоинт
   `/api/v1/days/{month}-{DD}`), при 1 памяти — один черновик на 9:00, при 2+ — первые две,
   вечерняя (18:00 накануне) и утренняя (9:00). Фото и название памяти (для хэштега) — через
   `dneslovId` текста и внешнее API dneslov.org (уже используется сайтом в `/saints/[id]`,
   `DneslovImages`), при отсутствии `dneslovId` — эвристика по родительному падежу
   (`src/scripts/lib/heroName.ts`, помечается `nameSource: "heuristic"` для проверки в админке).
   Черновики пишутся в новую коллекцию Mongo `channelPosts`, статус `draft`.
2. `/admin/channel-posts` — ревью черновиков: правка текста/фото/хэштегов, кнопка
   "Готово к отправке" → статус `ready`. Без подтверждения пост не публикуется.
3. `npm run channel-posts:publish` (cron, 9:00 и 18:00) — публикует всё `ready` с наступившим
   `scheduledAt` в Telegram (`sendPhoto`/`sendMessage`, обычный Bot API — без личной MTProto-сессии,
   стабильнее). VK — заглушка (`publishToVk` в `publish-channel-posts.ts`), пайплайн уже готов
   принять реальный вызов.

Скрипты — TypeScript, запускаются через `tsx` (добавлен в devDependencies). Переменные окружения
подгружают сами через `@next/env` (`src/scripts/lib/env.ts`) — тот же механизм, что у `next dev`/
`next start`, вручную `.env.production` не нужно ни экспортировать, ни передавать флагами.

**Почему VK — заглушка:** канал `@blagoslovie` в VK создан как тип "Канал", а API для этого типа
сообществ сейчас в закрытой альфе VK (не общедоступно, не зависит от настроек прав). Рабочий путь —
`wall.post` в классическую Группу/Паблик; решение, заводить ли отдельное сообщество под автопостинг
или ждать открытия API каналов, ещё не принято.

**Нужно для запуска на сервере:**
- `TELEGRAM_CHANNEL_ID` в `.env.production` (бот должен быть админом канала с правом публикации);
  `TELEGRAM_BOT_TOKEN` уже есть.
- Два крона: генератор раз в день, паблишер в 9:00 и 18:00.

**Если api.telegram.org недоступен напрямую** (проверено — блокировка на уровне хостера/региона,
`curl https://api.telegram.org` с сервера тоже не проходит) — два обхода, включаются через
`.env.production`, код уже готов ([src/lib/channelPosts/telegram.ts](src/lib/channelPosts/telegram.ts)):
- `TELEGRAM_API_BASE=https://<worker>.workers.dev` — свой бесплатный релей на Cloudflare Workers,
  код и инструкция по деплою в [telegram-relay/worker.js](telegram-relay/worker.js) (просто
  прозрачно перекладывает запрос на api.telegram.org, токен в воркере не хранится).
- `TELEGRAM_PROXY_URL=http://user:pass@host:port` — если уже есть HTTP/SOCKS5-прокси.

**Не проверено на реальных данных** — вся логика прогнана на моках (мок-ответы dneslov.org,
без обращения к прод-базе). Перед первым запуском стоит проверить `channel-posts:generate`
на нескольких настоящих днях и просмотреть черновики в `/admin/channel-posts` до включения крона публикации.

### Настройка крона

Редактируется командой (у пользователя `admin`, под которым крутится сам сайт — см. `typikon-web.service`):
```bash
crontab -e
```

В начало файла — `PATH`, иначе cron не найдёт `npm`/`node` из nvm (тот же путь, что и в systemd-юните):
```
PATH=/home/admin/.nvm/versions/node/v20.20.2/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

Дальше сами задания:
```
0 3 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:generate 2>&1 | logger -t channel-posts-gen
0 9,18 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:publish 2>&1 | logger -t channel-posts-pub
```
`.env.production` подгружать вручную не нужно — скрипты делают это сами через `@next/env`
(`src/scripts/lib/env.ts`), важен только `cd` в корень репозитория, где лежит `.env.production`.

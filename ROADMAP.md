## Аудит от 2026-08-13

### Исправлено
- Обход авторизации в admin API (~28 эндпоинтов: nobles, days, months, weeks, books, texts, signs, places) —
  `checkRightsBack()` не прерывал выполнение обработчика при отказе в доступе. Теперь возвращает `boolean`,
  все вызовы обёрнуты в `if (!(await checkRightsBack(req, res))) return;`.
- SQL-инъекция в поиске по SQLite (родословная: nobles/states/families/nationalities/rules, публичный v1 API
  и admin) — строка поиска подставлялась в `LIKE '%${search}%'` напрямую. Заменено на параметризованные запросы.
- Файлы Android-приложения (`public/app/*.apk`) выведены из git — раздували `.git` до 477 МБ с каждым релизом.
  Теперь заливаются на сервер напрямую через nginx (`location /app/` → `/var/www/typikon-app-releases/`),
  см. `release-app.sh`.

### Требует внимания (не исправлено)
- `src/app/api/auth/route.ts` — колбэк `jwt` логирует `console.log(token, account, user)` (утечка OAuth
  id_token в серверные логи), плюс хардкодит `https://typikon.su/login`. (Сам роут — мёртвый код
  next-auth, см. ниже; при удалении next-auth снимется само собой.)
- Два параллельных механизма авторизации: собственный JWT+cookie (`src/lib/authorize/*`) и `next-auth`.
  Подтверждено (2026-08-19): next-auth полностью мёртв — путь роута не совпадает с ожидаемым
  `[...nextauth]`, реальный логин идёт через Google Identity Services → `POST /api/login`. Можно
  удалять `next-auth` из зависимостей и `src/app/api/auth/route.ts` целиком.
- Устаревшие зависимости: `mongodb` v4 (актуальна v6), `typescript` 4.9, возможно мёртвый `next-auth`.
- Нет тестов и CI (`.github/workflows` отсутствует).
- `.git` уже весит 477 МБ из-за истории apk-коммитов — сама история не сожмётся сама по себе;
  переписывание истории (`git filter-repo`/BFG) — отдельная, более рискованная операция, делать только
  по явному запросу и с предупреждением всех, кто клонирует репозиторий.
- **Разделение абзацев в `texts.content` непоследовательно** (обнаружено 2026-08-19, при работе над
  "сообщить об ошибке"): часть импортированных текстов хранит границу абзаца как `"\n \n"` (перевод
  строки, пробел, перевод строки), а не `"\n\n"`. И веб (`ReadingContent.tsx`, `data-paragraph-index`),
  и мобильное приложение (`text_page.dart`, `content.split("\n\n")`) делят по буквальному `"\n\n"` —
  для таких текстов весь текст (тысячи символов) становится одним "абзацем" вместо нескольких. На
  корректность самого функционала (выбор слова/подсветка, статьи/оглавление) не влияет — контейнер
  просто получается крупнее, чем нужно. Чинить не сейчас; если возьмёмся — скорее всего проще
  нормализовать сам `content` в БД (заменить `"\n \n"` → `"\n\n"` при импорте/миграцией), чем менять
  паттерн split на regex сразу в двух местах на разных платформах.

### Исправлено (после аудита, вне протокола выше)
- Google-логин (`POST /api/login`) не проверял подпись id_token — доверял `user_id`, присланному
  клиентом напрямую. Теперь верифицируется через `google-auth-library` (2026-08-19, для мобильного
  Google Sign-In и заодно для веба).
- `getUserByVKId/GoogleId/TelegramId` — были то же самое, что и SQL-инъекция из аудита выше: точное
  совпадение подобъекта `{"auth.google": {userId}}`. Заменено на `"auth.google.userId": id` (2026-08-19).
- `/api/report` не проверял сессию — `userId` брался из тела запроса как есть. Теперь берётся из
  `getSession()`, без валидной сессии — `401` (2026-08-19).

## Аудит от 2026-08-24 (код, не продукт)

Разбор по коду, дополняет продуктовые идеи ниже. Пять блоков по убыванию отношения
пользы к трудозатратам.

### Блок 1. Дешёвые победы

- **`<html lang="en">`** в [src/app/layout.tsx](src/app/layout.tsx) на русско-церковнославянском
  сайте — влияет на выдачу, скринридеры и переносы.
- **`public/sitemap.xml` статичен и мёртв** — 2493 URL, сгенерирован внешним сервисом
  mysitemapgenerator, у всех записей `lastmod = 2024-02-20`. Новые чтения и жития в индекс
  не попадают вообще. Для контентного сайта на ~3200 страниц это самая дешёвая органика,
  которую мы не берём. Заменить на `src/app/sitemap.ts`, строящий карту из Mongo по реальным
  `updatedAt`.
- **Поиск отдаёт всё и без ограничений** — [src/app/search/api.ts](src/app/search/api.ts)
  делает `$text` без `limit`, без `projection` и без пагинации: на запрос из трёх букв
  возвращает все совпавшие тексты целиком, вместе с полем `content` (тысячи символов на
  документ). UI при этом использует только `id` и `name`. Плюс rate limiting отсутствует —
  вместе это простой способ положить сервер.
- **Утечка sqlite-хендлов** — `init()` из [src/lib/sqlite.ts](src/lib/sqlite.ts) создаёт новый
  `Database` при каждом вызове (58 вызовов по коду), `db.close()` встречается один раз. В
  long-running процессе файловые дескрипторы копятся. Нужен синглтон на процесс.
- **`ignoreBuildErrors: true`** в [next.config.js](next.config.js) — типы в проде не проверяются
  вообще, при 247 `: any` по коду. Замер на 2026-08-24: `npx tsc --noEmit` даёт **171 ошибку**,
  большая часть — `unknown` из `better-sqlite3.all()` в модуле `nobles`. Снимать флаг можно только
  после разбора этой кучи, но знать её размер полезно уже сейчас.

### Блок 2. Архитектурный рычаг: сайт целиком динамический

Корневой [layout.tsx](src/app/layout.tsx) вызывает `verifySession()` и `getItem()` — это
заставляет Next рендерить **каждую** страницу динамически. Ни одной `revalidate` или
`generateStaticParams` в проекте нет (проверено, ноль вхождений): страница жития XII века ходит
в Mongo при каждом заходе анонима.

Что делать: вынести сессию из корневого layout (клиентский компонент или отдельный сегмент),
контентные маршруты — `/reading/[id]`, `/saints/[id]`, `/months/[id]`, `/library/[id]` — перевести
на ISR, инвалидация по хуку из админки при сохранении текста. Это самая крупная разовая выгода по
скорости и нагрузке, и она же делает осмысленным офлайн-кэш в PWA.

Рядом: **шрифты**. `public/fonts` — 1.2 МБ OTF, из них `myFont` тянет ~450 КБ (Regular + Bold)
до первой отрисовки текста на каждой странице чтения. Конвертация в woff2 даёт примерно двукратное
сокращение без потерь; сабсеттинг — больше, но аккуратно, чтобы не потерять церковнославянские
надстрочные знаки.

### Блок 3. Продукт: закончить начатое важнее, чем начать новое

Автопостинг в Telegram написан целиком, но не проверен на реальных данных и крон не включён.
Незапущенная фича — ноль ценности при 100% затрат. Прогнать генератор на 5–7 настоящих днях,
просмотреть черновики, включить крон — дешевле любого нового направления и закрывает заявленный
фокус «доведение до пользователя».

Приоритеты внутри фокуса (уточнение к списку ниже):
1. **iCal-фид** — один route, данные уже есть в `/api/v1/days`, доставка идёт в календарь,
   которым человек уже пользуется. Лучшее отношение пользы к трудозатратам.
2. **PWA** — manifest + service worker; даёт офлайн вебу и частично закрывает iOS-разрыв
   (установка на домашний экран) без затрат на нативное приложение. Осмысленно делать
   **после** блока 2: кэшировать статически отрендеренные страницы намного проще.
3. **TTS** — начинать с русских синаксарей и житий; церковнославянский синтезом читается плохо,
   попытка начать с него закопает направление.

### Блок 4. Что нужно решить, а не откладывать: `nobles`

129 файлов из ~494 в `src` относятся к родословной. При этом модуль объявлен экспериментальным
и «не развиваем» — а последний коммит, все незакоммиченные изменения в рабочем дереве и четыре
новых скрипта в `package.json` относятся именно к нему. Расхождение между заявленным фокусом и
тем, куда уходит время, — самая дорогая позиция в этом списке.

Варианты: вынести в отдельный репозиторий или поддомен (модуль на sqlite, связь с основной базой
только через `dneslovId` — отделяется относительно чисто) либо честно признать вторым направлением
и убрать из «осознанно не в фокусе». Промежуточное состояние хуже обоих.

### Блок 5. Гигиена

- **Тесты — начинать не с UI**, а с [calcDay.ts](src/lib/calcDay.ts) и
  [lectionaryCycle.ts](src/utils/lectionaryCycle.ts): чистые функции с проверяемыми ответами
  (Пасха и отступки по годам). Это одновременно самая опасная логика в проекте (баг `/api/calc`
  с 400 на неделях 2–33 уже был) и идеальный кандидат для юнит-тестов. CI: `next build` +
  `tsc --noEmit` + эти тесты.
- **Мониторинг** — 209 `console.log` по коду, ошибки видны только в логах сервера.
- **Версии** — Next 14.2.12 → минимум 14.2.25+ (в 14.2.x был CVE-2025-29927 в middleware; у нас
  middleware не авторизующий, так что не эксплуатируется, но сидеть на уязвимой версии незачем),
  mongodb v4 → v6, TS 4.9 → 5.x, удалить мёртвый `next-auth`.
- **Индексы Mongo нигде не заводятся в коде** (`createIndex` — ноль вхождений). `$text`-поиск и
  `$match` по `dneslovId`/`mentionIds` работают ровно настолько, насколько индексы созданы руками
  на проде и переживают `mongorestore --drop`. Вынести в скрипт-миграцию.
- **`NOTES.md`** — в `.gitignore`, в историю не попадал (проверено `git log -- NOTES.md`), но
  root-пароль сервера лежит открытым текстом в рабочем каталоге. Сменить, перейти на ssh-ключи,
  отключить парольный вход для root.

## Идеи развития продукта

**Фокус (2026-08-13):** доступность чтений, их связность между собой и доведение до пользователя.
Словарь/склонения и родословная (`nobles`) — экспериментальные модули, целенаправленно не развиваем
(см. заметку ниже), новые фичи вокруг них не предлагаем.

### Доступность чтений
- **PWA / офлайн-режим** — чтение без интернета: кэширование текстов service worker'ом,
  установка сайта как приложения. Закрывает разрыв с тем, что офлайн сейчас есть только в Android-приложении.
- **iOS-приложение** — сейчас есть только Android (`public/app` → теперь `/var/www/typikon-app-releases`);
  часть аудитории на iPhone просто не имеет доступа к мобильному опыту.
- **Аудио / TTS чтений** — актуально для пожилых прихожан и незрячих; можно начать с TTS без записи дикторов.
- **Настройки читаемости** — шрифт уже есть (`ChooseFontPicker`), можно добавить размер/контраст/тёмную тему,
  режим сосредоточенного чтения.

### Связность чтений
- **Единая лента дня** — сейчас день/триодь/жития/библиотека — разные разделы; можно собрать чтения дня
  в одну последовательную ленту вместо навигации по отдельным страницам.
- **Граф цитирования** — сноски и ссылки между текстами уже есть (`FootnoteLink`); можно углубить до
  "где ещё цитируется этот отрывок" / "похожие чтения" на основе существующих связей.
- **Персональные подборки/маршруты** — возможность собрать свою последовательность чтений
  (не только официальный порядок дня), сохранить и продолжить с места остановки.
- **Несколько текстов в слот** и **алиасы страниц** — были в старых планах (`NOTES.md`), всё ещё актуальны
  и хорошо ложатся в тему связности контента.

### Доведение до пользователя
- **Telegram-бот** — самый дешёвый первый шаг: токен бота уже в `.env`, контент уже есть через v1 API;
  ежедневная рассылка чтения / жития дня.
- **Push-уведомления** — в вебе (PWA) и в приложении, привязать к времени начала дня по календарю.
- **Email-дайджест** — SMTP уже настроен (`nodemailer` используется для других писем).
- **Подписка на календарь** — iCal/Google Calendar фид с чтениями и памятями святых на день,
  доставка через уже существующий у пользователя календарь, а не через сайт.

### Технический долг / инфраструктура (сопутствует, не блокирует)
- Rate limiting на публичных API (`search`, `dictionary`) — сейчас отсутствует.
- Мониторинг ошибок (Sentry и т.п.) — сейчас ошибки только в `console.log`.
- Тесты хотя бы для критичных путей (авторизация, поиск, чтение дня) + CI на build/lint.

### Осознанно не в фокусе
- Словарь / морфология / склонения — эксперимент, не развиваем дальше как отдельное направление.
- Родословная (`nobles`) — эксперимент, не развиваем дальше; в будущем стоит решить, оставлять ли модуль
  в этом же продукте/репозитории или выносить отдельно.

## Автопостинг в Telegram/VK (@blagoslovie) — реализовано 2026-08-13

Первая реализация направления "Доведение до пользователя". Публикует проложные чтения (`song6`)
в Telegram-канал `@blagoslovie` по формату, который уже используется в канале.

**Схема:**
1. `npm run channel-posts:generate` (cron, ежедневно) — берёт `song6.items` дня (эндпоинт
   `/api/v1/days/{month}-{DD}`), при 1 памяти — один черновик на 9:00, при 2+ — первые две,
   вечерняя (18:00 накануне) и утренняя (9:00). Фото и название памяти (для хэштега) — через
   `dneslovId` текста и внешнее API dneslov.org (уже используется сайтом в `/saints/[id]`,
   `DneslovImages`), при отсутствии `dneslovId` — эвристика по родительному падежу
   (`src/scripts/lib/heroName.ts`, помечается `nameSource: "heuristic"` для проверки в админке).
   Черновики пишутся в новую коллекцию Mongo `channelPosts`, статус `draft`.
2. `/admin/channel-posts` — ревью черновиков: правка текста/фото/хэштегов, кнопка
   "Готово к отправке" → статус `ready`. Без подтверждения пост не публикуется.
3. `npm run channel-posts:publish` (cron, 9:00 и 18:00) — публикует всё `ready` с наступившим
   `scheduledAt` в Telegram (`sendPhoto`/`sendMessage`, обычный Bot API — без личной MTProto-сессии,
   стабильнее). VK — заглушка (`publishToVk` в `publish-channel-posts.ts`), пайплайн уже готов
   принять реальный вызов.

Скрипты — TypeScript, запускаются через `tsx` (добавлен в devDependencies). Переменные окружения
подгружают сами через `@next/env` (`src/scripts/lib/env.ts`) — тот же механизм, что у `next dev`/
`next start`, вручную `.env.production` не нужно ни экспортировать, ни передавать флагами.

**Почему VK — заглушка:** канал `@blagoslovie` в VK создан как тип "Канал", а API для этого типа
сообществ сейчас в закрытой альфе VK (не общедоступно, не зависит от настроек прав). Рабочий путь —
`wall.post` в классическую Группу/Паблик; решение, заводить ли отдельное сообщество под автопостинг
или ждать открытия API каналов, ещё не принято.

**Нужно для запуска на сервере:**
- `TELEGRAM_CHANNEL_ID` в `.env.production` (бот должен быть админом канала с правом публикации);
  `TELEGRAM_BOT_TOKEN` уже есть.
- Два крона: генератор раз в день, паблишер в 9:00 и 18:00.

**Если api.telegram.org недоступен напрямую** (проверено — блокировка на уровне хостера/региона,
`curl https://api.telegram.org` с сервера тоже не проходит) — два обхода, включаются через
`.env.production`, код уже готов ([src/lib/channelPosts/telegram.ts](src/lib/channelPosts/telegram.ts)):
- `TELEGRAM_API_BASE=https://<worker>.workers.dev` — свой бесплатный релей на Cloudflare Workers,
  код и инструкция по деплою в [telegram-relay/worker.js](telegram-relay/worker.js) (просто
  прозрачно перекладывает запрос на api.telegram.org, токен в воркере не хранится).
- `TELEGRAM_PROXY_URL=http://user:pass@host:port` — если уже есть HTTP/SOCKS5-прокси.

**Не проверено на реальных данных** — вся логика прогнана на моках (мок-ответы dneslov.org,
без обращения к прод-базе). Перед первым запуском стоит проверить `channel-posts:generate`
на нескольких настоящих днях и просмотреть черновики в `/admin/channel-posts` до включения крона публикации.

### Настройка крона

Редактируется командой (у пользователя `admin`, под которым крутится сам сайт — см. `typikon-web.service`):
```bash
crontab -e
```

В начало файла — `PATH`, иначе cron не найдёт `npm`/`node` из nvm (тот же путь, что и в systemd-юните):
```
PATH=/home/admin/.nvm/versions/node/v20.20.2/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

Дальше сами задания:
```
0 3 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:generate 2>&1 | logger -t channel-posts-gen
0 9,18 * * * cd /var/www/typikon.su/typikon-web && npm run channel-posts:publish 2>&1 | logger -t channel-posts-pub
```
`.env.production` подгружать вручную не нужно — скрипты делают это сами через `@next/env`
(`src/scripts/lib/env.ts`), важен только `cd` в корень репозитория, где лежит `.env.production`.
